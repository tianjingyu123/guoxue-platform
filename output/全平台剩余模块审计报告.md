> **审计范围**：前三轮（支付/订单、分佣、财务/对账、会员、实名认证、风控、多分站、功能开关、系统配置、用户封禁/GDPR、商家、管理后台RBAC）未覆盖的全部剩余模块
> **审计日期**：2026-05-21
> **审计方法**：四维度端到端审计（功能完整性 → 业务一致性 → 数据安全 → 边界与异常）
> **审计覆盖**：50+ 后端模块 + 125+ 管理后台视图
> **排盘系列排除**：paipan, fortune, classic-bazi, tool-registry, bazi-engine, ziwei-engine

## 执行摘要

### 审计分四组并行执行

| 组别 | 审计域 | 模块数 | P0 | P1 | P2 |
|------|--------|--------|----|----|-----|
| 1 | 社区社交 + 商业变现 | 11 | 0 | 18 | 若干 |
| 2 | 运营自动化 + 通信通知 | 14 | 12 | 35 | 25 |
| 3 | AI智能服务 + 内容发布 | 21 | 0 | 14 | 30+ |
| 4 | 基础设施 + 公共层 | 19 | 0 | 2 | 15 |
| **合计** | | **65+** | **12** | **69** | **70+** |

### 最严重的横向问题（跨多个模块的共性问题）

1. **被封禁用户未全局阻断**：至少 8 个模块（IM、通知、签到、SMS、Bot、WebSocket、AI Gateway、Comment/Interaction）未检查用户 banned 状态
2. **多分站数据隔离缺失**：至少 8 个模块/查询（operation-engine、task、competition、churn、content、classic、discover、article.getHomeFeed）未带 stationId 过滤
3. **configSystem 万能 KV 存储**：运营数据、热榜、邮件模板等全部塞进一张表，无版本历史、覆盖式写入
4. **内存互斥锁不可用于多实例**：Operation Engine/Robot cron 用内存 boolean flag 做锁，多实例部署 100% 冲突
5. **非安全随机数使用**：SMS 验证码（Math.random()）、Competition 出题（Math.random()）、Gray Release（Math.random()）

### 4.6 架构级发现

**configSystem 万能 KV 存储问题**：
- Operation Engine（轮换推荐、热榜、周报）、Operation Robot（配置）、Email（模板）全部存进 configSystem
- 每次 Cron 运行覆盖上一次结果，无历史版本
- 表膨胀风险：configSystem 承担了本该由 5+ 张独立表承担的功能

**内存互斥锁不可多实例**：
- Operation Engine/Robot 的 Cron 用内存 boolean flag 做锁
- 单实例安全但多实例 100% 冲突
- 应改用 Redis 分布式锁或 BullMQ 等任务队列

**双轨限流策略**：
- Redis (分布式) + Memory (单机) 两套并行
- 灵活但有维护负担 — 两套代码需保持同步

**纯原生 API 调用**：
- Coze、SMS、Email、Push 全部使用裸 HTTP/TLS
- 优点：零 SDK 依赖，包体积小
- 风险：重连/超时/错误处理全部手写，维护成本高
