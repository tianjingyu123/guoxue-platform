# 一、资金流向全链路

## 模块：shop（商城/订单/支付）

### [P0-阻塞上线] 支付回调多表操作无事务保护
- 涉及文件：`apps/server/src/modules/shop/shop.service.ts`，`handlePaymentNotify` 方法（约第500-560行）
- 问题描述：支付回调成功后依次执行：更新订单状态(PAID) → 计算分佣(commissionSvc.calculateAndRecord) → 更新会员(memberLevel/memberExpire)。这三步是三次独立数据库操作，不在 Prisma `$transaction` 中。如果分佣计算成功但会员更新失败，订单已标记为已支付但用户未获得会员，造成资金与权益不一致。
- 影响范围：所有支付回调场景（微信/支付宝/银联/汇付），涉及实际资金入账
- 修复方向建议：将回调中的订单状态更新、分佣记录、会员开通包裹在同一个 `$transaction` 中，确保原子性；或引入 Saga 补偿模式

### [P0-阻塞上线] 退款后分佣未回收
- 涉及文件：`apps/server/src/modules/shop/shop.service.ts`，`refundOrder` 方法（第754-794行）
- 问题描述：退款仅将订单状态改为 REFUNDED，未冲正已发放的分佣。推荐人已获得的 StationEarning 和平台的 PlatformFeeRecord 在退款后仍然存在。这意味着恶意用户可以通过"购买→退款"循环刷佣金。
- 影响范围：所有已退款订单对应的分佣记录，资金安全风险
- 修复方向建议：退款时检查是否存在分佣记录，若存在则创建冲正记录；或退款回调中调用 commissionSvc 进行佣金回收

### [P0-阻塞上线] 取消订单不恢复库存和优惠券
- 涉及文件：`apps/server/src/modules/shop/shop.service.ts`，`cancelOrder` 方法（约第878行）
- 问题描述：用户取消订单时，`createOrder` 中已扣减的库存不会恢复，已标记为已使用的优惠券不会释放。在支付回调与取消的竞态场景中，这会导致库存永久损失和优惠券浪费。
- 影响范围：被取消订单的商品库存、用户优惠券
- 修复方向建议：cancelOrder 中增加库存恢复（increment stock）和优惠券释放（标记 used=false）

### [P0-阻塞上线] cancelOrder 与支付回调无互斥锁
- 涉及文件：`apps/server/src/modules/shop/shop.service.ts`，`cancelOrder` 和 `handlePaymentNotify`
- 问题描述：cancelOrder 检查订单状态为 PENDING 后执行取消；handlePaymentNotify 检查订单状态为 PENDING 后执行支付成功。两个操作之间没有分布式锁或乐观锁。在并发场景下，支付回调可能将订单改为 PAID，然后 cancelOrder 再将其改为 CANCELLED，导致"用户付了钱但订单被取消"。
- 影响范围：所有 PENDING 状态订单的支付和取消操作
- 修复方向建议：cancelOrder 和 handlePaymentNotify 使用同一个分布式锁 key（如 `order:lock:{orderId}`），或使用 Prisma 乐观锁（version 字段 + updateMany where status=PENDING）

### [P1-影响体验] 优惠券折扣金额未在服务端计算
- 涉及文件：`apps/server/src/modules/shop/shop.service.ts`，`createOrder` 方法（第269-274行）
- 问题描述：创建订单时如果传入 couponId，仅标记 `userCoupon.used = true`，未在服务端重新计算优惠后的 `actualAmount`。订单金额可能包含未经验证的优惠券折扣。
- 影响范围：所有使用优惠券的订单
- 修复方向建议：服务端根据优惠券类型重新计算折扣金额，`actualAmount = 商品总价 - 优惠券折扣`

### [P1-影响体验] 支付宝/银联退款需管理员手动调用
- 涉及文件：`apps/server/src/modules/shop/shop.controller.ts`，`alipayRefund` / `unionpayRefund` 端点
- 问题描述：refundOrder 方法仅对接微信支付退款。支付宝和银联的退款需管理员在后台手动调用独立 API，没有统一的退款入口。管理后台也没有这两个 API 的操作入口。
- 影响范围：支付宝/银联支付的订单退款流程
- 修复方向建议：refundOrder 中根据订单的支付渠道自动路由到对应退款接口，管理后台统一入口

### [P2-锦上添花] 超时未支付订单无自动取消
- 涉及文件：`apps/server/src/modules/shop/shop.service.ts`
- 问题描述：shop 模块没有定时任务自动取消超时未支付订单（如30分钟未支付）。PENDING 订单会永久保持 PENDING 状态，占用库存。
- 影响范围：长期未支付订单占用的库存
- 修复方向建议：添加定时任务（Cron），每5分钟扫描超过30分钟的 PENDING 订单并自动取消

## 模块：commission（分佣）

### [P0-阻塞上线] 分佣记录与收益更新不在同一事务
- 涉及文件：`apps/server/src/modules/commission/commission.service.ts`，`calculateAndRecord` 方法（第51-108行）
- 问题描述：创建 StationEarning 记录和原子更新 station.totalEarning 是两个独立操作，不在 `$transaction` 中。如果 totalEarning 更新成功但 StationEarning 创建失败，分站余额与实际记录不一致。
- 影响范围：所有分佣计算场景
- 修复方向建议：将 StationEarning 创建和 station.totalEarning 更新包裹在同一个 `$transaction` 中

### [P1-影响体验] 提现门槛配置割裂
- 涉及文件：`apps/server/src/modules/commission/commission.service.ts`，`applyWithdrawal` 方法（第186-194行）

- 影响范围：运维配置体验
- 修复方向建议：将提现门槛迁移到 ConfigSystem，或至少在前端提供统一的配置入口

### [P2-锦上添花] 管理后台无平台抽成汇总独立页面
- 涉及文件：`apps/server/src/modules/commission/commission.controller.ts`，`GET commission/platform-fee/summary`

## 模块：finance（财务）

### [P0-阻塞上线] 对账逻辑未实际对比支付渠道账单
- 涉及文件：`apps/server/src/modules/finance/finance.service.ts`，`triggerReconciliation` 方法（第15-47行）
- 问题描述：对账逻辑仅汇总内部 PAID 订单金额，直接标记为 MATCHED，没有从支付渠道下载账单进行逐笔比对。WechatPayService 已有 `downloadTradeBill` 和 `downloadFundFlowBill` 能力，但 FinanceService 未调用。这意味着"对账"功能形同虚设，无法发现资金差异。
- 影响范围：资金安全——无法发现支付渠道与平台之间的金额差异
- 修复方向建议：triggerReconciliation 中调用 WechatPayService 下载账单，逐笔比对订单号+金额+状态，发现差异时标记为 MISMATCHED 并记录差异明细

### [P2-锦上添花] 管理员确认支付无二次确认
- 涉及文件：`apps/admin/src/views/shop/OrderList.vue`（约第43-46行）

- 影响范围：误操作风险
- 修复方向建议：为 adminPayOrder 操作添加确认弹窗

# 二、管理后台功能完整性与合理性

## 模块：全局管理后台

### [P0-阻塞上线] RBAC 权限前后端不一致
- 涉及文件：`apps/admin/src/router/index.ts` vs 各 Controller 的 @Roles() 装饰器
- 问题描述：
  1. **FINANCE_ADMIN**：前端路由可见财务页面（对账/结算/提现审核等），但后端 finance.controller.ts 只允许 SUPER_ADMIN 和 OPERATION_ADMIN。FINANCE_ADMIN 进入页面后所有操作返回 403。
  2. **OPERATION_ADMIN**：后端允许操作财务，但前端路由的 meta.roles 未包含 OPERATION_ADMIN，导致该角色看不到财务菜单。

- 影响范围：三个管理员角色的正常使用，属于阻断性问题
- 修复方向建议：统一前后端角色定义——或者调整后端 @Roles() 装饰器，或者调整前端路由 meta.roles；建议以 PRD 的角色权限矩阵为准，一次性对齐

# 三、跨模块业务一致性

## 模块：user（用户管理）

### [P0-阻塞上线] 封禁用户仍可下单、消费、提现
- 涉及文件：
  - `apps/server/src/modules/user/user.service.ts`，`updateUserStatus` 方法
  - `apps/server/src/modules/shop/shop.service.ts` — 创建订单不检查用户状态
  - `apps/server/src/modules/coin/coin.service.ts` — 消费不检查用户状态
  - `apps/server/src/modules/commission/commission.service.ts` — 提现不检查用户状态
  - `apps/server/src/modules/content/content.service.ts` — 发布不检查用户状态
- 问题描述：`updateUserStatus` 仅将 user.status 改为 DISABLED，但以下操作完全不检查该字段：
  - 下单（shop.service.ts createOrder）
  - 虚拟币消费（coin.service.ts spend）
  - 提现申请（commission.service.ts applyWithdrawal）
  - 内容发布（content.service.ts create）
  被封禁用户的功能与正常用户完全一致。
- 影响范围：平台安全——封禁机制形同虚设
- 修复方向建议：
  1. 创建全局 Guard（如 `ActiveUserGuard`），在需要身份验证的端点统一检查 user.status
  2. 或在各关键操作的 Service 方法入口处增加状态检查

### [P1-影响体验] 用户注销流程未实现
- 涉及文件：Prisma Schema 中 User 模型有 `deleteRequestedAt` 字段，但 user.service.ts 无对应方法
- 问题描述：用户注销（GDPR 合规）流程完全未实现——无法申请注销、无法执行数据清理、无法处理注销后的订单/资金。
- 影响范围：法律合规（个人信息保护法）
- 修复方向建议：实现完整的注销流程——用户申请 → 冷静期 → 数据清理/匿名化 → 资金处理

## 模块：station（分站）

### [P1-影响体验] 分站数据隔离依赖业务代码自觉
- 涉及文件：所有含 stationId 字段模型的 Service 文件
- 问题描述：Prisma Schema 中 7 个模型（Content/Article/Circle/Course/Product/Video/ToolRecord）声明了 stationId，但 Service 层采用"传入才过滤"模式。无全局 Guard 或中间件强制注入 stationId。按 ID 查询单条记录的方法（如 getProduct、getOrder）完全不检查 stationId。任何知道 record ID 的用户都可以访问任意分站的数据。
- 影响范围：多分站数据隔离的安全性
- 修复方向建议：
  1. 从 JWT/user 中获取绑定的 stationId，而非信任客户端 Header
  2. 所有带 stationId 模型的查询统一注入 WHERE 条件
  3. 按 ID 查询单条时也需校验 stationId 归属

# 四、边界与异常场景

## 模块：shop（商城）

### [P0-阻塞上线] 优惠券核销缺少完整校验
- 涉及文件：`apps/server/src/modules/shop/shop.service.ts`，`createOrder` 方法中的优惠券处理
- 问题描述：创建订单使用优惠券时，未校验：
  1. 优惠券是否在有效期内
  2. 优惠券状态是否可用
  3. 优惠券是否属于当前用户
  4. 订单金额是否满足最低消费门槛
- 影响范围：可能被恶意利用无效/过期/他人优惠券
- 修复方向建议：在 createOrder 中增加优惠券的多维度校验逻辑

### [P1-影响体验] 库存扣减原子但超卖风险存在
- 涉及文件：`apps/server/src/modules/shop/shop.service.ts`，`createOrder` 方法（第236-278行）
- 问题描述：库存扣减在 `$transaction` 中使用 `updateMany where stock > 0` 实现了原子扣减，这一点是安全的。但超时未支付订单不会自动取消和恢复库存，在高并发 + 高放弃率场景下，库存被大量 PENDING 订单占用。
- 影响范围：商品库存管理
- 修复方向建议：结合 P1 的"超时自动取消"修复，取消时恢复库存
