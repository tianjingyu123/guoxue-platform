# 头部平台全栈质量标准与执行方案 V1.0

> 生效日期：2026-08-23（本机时区）
> 适用范围：移动端、管理端、服务端、数据库、算法引擎、基础设施、内容与运营
> 原则：以用户任务成功率和业务可恢复性为核心，以自动化证据代替主观“看起来可用”。

## 1. 对标目标

本项目的目标不是复制某一家产品的视觉外观，而是达到头部内容、社区、电商与知识服务平台共同具备的能力：

1. **可信**：内容来源、交易身份、权限边界、资金流向和操作记录可解释、可追溯。
2. **顺畅**：核心任务路径短，等待、空状态、失败、弱网和重复提交均有确定行为。
3. **稳定**：以 SLO、错误预算和可观测性管理可靠性，不依赖人工发现线上故障。
4. **安全**：默认拒绝、最小权限、纵深防御；敏感操作必须鉴权、审计、限流和幂等。
5. **可演进**：自动发布门禁覆盖代码、数据、镜像、迁移、监控和回滚，支持小步发布。

## 2. 全域量化标准

| 领域 | 头部标准 | 最低验收阈值 | 发布阻断条件 |
| --- | --- | --- | --- |
| 产品任务 | 主路径闭环、状态可恢复、术语一致 | 核心任务成功率 ≥ 98%；关键路径无死入口；失败可重试且不产生重复业务结果 | 核心路径中断、假入口、误导性成功 |
| UI 与设计系统 | 品牌辨识、组件一致、信息层级清晰 | 统一色彩/字阶/间距/圆角/状态；触控目标建议 ≥ 44×44 CSS px；加载、空、错、禁用状态齐全 | 关键操作不可见、状态无反馈、遮挡操作 |
| 无障碍 | 对齐 WCAG 2.2 AA | 键盘可达；焦点可见；表单有标签；语义/ARIA 正确；正文对比度 ≥ 4.5:1；支持减少动态效果 | 登录、支付、发布等关键路径只能依赖鼠标或颜色识别 |
| Web 性能 | 以真实用户 p75 评估 Core Web Vitals | LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1；路由级懒加载；首屏不加载非关键编辑器/图表 | 首屏出现阻塞性大资源回归且无豁免 |
| 移动体验 | 弱网、前后台、跨端行为一致 | 首屏有骨架；请求可取消/防抖；前后台恢复；安全区适配；网络失败可恢复 | 白屏、不可返回、重复支付/下单 |
| 服务端 API | 契约稳定、默认安全、可观测 | 月度可用性 ≥ 99.9%；普通读 p95 ≤ 300ms、写 p95 ≤ 500ms；5xx ≤ 0.1%；全链路 trace/request ID | 未鉴权敏感接口、跨角色/跨站点越权、关键接口无幂等 |
| 数据库 | 一致性、可迁移、可恢复 | 金额使用精确定点类型；业务唯一约束；查询索引；事务边界清晰；RPO ≤ 5 分钟、RTO ≤ 30 分钟 | 破坏性迁移无双写/回滚方案、备份不可恢复 |
| 权限与多租户 | 默认拒绝、最小权限、数据域隔离 | RBAC + 资源归属/站点隔离；服务端强制校验；敏感操作二次确认并审计 | 仅前端隐藏权限、默认放行、IDOR |
| 应用安全 | 对齐 OWASP ASVS 5.0 L2 | 输入白名单与清洗；CSP/安全响应头；密钥外置；回调验签；限流；依赖无未批准 Critical/High | 明文密钥、签名绕过、Critical/High 漏洞无处置 |
| 管理后台 | 分角色工作台、批量效率、全链路审计 | 角色首屏与职责匹配；筛选可复用；批量操作可预览/撤销；导出受权限控制 | 资金/审核/删除操作无确认或无审计 |
| 内容与 AI | 来源可信、风险透明、可人工接管 | 版权与来源字段强制；AI 结论含边界说明；高风险输出可拦截/人工复核；缓存、成本和质量可度量 | 无版权依据上线、把模型输出包装成确定事实 |
| 可观测性 | 黄金信号、SLO、可行动告警 | 延迟/流量/错误/饱和度齐全；日志指标追踪可关联；告警含影响、阈值、负责人和处置手册 | 关键服务无监控、无回滚信号、告警无法行动 |
| 交付与供应链 | 可复现、可回滚、证据化发布 | lint、typecheck、单测、E2E、构建、依赖、镜像、迁移、备份、监控、回滚全门禁；制品不可变 | 任一强制门禁失败或证据缺失 |

## 3. 多角色审计视角

| 角色 | 必查问题 |
| --- | --- |
| 普通用户 | 能否在最短路径发现内容、完成学习/互动/购买，并理解每一种状态？ |
| 创作者/主播 | 发布、审核、开播、收益和申诉是否闭环；失败能否恢复？ |
| 商家 | 商品、库存、订单、发货、退款、对账是否一致且可追溯？ |
| 客服 | 是否能在权限范围内定位用户旅程、订单和错误，并安全处理？ |
| 内容审核 | 来源、版权、风险、版本和发布记录是否完整？ |
| 财务 | 金额精度、审批、对账、结算、退款和审计链是否不可抵赖？ |
| 运营 | 是否有可信指标、分角色看板、批量效率和异常处置入口？ |
| 安全/合规 | 是否默认拒绝、密钥外置、回调验签、数据隔离、日志脱敏？ |
| 开发/测试/SRE | 是否可在上线前自动发现回归，并在上线后快速定位和回滚？ |

## 4. 执行方案

### 阶段 A：基线与红线

- 盘点页面、接口、数据库模型、角色、外部回调和发布制品。
- 将越权、资金错误、数据破坏、核心路径中断、明文密钥定义为 P0/P1。
- 运行现有发布门禁，先修门禁自身的假阳性和漏检，再评价业务代码。

### 阶段 B：体验与功能闭环

- 按“入口 → 任务 → 反馈 → 恢复 → 追溯”审查每条核心旅程。
- 对管理端实施角色化信息架构；对移动端补齐触控、键盘、辅助技术与弱网语义。
- 将修复转化为回归测试，避免依赖人工记忆。

### 阶段 C：服务端与数据纵深

- 验证鉴权、角色/站点隔离、输入清洗、幂等、事务、回调验签和审计日志。
- 验证 Prisma 基线、索引/唯一约束、迁移可回滚、备份与恢复证据。
- 对关键 API 建立延迟、错误率、队列积压和外部依赖指标。

### 阶段 D：发布与运营闭环

- 代码门禁：lint → typecheck → 算法 → 单测 → E2E → 多端构建。
- 交付门禁：依赖 → 镜像 → 配置绑定 → 迁移 → 备份 → 监控 → 回滚。
- 上线采用小流量/分批发布；以 SLO 和错误预算决定继续放量或回滚。

## 5. 严重度与处置时限

| 级别 | 定义 | 处置 |
| --- | --- | --- |
| P0 | 资金/数据不可逆、严重越权、全站不可用 | 立即阻断发布并回滚，持续处置直至恢复 |
| P1 | 核心角色或核心路径不可用、重大安全风险 | 当次发布必须修复，不允许无期限豁免 |
| P2 | 非核心能力降级、性能/体验明显落后 | 纳入最近迭代，设负责人和验收指标 |
| P3 | 一致性、效率或长期维护性问题 | 进入技术债池，按收益和风险排序 |

## 6. 每次发布的完成定义（Definition of Done）

1. 需求与角色边界明确，关键状态和失败恢复已实现。
2. 新增逻辑有单测或契约/E2E 证据；修复项有回归保护。
3. lint、typecheck、核心算法、服务端单测、E2E、多端构建全部通过。
4. 数据迁移、备份、监控、告警、回滚和外部依赖证据齐全。
5. 浏览器/真机完成桌面、窄屏、键盘、弱网与关键角色复验。
6. 不存在未处理的 P0/P1；P2/P3 有明确记录、负责人和期限。
