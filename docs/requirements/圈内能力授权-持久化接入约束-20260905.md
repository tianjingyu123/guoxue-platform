每项规则完整填写以下字段，不补默认业务值：

| 字段 | 含义 |
| --- | --- |
| revision / enabled | 策略修订与显式启停；修订变化后旧批准不能自动套用新策略 |

| maxActiveViolations | 当前仍生效、未过期的圈内违规记录上限 |
| reapplyCooldownHours | 驳回/撤销后从处理时间计算的重新申请等待期 |
| maxValidityDays | 人工批准可给出的有效期上限 |
| maxUnits / maxConcurrent | 单次授权的总业务次数与并发上限；尚不是 SDK 资源预留或带宽/存储预算 |
| providerRoles | 可接受的服务者角色子集 OWNER/PARTNER/GUEST，不硬删既有 PARTNER 角色 |

事实采集固定为 `valid-circle-posts-v1`：成员账号正常、未删除且成员关系有效；帖子已发布、非明确审核拒绝、作者正常、定时发布时间已到；近期统计窗口由配置指定。圈内帖 auditStatus 是推首页审核字段，普通圈内帖子不能因其 PENDING 默认值被全排除。违规记录仅统计 ACTIVE 且仍生效的记录。不用已有全平台发布服务的快速通道、缓存指标或固定阈值。

## 2. 主体与生命周期

普通申请接入方案：圈主为本圈能力、以及本圈服务者发起申请；平台按配置审核；服务者本人主动启用自己的问答能力，圈主不能代嘉宾点击启用。该分工用于让圈主控制本圈资源入口，同时保留嘉宾接单意愿，未对外开放。用户 2026-09-05 补充的平台直授优先规则见 2.1，不得以普通申请条件限制平台直授。

- 达标只生成 PENDING 申请；批准得到 APPROVED 但 enabled=false。
- 圈级批准不传递给所有嘉宾。音频/视频问答都需对应圈级和该服务者两份有效授权；两种问答互不通用。
- 启用前检查圈子、当前圈主/成员关系/身份、策略修订、服务者角色和有效期；更换圈主不能沿用旧圈主授权。
- 审批/恢复禁止申请人、当前/原圈主或服务者自审批；自动化不能执行权限变更。
- 暂停后恢复仍需本人重新启用；到期授权不能直接启用，需重新申请。到期是由 expiresAt 派生的有效状态，不靠定时任务准时改状态才能拒绝新增。
- 损坏配置不允许新审批或启用；平台治理角色仍能人工撤销，主体仍能停用，避免安全关闭动作被配置故障堵死。
- 既有已付费订单查询、履约、退款、申诉不调用“新业务资格”闸门。

### 2.1 平台定向直授（用户补充，已实现本地内核/事务/HTTP 边界）

- 平台真人 `SUPER_ADMIN` / `OPERATION_ADMIN` 可为名师或战略伙伴直接指定圈子、对象、能力、期限、总次数和并发额度；无绑定的当前平台角色从主库加锁读取。圈级绑定角色不等于平台权限，自动化不能直授；管理员不能给自己或自己的圈子自授，应由另一平台管理员操作。
- 来源明确区分 `CIRCLE_APPLICATION` 和 `PLATFORM_DIRECT`。直授直接成为 `APPROVED/enabled=true`，不要求先申请、满足人数/运营时长/内容量/活跃度/圈子身份等级、重新申请冷却或圈子申请额度。不修改这些普通规则，也不伪造“圈子已达标”。`circle.capability-policy.v1` 是普通申请规则，不能被当作平台直授的全局开关。
- LIVE/SHORT_VIDEO 可直授当前圈主或所选圈内成员；AUDIO_QUESTION/VIDEO_QUESTION 必须指定个人，不能批量给整圈所有人开通。个人直授不依赖圈级授权，单独消耗其明确额度；不连带开放其他能力/其他成员，不要求把 MEMBER 强行改为 GUEST/圈主。
- 保留账号/圈子正常、主体真实存在、有效成员关系和授权范围边界；不修改用户身份、角色、支付价格、钱包或合规状态。被移出圈子、圈子关闭、账号停用、换圈主、暂停/撤销/到期仍不能发起新业务；既有履约与可信收尾保留。实际业务接线时仍需保留供应商可用性、内容审核、支付及全局风险关闭约束，不能用直授绕过。
- 直授要求明确有限额度和期限，不套用圈子申请上限；32 位正整数和最长 3650 天只是技术边界，不是正式套餐或默认值。暂停后恢复不替本人接单，恢复为未启用；本人可停用/启用。
- 对当前最新记录核对 `expectedLatestId/expectedLatestRevision`；首次须 revision=0 且无最新ID。替换旧授权时，同事务将旧活动记录撤销、保留审计、创建新直授及其审计。重复点击不能隐式刷新次数；旧预留也不能借新直授版本激活。
- 新增后继迁移 `manual_add_circle_platform_direct_grant`：只增来源列并允许额度的圈级关联为空，个人关联及全部限制外键保留；历史记录默认仍为普通申请，不自动批准。必须按工作流→额度账本→直授三项依赖顺序执行。全部仅在新建 localhost 合成库验证，未授权线上执行。
- 后台定向授权按钮、用户能力/申请页、名师详情入口及实际直播/视频/通话/媒体资源适配尚未接入。接线必须以同一服务端决策显示入口，不能继续把现有 OWNER/GUEST 条件当成平台直授的硬限制；在此之前不能宣称名师已能实际使用直授功能。

## 3. 持久层必须满足的条件（部分已实现，按项验收）

1. 独立存储申请、授权、变更审计和配额预留记录；不把它们塞进 ConfigSystem，不覆盖旧 CirclePublishGrant，不把价格字段转换成获批记录。
2. 对 `(circleId, capability, subject)` 组合建立并发保护；圈级 subject 和服务者 subject 需要不含 NULL 唯一性漏洞的规范化标识。申请在事务内重新读最新记录和资格，PENDING/有效 APPROVED/SUSPENDED 不得并发重复创建。
3. 审核事务在主库读取并锁定策略/主体/申请。使用 expectedRevision 的条件更新；受影响行数必须为 1。状态变更与审计必须同事务提交，不先回“审核成功”再异步写库。
4. 资格结果绑定 circleId、ownerId、capability 和 policyRevision，不能拿其他圈子或能力的达标结果审批。事实变化较快，接入时必须重新采集，不能信任客户端提交的 progress、eligible、roles、executor。
5. 同一操作的幂等键必须绑定授权、真实业务对象、额度数量和用途；重试可以返回同一结果，不能替另一业务对象重复消费。
6. 真正创建直播、短视频、问答或分配媒体资源之前，对圈级和服务者额度在同一事务原子检查并预留。失败释放、超时回收、完成结算都要幂等，撤权后阻止新预留但保留已有记录。
7. maxUnits 当前表示授权生命周期内的业务次数，maxConcurrent 表示同时占用数；直播时长、录制/转码/存储/带宽、音视频时长成本还需独立资源计量和预算，不以业务次数冒充已实现全部成本控制。不得未经业务确认自动按日/月重置额度。
8. 新控制器与服务入口同时执行权限与人工红线校验，审计 actor 来自已认证会话；不能接收客户端任意指定 HUMAN 来绕过自动化红线。
9. 新迁移应为可审查的增量建表/约束，不自动给历史账号开权限；更新全量基线并在隔离数据库验证。未取得精确授权不得执行线上迁移。

第五批已完成申请/授权和审计两表；圈内串行事务锁、已有配置/主体行锁、取锁后重新取时及采集资格、版本/状态 CAS、变更和审计同事务、无绑定平台角色实时读取、HTTP 参数与双层红线守卫。审核记录保留版本，不提供删除接口。新迁移为 `manual_add_circle_capability_workflow`，只新增结构，无历史数据回填或默认批准。

第六批收紧了缺行锁边界：后续授权只能使用取锁查询实际返回的配置、账号、成员、角色 ID；空查询不会把中途插入的新记录视为已锁定。已有记录的行锁保护与新记录保守拒绝分别处理，不能将 advisory lock 描述为所有后台写路径都会遵循的全局锁。

第七批已实现配额账本和同事务更新代码，当前运行时授权方法仍只是校验钩子；只有内部 `reserveInTransaction` 会写额度记录，现有业务未调用它。待验范围包括完整申请/审批涉及的角色/配置/成员新增撤销交错、与线上同版本数据库的兼容性、直播/视频/问答/媒体资源创建接线及前后台状态展示。纯函数、模拟事务、局部 PostgreSQL 测试的证据分开记录，不能相互替代。

### 3.1 额度决策内核（第六批，本地未接线）

`circle-capability-quota.policy.ts` 是纯决策函数，没有数据库、订单、SDK 或网络调用。此批只增加可测试契约，不增加第三张表、不改变现有迁移，也不注册新入口。

| 状态 | 累计次数占用 | 并发占用 | 允许的后续动作 |
| --- | --- | --- | --- |
| HELD（未超时） | 暂占 1 | 暂占 1 | 重新核权后 ACTIVATE；未开始失败 RELEASE；到期 EXPIRE |
| HELD（已超时） | 0 | 0 | 只能收尾，不能恢复使用原请求 |
| ACTIVE | 计入 1 | 占用 1 | 收到可信业务终态后 COMPLETE，不因占位 TTL 释放 |
| COMPLETED | 保留 1 | 0 | 原操作幂等回读，不返还累计次数 |
| RELEASED / EXPIRED | 0 | 0 | 原操作幂等回读，不能再次激活 |

圈级与服务者额度同时检查，但目前只是对调用方提供的事务快照做计算，**不是原子记账已完成**。每次业务固定 1 单位；预留期限由业务适配层明确传入，技术边界为 1–900 秒，且不能超过任一授权到期时间；不是正式业务资源套餐或自动月度重置。

以上为第六批纯内核边界；第七批内部服务已从事务仓储取得这些快照，不接受客户端计数或回执。真实业务适配仍未接线。

业务绑定必须包含圈子、能力、真实操作者、服务者（问答必需）、业务类型、一次业务实例 ID、请求幂等键、次数和期限。直播应绑定一次具体开播会话，不以可重复使用的直播间 ID 冒充唯一会话。两份索引回读必须指向同一完整快照；同请求只返回 NONE，不产生第二次 SDK 或订单动作。不同业务/主体/期限不能复用请求键；过期预留不能靠换 key 偷占第二次。

ACTIVATE 重新检查当前账号、主体、策略、两份授权及其修订；暂停、撤权、到期、换圈主、策略变化均阻止开始新业务。RELEASE / EXPIRE / COMPLETE 为内部可信适配器的收尾操作，不是客户端可调用的绕权入口；既有履约不能因为撤权而被阻断。已进入 ACTIVE 的不明失败保持占用，交由可靠对账确认结束，不能在不清楚供应商状态时自动退回额度。

### 3.2 接入账本与外部资源前必须满足

- 资格、最新授权、业务所有权、幂等索引、累计/并发计数必须来自同一主库事务；客户端不能提交 usage、授权快照或 priorReceipt。
- 同圈串行保护要覆盖预留、激活、收尾和授权变更；同业务唯一约束、请求键唯一约束、操作回执唯一约束及 revision CAS 必须落在数据库。
- 两份额度和业务记录/审计必须同事务提交或全部回滚。不能先调用 SDK 再记 ACTIVE；外部调用需有持久化待执行记录或同等可靠恢复机制，事务外发送且使用供应商幂等标识。
- 重放结果 NONE 仅返回既有状态，绝不用于重新调度外发。外部响应丢失不能被当作“业务未开始”直接 RELEASE；先对账或人工确认。确认最终结束后 COMPLETE 保留累计消费，不擅自补退款/返额度规则。
- 真实双连接必须验证：同业务双请求、同圈最后一次额度竞争、不同服务者共用圈级并发、撤权与激活交错、失败回滚、重复收尾、过期与激活竞争、未知供应商状态。纯函数和模拟事务结果不得标为上述竞争已验真。

### 3.3 第七批内部额度账本

- `CircleCapabilityQuota` 保存不可变业务绑定、圈级/个人授权版本和生命周期。总次数直接从有效账本聚合，ACTIVE/COMPLETED 均保留累计消费，未超时 HELD 同时暂占总量和并发，避免另维护可漂移的独立计数器。
- `CircleCapabilityQuotaReceipt` 保存初次预留及每次操作的前后白名单快照、来源、操作者或内部业务证据引用。同业务实例、请求键、操作键和同账本版本分别有唯一约束；外键 RESTRICT，不能随圈子或授权删除而抹去账本。
- 内部预留/激活/收尾只接受调用方的 `Prisma.TransactionClient`，不自行建立或提交第二个事务。同圈锁键与授权仓储一致；写回执失败或调用方后续业务失败应使整个事务回滚。
- 只有可信业务适配器可发起收尾，且必须先在同事务验证真实业务状态及证据；`evidenceRef` 不是用户传一个字符串即可证明业务结束。当前没有公开收尾 HTTP API，也没有媒体回调/订单/可靠任务适配器。
- 新增迁移 `manual_add_circle_capability_quota_ledger` 依赖 `manual_add_circle_capability_workflow`；仅新增 2 枚举、2 表、8 索引、4 限制外键，不回填、启用或删除数据。未来线上执行需要覆盖这两个精确迁移的新授权，不能套用历史“仅兴趣引导迁移”的授权。
