# 资金与分账架构 · 设计文档（2026-07-14）

> **分工**：董事长负责微信 / 支付宝 / 汇付三条通道的资质与产品开通；本文负责资金架构设计，并对「无二清、无业务风险」负责。
>
> **v2 — 依据董事长 2026-07-14 拍板的渠道能力现状重写。**

---

## 零、渠道能力现状（董事长确认，架构的地基）

| 渠道 | 我们的身份 | 已具备能力 | 关键约束 |
|---|---|---|---|
| **汇付** | **服务商** | ✅ 自己分账 ✅ **给下级客户开户（进件）** | **无 30% 上限** → 高比例分账唯一出路 |
| **微信** | **服务商（技术服务通道，非电商收付通）** | ✅ 分账 ✅ 商家转账到零钱 | 🔴 **分账上限 30%**（硬顶） |
| **支付宝** | 未开 | 有优势随时可开 | 见第五章——**建议开，它能解一个死结** |

**这张表推翻了 v1 的核心假设。** 原以为「子商户进件」要从零谈资质，实际上**汇付服务商身份已经给了我们开户能力**——缺的只是系统里的字段和调用流程。

**架构因此收敛成一句话：**

> **汇付做主通道（进件 + 收单 + 分账），微信做平台自营收款和代付出款。**

---

## 一、一条铁律

> **二清的判定核心不是「钱有没有经过平台账户」，而是「资金的分发指令由谁执行」。**
>
> - 平台把钱从自己账户转给商家/驿站/圈主 → **二清**（无证清算，违法）。
> - 平台只下达分账/代付指令，由**持牌机构**（汇付、微信、支付宝）执行分发 → **合规**。

**推论：平台永远不做「收了再转」这个动作。**

---

## 二、责任跟着钱走

平台一旦成为收款主体，就是法律意义上的**经营者**——商品质量、服务纠纷、内容违规、退款、开票责任全在平台。

**设计原则：能自己收款的，就让他自己收款。**
**能否自己收款的唯一硬条件：有没有营业执照。**（个体工商户即可；个人办不下商户号）

### 3.1 驿站：驿站收款 → 分账 30% 给平台

```
学员报名
  └─ 汇付收单（用户仍是微信扫码付款，体验无差异）
      └─ 钱进【驿站的汇付子账户】
          └─ 汇付分账
              ├─ 驿站 70%
              └─ 平台 30%
```

**⚠️ 澄清一个容易混淆的点**：「用微信支付」和「走汇付」**不冲突，是同一笔交易的两个层面**——
- **用户体验层**：用户扫码、用微信钱包付款（不变）
- **资金通道层**：收单机构是汇付，资金进汇付的驿站子账户，由汇付分账

**为什么默认汇付**：微信分账**硬顶 30%**，而驿站抽成正好 30%——**卡死在上限边缘，没有任何余量**。
👉 **而且微信的 30% 上限还有个隐藏坑**：分账基数是「订单金额 − 手续费」的可分账金额，不是订单原始金额。**平台想拿满 30%，实际会超限报错。**
👉 **若走微信通道，驿站抽成必须降到 28% 或更低留余量。汇付无此问题。**

**责任外移到位**：收款主体是驿站 → 课程质量、场地安全、服务纠纷全在驿站。✅ 这正是「松散赋能、不做强加盟」想要的。

**老师结算**：✅ **代码已天然符合** —— `StationTeacher` 表**没有任何分成字段**，驿站给老师怎么结算，平台系统完全不记、不碰。**必须保持这样**：一旦平台系统里出现「老师应得多少」的记账，就等于平台在组织资金分配，责任被吸回来。

> 🟠 **发现的死字段**：`InstituteCourse.teacherShare`（研究院线下课老师分成比例）——**全库零使用点，从没算过钱**。研究院既然独立公司运营，这个字段应**标记废弃**，防止后人误用把责任吸回平台。

### 3.2 圈子：双轨制（董事长拍板）——这个设计很漂亮，值得说透

| | 无执照圈主 | 有执照圈主 |
|---|---|---|
| 收款主体 | **平台** | **圈主企业** |
| 平台分成 | **50%** | **20%** |
| 圈主到手 | 50%（税前） | 80% |
| 通道 | 平台商户号收款 → 代付给个人 | 汇付进件 → 分账 20% 给平台 |
| 平台责任 | **高**（收款主体 = 经营者，内容责任在平台） | 低 |

**这个设计的精妙之处：50% vs 20% 的费率差，就是一台自动的合规驱动引擎。**

- 圈主收入越大，那 30% 的差价越肉疼 → **他自己会去办执照**
- 平台不需要强制，也不需要谈判 —— **定价即治理**
- 平台背高风险时收高价（50%），风险外移后主动降价（20%）—— **定价与风险严格对称，商业上完全站得住**

**而且它和一条外部约束天然咬合**：灵活用工平台通常有**单人年度限额**（一般 10–12 万/年，超过就要求转为经营所得、办执照）。所以圈主做大 → **限额自动触顶 → 被迫办执照 → 自动切到 20%**。制度和渠道规则指向同一个方向。

**🔴 但必须补一道保险**：如果头部圈主收入做大了**还是不办执照**，平台就长期背着高额资金 + 内容风险。
👉 **建议设硬阈值**：圈主年累计收入超过阈值（建议 10 万，对齐灵活用工限额）→ **强制要求办执照，否则暂停收款/暂停提现**。这不是限制圈主，是保护平台。

**⚠️ 无执照圈主那 50% 的支出，是平台的成本，需要发票才能税前列支** —— 见第四章。

**技术要求**：`Circle` 表现在**一个资质/分成/商户号字段都没有**（`CircleRevenueSplit` 是给「嘉宾」分成的，不是圈主）。双轨制要从零建：
- `settlementMode`: `PLATFORM_COLLECT`（无照 50%）/ `SELF_COLLECT`（有照 20%）
- `huifuId` / `businessLicense` / `payeeOpenid`
- **模式切换后，历史订单按旧模式结算**（不追溯）

### 3.3 商家：商家自收款 + 分账

**⚠️ 纠正你之前说的「定期开票结算」**：如果是「平台代收货款 → 定期结算给商家」——**那就是二清**。

**正确做法**：钱直接进商家的汇付子账户，平台通过分账收佣金。开票关系随之自然厘清：
- **商家给用户开票**（商品发票）
- **平台给商家开票**（技术服务费发票）

**你不需要「结算给商家」，因为钱压根没到过你手上。**

🔴 **`Merchant.businessLicense` 现在是「可选」，必须改必填** —— 无执照 = 无法进件 = 无法自收款 = 只能平台代收 = 二清。执照不是形式要求，是合规架构的**物理前提**。

### 3.4 研究院：独立公司

独立商户号，独立收款。平台系统只做订单与履约，**不碰它的钱**。与平台之间是关联交易（需真实服务合同 + 公允定价）。

### 3.5 运营商 / 分站：灵活用工代付

**这是纯支出，不是分账**（见第五章为什么）。加盟费（999 / 4999）**不产生任何分佣**——✅ 现在代码就是这样，**必须保持**（见第六章传销红线）。

## 四、灵活用工与个税（你没问，但风险很大）

个人从平台取得的佣金/分成属于**劳务报酬**，**平台是法定扣缴义务人**。不代扣代缴 = 税务违法，且金额累积，规模上来后追溯风险巨大。

**涉及的人群**：无执照圈主（50%）、运营商、分站站长、达人、创作者、普通用户提现。

**现状问题**：
- 有 `finance.tax.enabled` / `finance.tax.rate` 配置和 `WithdrawalApplication.taxAmount` 字段
- 🔴 **但站长那套 `Withdrawal` 表没有税费字段** —— 三套提现表口径不一（`Withdrawal` 站长 / `WithdrawalApplication` 用户 / `VideoCreatorWithdrawal` 创作者）

**建议**：接**委托代征 / 灵活用工平台**——由持牌机构向个人付款、代征个税、**向平台开具发票**（平台才能税前列支）。
👉 **优先问汇付有没有「灵工」产品** —— 如果有，进件、收单、分账、代付、代征、开票**全在一家**，架构最简。

## 五、分账 ≠ 代付：两种钱，两条路（最关键的区分）

|  | **分账（绑单）** | **代付 / 转账（不绑单）** |
|---|---|---|
| 本质 | 一笔订单的钱按比例分给多方 | 平台把钱付给某个人 |
| 必须绑定 | 具体交易（`transaction_id`） | 无需 |
| 适用 | 驿站 30%、圈主 20%、商家货款 | **运营商/分站佣金、圈主 50%、用户提现** |
| 通道 | 汇付分账（无上限）/ 微信分账（≤30%） | 汇付代付 / 微信商家转零钱 / 支付宝转账 |

### 🔴 为什么运营商/分站佣金**不能**用分账

佣金是「某人本月推广了 37 单，月底累计结算 ¥2,400」——**它不对应任何一笔具体订单**，而分账的技术前提就是绑定 `transaction_id`。**所以只能走代付。**

### 💡 支付宝的价值：它能解一个死结（建议开）

**存量断裂**（上批实测发现的）：
- 微信「企业付款到银行卡」**已下线**，只剩「商家转账到零钱」——**只能打零钱、必须要 `openid`**
- 而 `Withdrawal` 表**只存银行卡 / 支付宝账号，没有 openid 字段**
- 👉 **提现口径和渠道能力对不上**

**三条代付通道各司其职，正好补齐**：

| 用户填的收款方式 | 走哪条代付 | 备注 |
|---|---|---|
| **支付宝账号** | **支付宝单笔转账** | ✅ **不需要 openid，直接覆盖存量口径** |
| **银行卡** | **汇付代付** | ✅ 微信/支付宝都打不了银行卡，只有汇付能 |
| 微信零钱 | 微信商家转账 | ⚠️ 需新增 `openid` 字段 |

👉 **结论：支付宝该开——它是解决存量提现口径最省事的一条。**

### 🔑 根因

分账的本质是「把钱分给某个**持牌机构认识的账户**」。而系统里，驿站/商家/圈主在渠道眼里**根本不存在**——没有 `huifuId`、没有 `subMchId`、没有 `openid`。

**这就是所有分账接不通的唯一根因，也是必须先建的地基。**

## 八、实施路线（按「风险外移收益 / 依赖」排序）

### 批次 0 —— 结算引擎转正（**不依赖任何渠道，可立刻开工，建议先做**）

> ⚠️ **修正（2026-07-14 侦察后）**：本节原写「打开 `settlement.ledger_withdrawable.enabled` 即可」——**这是错的**。
> 结算引擎不是「建好了等开开关」，而是**一个覆盖率不到一半的半成品影子**。开关是它唯一做完的部分。
> 直接开 = 达人/主播余额归零 + 站长丢掉全部历史收益。详见下方缺口表。

**转正后要解决的两件事（目标不变）：**

**① 堵住真实资损漏洞（R5）**
> 站长赚 500 → 提现 500 → **钱已打出** → 用户退款 → 冲正 `totalEarning` → 余额 **−500** → 站长不干了 → **平台净损失**

转正后余额读 `LedgerEntry` 净结算额，且 `SettlementRule.bufferDays`（默认 **7 天**）内的分账是 `PENDING`、**不计入可提现** → 钱要过了退款期才能提。**就是行业标准的 T+7 缓冲。**

**② 圈主/驿站主的钱现在根本取不出来**
他们的渠道佣金只写进 `LedgerEntry`，而提现读 `UserEarning` —— 转正就是那座桥。**不转正，圈子 50%/20% 分成做出来也是死的。**

#### 转正前必须补的缺口（侦察实测）

| 缺口 | 证据 | 状态 |
|---|---|---|
| 达人/主播（答题·围观·连麦·礼物·咨询）**只写 `UserEarning`，零 `settle()` 调用** | `revenue.service.ts:58` 是全库唯一 `UserEarning` 写入点；`settle()` 全库仅 `commission.service:271` 一个调用方 | ✅ **本批已补**（`RevenueService.settleLedger` + 5 个业务调用点） |
| **`MEMBER_PURCHASE` 规则 `enabled=false`** → 会员佣金旧口径真发、引擎口径不落账 | `settle()` 遇未启用规则**静默跳过**（`settlement.service.ts:70-73`） | ✅ **本批已修**（启用 + 补 `OPERATOR` 管理奖角色） |
| **`PEEK`/`AUDIO_CALL` 规则比例是过期旧值**（0.7 vs 实际 0.3/0.5） | 靠 `enabled=false` 才没生效；一旦启用就多发钱 | ✅ **本批已修**（改对再启用，旧口径行为零变化） |
| **存量数据不在总账里** | `LedgerEntry` 从影子双写上线才开始记，`Station.totalEarning`/`UserEarning` 是历史累计 | 🔴 **待回填**（转正的最后一道坎） |
| 缺余额级对账工具 | 既有每日 2AM 对账是**逐订单**的，且只覆盖双写订单（其注释自道），结构上查不出存量缺口 | ✅ **本批已建**（`GET admin/settlement/reconcile-balances`，只读，生产可跑） |

#### 转正放行条件（唯一）

`GET admin/settlement/reconcile-balances` 返回 **`canSwitch: true`** —— 即全部受益主体的
`gap = 旧口径余额 − 总账全量净额` 都在 1 分容差内。

**这个端点就是红绿灯。gap 不为 0 就说明：开关一开，这些人的钱会凭空增减。**

> 🟠 本地库实测已暴露一个隐患：`Station.totalEarning` 合计 **22239.4**，而其明细表 `StationEarning` 合计只有 **1012.7** ——
> **旧口径自身就不自洽**（`totalEarning` 是累加字段，被直接写过，没有对应明细）。
> 本地大概率是脏测试数据，但**生产必须用上述端点单独核一遍**：若生产也这样，回填就没有可信的数据源，
> 得先决定以哪个为准（明细可追溯但可能不全；`totalEarning` 是提现实际读的值但无凭据）。

### 批次 1 —— 汇付进件 + 主体身份体系（地基）
1. 汇付**开户/进件接口**（服务商能力，代码从零建）
2. `Merchant` / `StationOffline` / `Circle` 增加 `huifuId` + 资质字段 + 进件状态机
3. `Merchant.businessLicense` 可选 → **必填**
4. `Circle.settlementMode` 双轨字段 + 50%/20% 费率

### 批次 2 —— 驿站收款闭环（**第一个真正外移风险的**）
1. `StationOrder` 补支付字段（现在压根没有）
2. 下单带 **`delay_acct_flag`**（分账硬前提）
3. 支付成功回调 → **自动触发汇付分账** 70/30

### 批次 3 —— 代付出款（钱能自动出去）
1. **支付宝转账**（覆盖存量支付宝口径，不需 openid）
2. **汇付代付**（银行卡——微信/支付宝都打不了）
3. 微信商家转账（需先补 `openid` 字段）
4. 接入**代扣个税 / 委托代征**
5. **P0 人工打款通道保留**作为兜底降级

### 批次 4 —— 商家 + 圈子切换、存量二清收口
1. 商家进件 → 商家自收款 + 分账（**货款金额最大，二清风险最高**）
2. 有照圈主切 `SELF_COLLECT`
3. 商家保证金接真实支付
4. 修复/或废弃微信分账死代码

### 存量二清止血（切换完成前）
现有三处（商家结算 / 驿站抽成 / 圈子分成）仍是「平台代收 + 人工转账」：
- 每笔必须有**打款流水号**（`payoutRef` 已实现，可复用）
- 每笔必须有**真实服务合同/结算单**作为资金往来凭证
- **控制规模** —— 二清风险与资金沉淀规模正相关
