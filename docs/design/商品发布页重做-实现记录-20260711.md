## 三、字段落库映射（关键设计）

Product 表没有独立的封面/轮播/详情图字段，全部映射进现有两个字段：

| 前端概念 | 落库位置 | 说明 |
| --- | --- | --- |
| 商品封面 | `Product.images[0]` | 列表/商城卡片展示 |
| 轮播图 | `Product.images[1..]` | C 端商品页顶部轮播本来就吃整个 images 数组 |
| 详情图 | `Product.detail` 开头的连续 `<img>` 序列 | `<img src style="width:100%">` 依序拼接，C 端 rich-text 渲染不变 |
| 图文补充说明 | `Product.detail` 中图片序列之后的 HTML | wangEditor 产出 |

**编辑回填的反解析**：`parseDetail()` 用 DOMParser 从 detail 开头收集连续的顶级 `<img>`（含 wangEditor 的 `<p><img></p>` 包裹形态）作为详情图，遇到第一个非图片内容即停，剩余 HTML 进补充说明。**旧数据兼容**：纯富文本详情 → 详情图为空、整体进补充说明（折叠块自动展开），保存后自然迁移到新结构。

## 四、价格/SKU 语义结论（侦察结果）

| 字段 | 语义 |
| --- | --- |
| `Product.price` | 商品级售价：单规格=成交价；多规格=列表展示价（应=最低 SKU 价） |
| `ProductSku.price` | 规格成交价：下单传 skuId 时以 SKU 价计价（shop-order.service 确认） |
| `ProductSku.specs` | Json `{规格名: 规格值}` |

- **后端没有 price=min(sku.price) 自动同步逻辑**（merchant.service create/update 完全不碰 skus）→ 按任务要求在**提交侧计算**：多规格时 `price=min(sku.price)`、`stock=sum(sku.stock)`。
- **SKU 端点**：merchant-backend 无 SKU 端点；复用 `POST /shop/products/:id/skus` + `DELETE /shop/skus/:skuId`（owner 校验 `product.userId===req.user.id`）。无更新端点 → 保存时 diff：没动的行不碰（保留原 SKU id，不影响历史订单引用），改过的行=删旧+重建，删掉的行=删，新行=增。

## 五、已知边界（如实记录）

1. **原价划线价没做**：`MerchantProductDto` 不收 `originalPrice`（shop 的 `UpdateProductDto` 也不收），main.ts `whitelist:true` 会静默剥离 → 做了输入框=假保存。需产品要划线价时，给 MerchantProductDto 加一个 `originalPrice` 可选字段即可（一行 DTO+service 透传），本轮铁律不动后端故未做。
2. **店铺操作员（MerchantMember 非 owner）改 SKU 会 403**：merchant-backend 端点经 `shopUserId()` 归一到 owner，但 `/shop/*` SKU 端点用 `req.user.id` 直比 `product.userId`。owner 本人不受影响；操作员保存商品主体成功、规格同步会失败（前端已提示"N 条规格同步失败"）。彻底解法=给 merchant-backend 加 SKU 端点（不动本轮）。
3. **多维规格降一维**：现库 specs 支持多键 `{颜色:红,尺寸:M}`；编辑器按"规格名+规格值"单维展示（多键用 " / " 拼接显示），该行被修改保存后重建为单键。现网商家 SKU 均为单维场景，影响极小。
4. **编辑回填走 `GET /shop/products/:id`**（公开详情端点，含 skus、各状态商品均可取）；merchant-backend 自己的详情端点不含 skus。
5. 审核流不变：普通商家新建=PENDING、官方旗舰店免审 ON_SALE（后端原逻辑）；编辑不改 status。
