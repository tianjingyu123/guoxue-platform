# 后台管理端目录整合方案

> 2026-07-08 · 承接《发布架构统一-官方身份与创作工作台-20260708》· 董事长已拍板采纳"统一官方身份"方向 · 状态：方案待逐项拍板后分块执行（本文不动代码）

## 一、背景与目标

后台 admin 长期"什么都能在后台编辑发布"，与后来长出的**场景化实体**（圈子文章 Article / 古籍库 ClassicBook / 诗词库 / 商家商品 Merchant Product）形成**四套并存、双入口**的重叠，语义混乱、搜索推荐重复、多处维护多处 bug。

董事长拍板：**admin 从"发布/创作中心"收敛为"审核 + 运营管理 + AI 兜底"，创作发布权交还给场景化的前端(C 端)/商家端/讲师工作室；官方内容一律用官方身份走真实流程。**

**四条收敛原则**：
1. 真人创作发布走前端/商家端/讲师工作室；后台发布接口只留给 **AI 数字员工 API 自动发种子内容**（无 UI 或极简兜底）。
2. 官方身份复用真实容器：官方内容→「热卜官方」圈(多管理员)；官方商品→「官方旗舰店」Merchant。
3. 一种内容/商品只有**一套实体、一个发布入口、一套校验**；消除双入口。
4. admin 保留"看得见、管得住"：列表 / 审核 / 上下架 / 推荐 / 数据订正 / 批量运营——**这些是管理，不是创作编辑器**。

### 2.2 冲突清单（本方案要解决的核心）

- **C1 文章双入口**：内容管理选 type=ARTICLE(写 Content) ↔ 圈子文章 Article 表。两张表都叫"文章"。
- **C2 古籍双入口**：内容管理选 type=CLASSIC(写 Content) ↔ 古籍管理 ClassicBook（含章节/注疏，才是真古籍库）。
- **C3 诗词已处置**：诗词板块已在瘦身批次剥离（pkg-poetry / admin poetry views 均删除，董事长定：**不再单独建诗词板块，诗词并入古籍**）。Content.type=POEM 与 `/contents/poem/*` 端点因此**成为死代码**（无 C 端消费方）。
- **C4 商品双入口**：admin 商品管理 `POST /shop/products`(打 isPlatform/PLATFORM/直接上架) ↔ 商家端 `POST /merchant-backend/products`(supplierType=MERCHANT/待审)。**同一张 Product 表两套创建逻辑。**

### 2.3 关键约束：Content 表 C 端读取现状（废弃前必读）

`content.controller` 除 admin 增删改外，暴露了若干 C 端公开读接口：
- `GET /contents/poem/random|daily|:id/appreciation`（诗词）——**消费方 pkg-poetry 已删除，现为死端点**，可随 Content 一并退休。
- `GET /contents/featured`、`GET /contents`、`GET /contents/:id`——**仍需逐一排查 C 端是否有活消费方**（首页精选/内容详情等），有则先迁移、后停写入。

→ 诗词读取已无牵挂；剩 featured/list/:id 三个通用读需在块 E 废弃前逐一确认。数据表按项目铁律**只增不删、保留**。

## 三、目标结构（分类决策）

| 类别 | 创作发布走哪 | admin 保留 | 处置 |
|---|---|---|---|
| **文章**(轻) | C 端「圈子文章」编辑器（官方内容→热卜官方圈·多管理员） | 文章管理：列表/审核/推荐/下架 | 砍 admin 文章**创作编辑器**；砍 Content.type=ARTICLE 入口 |
| **短视频/帖子**(轻) | C 端已上线（circleId 兜底官方圈） | 列表/审核 | 无编辑器可砍，维持 |

| **古籍（含诗词）** | 保留专业库独立录入（章节/注疏/向量化；**诗词并入古籍**，如归"集"部） | 古籍管理（现状保留·作为诗词唯一归属） | 砍 Content.type=CLASSIC 重复入口 |
| **诗词** | — | — | 板块已剥离·**并入古籍**·不再单独存在；Content.type=POEM 及 `/contents/poem/*` 死端点随 Content 退休 |
| **课程** | 讲师创作工作室（桌面·复用 admin 栈·讲师自己账号·设计文档 Phase 3） | 教学管理（学员/评价/作业） | 课程编辑器**升级**为工作室，非砍 |

**Content 表归宿**：三类 type 入口全部砍掉后，Content 退化为仅历史数据。诗词读取已无消费方；featured/list/:id 确认迁移后，Content 表**保留但停止新写入**（僵尸化，数据不删）；后续无任何读取再评估归档。

## 六、风险与红线

- **数据表只增不删**（项目铁律）：Content/Product 等表一律保留，只改入口与写入逻辑。
- **C 端读取不断链**：任何废弃前，先确认并迁移读取方（诗词是已知点，featured/list/:id 需逐一排查）。
- **搜索/推荐去重**：双入口合并后，检查搜索/推荐是否还从旧表取数导致重复或漏数。
- **灰度可回滚**：编辑器下线用开关/隐藏而非物理删，观察一轮再清理。
- **官方身份账号安全**：官方圈 ADMIN、官方 Merchant 操作员名单需可控可审计。
