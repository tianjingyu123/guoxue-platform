# 热卜直播全域体验标准与改造基线 V1.0

> 状态：已冻结，作为直播板块产品、设计、研发、测试和运营的共同验收基线。
> 适用端：Android、iOS、HarmonyOS、H5、微信小程序、管理后台、主播控制台、OBS。
> 上位规范：`全平台体验标准-头部对标-V1.0-20260717.md`。发生冲突时，以安全、合规、数据事实和上位规范为先。

## 1. 目标定义

“主流平台级”不是复制抖音或小红书的颜色和按钮，而是同时满足以下条件：

1. **即时可看**：从点击直播卡到首帧期间不出现白屏，不要求再次点击播放；弱网、切后台和播放失败均有明确恢复路径。
2. **场景闭环**：观众、主播、副播、场控、商家和 OBS 导播在各自界面完成任务，不依赖隐藏入口或跨角色猜测。
3. **状态可信**：在线、累计观看、峰值、互动、礼物、订单、推流和麦位数据都有唯一口径，不以轮询次数冒充用户行为。
4. **互动自然**：评论、点赞、关注、分享、举报、连麦、礼物和商品入口可发现、可撤销、可恢复，且不遮挡核心画面。
5. **安全可控**：开播资质、隐私权限、未成年人、内容审核、评论治理、消费保护、推流密钥和异常下播有完整防线。
6. **持续可运营**：预告、开播、直播中、断流、结束、回放、复盘和二次分发形成完整生命周期。
7. **可量化验收**：每一项能力都有状态、指标、自动化门禁或真机证据，禁止用静态效果图代替真实链路。

这里列出的连麦、打赏、带货等不是优化范围的上限，而只是场景样本。评审对象是从发现直播到回放复盘的完整系统；任何角色、状态、终端、网络、权限、安全或运营链路缺失，都不能以“主流程能跑”判定达到主流平台级。

### 1.1 核心用户与唯一任务

| 角色 | 核心任务 | 成功标准 |
|---|---|---|
| 观众 | 立即理解“谁在讲、讲什么、为什么值得停留”，并在不中断观看的前提下互动或购买 | 进入即播；3 秒内理解主题；常用操作单手可达 |
| 主播 | 始终看到自己的真实直播效果、公屏和关键状态，低干扰完成主持 | 画面为主、控制为辅；高频操作一步完成；危险操作二次确认 |
| 副播/嘉宾 | 清楚知道申请、候场、设备检查、连入、静音和退出状态 | 状态无歧义；音视频权限先确认后开通；退出幂等 |
| 场控/运营 | 不遮挡主播画面地处理评论、麦位、商品、风险和流程 | 权限分级；操作可审计；结果实时回显 |
| 商家 | 在正确时机讲解商品、发优惠并核对转化 | 商品事实来自后端；库存/价格/订单不可伪造 |
| OBS 导播 | 安全取得推流参数、预检信号、稳定推流并定位异常 | 密钥可轮换；推断流可观测；异常有明确诊断和恢复建议 |

### 1.2 十二维度评分门禁

| 维度 | 必须回答的问题 | 上线底线 |
|---|---|---|
| 产品完整性 | 每个角色从进入到退出是否闭环，是否存在死路、假按钮或隐藏必经步骤 | P0 场景 100% 闭环 |
| 视觉还原 | 是否延续既有热卜设计语言，层级、留白、动效和信息密度是否统一 | 关键页设计复核无 P0/P1 偏差 |
| 交互效率 | 高频动作是否单手一步完成，危险动作是否可确认和撤销 | 高频路径不超过 1 层面板 |
| 音视频真实性 | 主播、嘉宾、普通 CDN 观众是否看到同一多人舞台并听到一致混音 | 双机连麦 + 第三观众证据通过 |
| 弱网与恢复 | 首帧、缓冲、切网、前后台、来电、权限撤销和崩溃恢复是否有事实状态 | 无白屏、无永久卡死、可退出 |
| 社区与治理 | 评论、举报、禁言、场控、敏感内容、未成年人和申诉是否闭环 | 权限最小化且操作可审计 |
| 商业化可信度 | 礼物、余额、限额、商品、库存、优惠、订单、退款和归因是否基于最终态 | 无重复扣费、无静态假数 |
| OBS/专业生产 | 移动直播与 OBS 是否共享房间、互动、治理、监播、结束与回放事实 | 推断流和异常回调实测通过 |
| 数据与运营 | 在线、累计、峰值、停留、互动、礼物、GMV 和质量口径是否唯一 | 前后台口径可对账 |
| 性能与成本 | 首帧、卡顿、耗电、流量、混流转码和 CDN 成本是否可监测和告警 | 指标达标且费用有预算告警 |
| 可访问与适配 | 刘海/挖孔/手势区、横竖屏、字体缩放、读屏、减少动态是否可用 | 关键操作不重叠且不只靠颜色 |
| 发布与可观测 | 客户端、服务端、云配置、回调和证据是否绑定同一 releaseId | 可灰度、可回滚、可定位 |

评分规则：每维 0–5 分；任何 P0 未通过即阻断，不允许总分抵消。进入公开运营前十二维均不得低于 4 分，音视频真实性、内容安全、消费安全、发布可观测必须为 5 分。

## 2. 研究依据与取舍

- TikTok 官方把多嘉宾拆成观众申请、主播邀请、音频/视频模式、权限范围，以及 Panel/Grid/Fixed 布局；热卜采用同等级状态完整性，不复制其视觉皮肤。
  https://support.tiktok.com/lo/live-gifts-wallet/tiktok-live/tiktok-live-multi-guest
- TikTok LIVE 官方能力域同时包含互动、礼物、多嘉宾、审核、活动和回放；证明成熟直播不是单一播放器。
  https://support.tiktok.com/en/live-gifts-wallet/tiktok-live/what-is-tiktok-live
- YouTube 官方直播治理包含慢速模式、关注/成员限制、两级管理员、敏感词、待审消息、超时和隐藏用户；热卜需达到同类治理闭环。
  https://support.google.com/youtube/answer/9826490
- DCloud 官方明确 App nvue 的纵向 `swiper` 可内嵌视频实现短视频/直播垂直切换；复杂列表只保留前、当前、后三屏，避免无限堆积。
  https://uniapp.dcloud.net.cn/component/swiper.html
- 腾讯云官方提供推断流、异常、录制、截图、审核和监播回调；OBS 不能只展示地址，还必须接入状态与异常闭环。
  https://cloud.tencent.com/document/product/267/32744
- 腾讯云当前 `StartPublishCdnStream` 明确要求多人混流开启转码、保存 `TaskId` 供更新/停止，并使用独立 CDN 输出；普通观众看到多人舞台必须以真实合流播放证据验收。
  https://cloud.tencent.com/document/api/647/81479
  https://cloud.tencent.com/document/api/647/81477
- 腾讯云 TRTC 的房间、媒体事件、连麦席位、混流转推和 OBS 接入共同构成真实媒体状态；业务“已同意连麦”不能替代嘉宾真正进房、发布和合流成功。
  https://cloud.tencent.com/document/product/647/51586
- 抖音直播运营体系覆盖实时数据、观众经营、回放/高光、违规与流量复盘；主播端不能只剩开关摄像头和结束按钮。
  https://liveservice.douyin.com/
- 小红书电商直播把内容、直播和店铺作为连续交易场景；商品价格、库存、优惠、订单和退款必须以服务端最终态为准，视觉浮层不能伪造交易完成。
  https://ec.xiaohongshu.com/
- 2026 年《直播电商监督管理办法》及配套问答要求规则直接明示、首次打赏提供单次/日累计限额设置、默认开启提醒，并禁止未经同意公开用户消费统计。热卜因此不向普通观众展示消费榜或金额榜；经营统计只向主播本人和授权管理员开放。
  https://www.cac.gov.cn/2026-04/13/c_1777815804150225.htm
  https://www.cac.gov.cn/2026-04/13/c_1777815804146013.htm
- OBS 官方把丢帧视为推流链路/码率问题，并建议自动配置、码率调节和网络诊断；平台应展示可执行诊断而非笼统“网络错误”。
  https://obsproject.com/kb/stream-connection-troubleshooting/

取舍原则：以热卜“国学知识直播、圈子关系、可信内容和克制商业化”为主体；借鉴成熟平台的信息层级、状态机和可靠性，不照搬高刺激、强消费或游戏化界面。

## 3. 视觉与交互语言

### 3.1 设计方向

- **主体**：实时讲解中的人、知识与画面，而不是控制台或装饰。
- **签名元素**：克制的朱印式“直播”标识与古金主题签，不使用霓虹电竞风。
- **画面策略**：视频满屏，信息悬浮；顶部和底部渐变仅保证可读性，不形成厚重黑色工业面板。
- **字体策略**：功能信息使用系统黑体；主题或栏目名可少量使用项目既有宋体语义；数字使用等宽表现。
- **颜色上限**：墨黑 `#181614`、米白 `#F7F3EC`、朱红 `#C41E3A`、古金 `#C9A96E`、松绿 `#4F745B`。直播视频上使用白色正文与透明墨色承载层。
- **密度**：常驻只保留身份、退出、公屏、输入与 4 个最高频动作；其他能力进入可预期的半屏面板。

### 3.2 硬性可用性规则

- 所有点击目标不小于 `88rpx × 88rpx`；图标必须有文字或无障碍标签。
- 顶部使用运行时 `statusBarHeight/safeAreaInsets`，底部使用运行时手势区；直播页禁止硬编码安全区。
- 文字、操作和弹层不得覆盖摄像头挖孔、系统状态栏、横屏刘海或底部手势条。
- 评论最多占屏宽约 72%、高度约 28%；大礼物动画可短时越界，但必须可关闭且不阻断退出/举报。
- 动画尊重“减少动态效果”；点赞和礼物合并渲染，避免高频创建节点。
- 颜色不是唯一状态信号；静音、断流、候场等均同时提供图标和文字。

### 3.3 “墨曜直播舞台”视觉令牌

直播间采用独立的深色沉浸层，但必须能一眼认出属于热卜，而不是通用短视频模板或工程调试界面。

| 令牌 | 色值 | 唯一职责 |
|---|---|---|
| 墨夜 `live-ink` | `#13110F` | 无画面、加载与弹层深色基底 |
| 暖白 `live-paper` | `#F7F2E8` | 视频上的主文字与主要图标 |
| 朱砂 `live-seal` | `#C93A4A` | 直播状态、关注、结束、主要确认；禁止满屏使用 |
| 青黛 `live-link` | `#315C61` | 连麦、设备、可信连接和专业生产状态 |
| 松绿 `live-safe` | `#4F745B` | 在线、健康、已连接、恢复成功 |
| 古金 `live-honor` | `#C9A96E` | 主播身份、主题签和礼物事件；禁止用于普通按钮 |

- 视频上的承载层统一使用“墨玻璃”：`rgba(19,17,15,.54~.82)` 加暖白低透明描边；禁止连续堆叠厚重纯黑卡片。
- 功能信息使用系统黑体；房间主题只允许一处使用项目宋体语义；数据使用等宽数字，避免跳动。
- 圆角按职责分为胶囊 `999rpx`、半屏 `32rpx`、信息卡 `22rpx`；不再让所有组件使用同一圆角。
- 常驻文字不得小于 `22rpx`；直播状态等纯装饰微标可使用 `18–20rpx`，但不能承担唯一信息。
- “品、礼、麦、控”可以作为热卜朱文/白文小印的视觉签名；关闭、分享、翻转、相机、静音等通用动作必须使用可辨认图形和文字，不能只放难懂单字。

### 3.4 核心舞台布局冻结

观众端采用“上身份、下互动、右反馈、画面居中”的单手布局。主播端采用同一舞台语言，但将关注和消费入口替换为健康、场控和结束能力。

```text
观众端                                      主播端
┌ 主播头像/名称/圈子/关注  头像群/人数  × ┐  ┌ 直播/时长  健康/人数  控制台  结束 ┐
│ 直播主题 · 可见范围 · 连麦状态            │  │ 主题 · 分发状态 · 关键经营事实         │
│                                           │  │                                      │
│           主播 / 1v1 / 多人舞台           │  │         本机真实预览 / 多人舞台         │
│                                     心动反馈│  │ 音频席/申请队列                         │
│ 正在讲解商品                              │  │ 商品/礼物事件                            │
│ 公屏、欢迎、礼物、治理事件                 │  │ 公屏、观众问题、礼物、风险事件             │
├ 说点什么…  品  礼  赞  麦  更多 ─────────┤  ├ 回复公屏  翻转  麦克风  画面  更多控制 ┤
└ 手势安全区                                ┘  └ 手势安全区                             ┘
```

- 主体信息不得出现在画面正中央；视频主体的脸和多人席位优先级高于标题、统计和装饰。
- 顶部身份区在窄屏可压缩圈子副标题，但主播名称、关注、在线人数和退出不能被裁掉。
- 公屏默认显示最近 4–5 条；系统、主播、礼物、治理消息具有不同语义标识，但不以高饱和色块刷屏。
- 点赞采用右侧短时上浮反馈，不使用每次点击都弹出的系统 Toast；失败才提示。
- 主播必须在直播画面内直接看到并回复公屏，控制台只承载队列、治理、商品、数据和低频设置。
- 多人视频直接使用画面标签表达身份；右侧席位卡只保留纯音频席，避免同一嘉宾重复占据两层界面。

### 3.5 状态视觉与动效门禁

- 进入：封面保持到首帧，连接状态用朱印呼吸点与明确阶段文案；禁止白屏和空黑屏。
- 互动：点赞合并为 300–700ms 上浮反馈；礼物事件在公屏和轻量横幅各出现一次，不遮挡退出与举报。
- 连麦：申请、受邀、设备预检、连接、已连入、静音、弱网、退出分别有文案和非颜色信号。
- 弱网：画面保留最后一帧，显示“正在恢复/仅听声音/重试”可执行选项；不展示笼统错误码。
- 结束：3 秒倒计时期间仍可手动进入下一场或返回；禁止停留在不可操作的结束画面。
- 减少动态：系统开启减少动态效果时停用点赞漂浮和装饰入场，只保留状态必要过渡。

## 4. 信息架构与页面职责

### 4.1 直播广场

- 分为“正在直播、预约、回放”；默认遵守圈子可见性，只有主播显式选择全平台且审核通过才进入全平台流。
- 卡片必须显示真实封面、主播、主题、圈子/全平台范围、直播状态和真实人数；禁止静态假数。
- 进入直播间立即播放；预加载下一间的详情和播放地址，不提前计入观看或打开音频。
- 空态、加载、无权限、已结束、网络失败均有独立文案和下一步。

### 4.2 观众直播间

```text
┌ 安全区：主播身份/关注 · 在线人数 · 更多 · 退出 ┐
│ 主题签/圈子范围（进入后自动弱化）                 │
│                                                   │
│               直播或多人连麦舞台                  │
│       礼物事件 / 正在讲解商品 / 风险与网络提示      │
│                                                   │
│ 公屏（左下，不盖主体）                             │
├ 评论输入 ─── 商品袋 · 礼物 · 连麦 · 分享/更多 ────┤
└ 安全区                                             ┘
```

- 上下滑切换直播间，只维持前/当前/后三个页面实例；切走必须暂停播放器、退在线状态、退出连麦。
- 当前房间结束：显示 3 秒倒计时；有下一间则自动进入，没有则返回进入直播间前的位置。
- 第一次进入自动播放；平台自动播放限制导致无声时，明确展示“一键开启声音”，不展示二次“播放”门槛。
- 更多面板包含清晰度、仅听声音、屏蔽礼物、举报、分享、播放诊断和隐私说明。

### 4.3 主播直播间

- 主播看到的主舞台与观众一致，必须能看到真实本地画面、公屏、商品浮层、礼物和连麦布局。
- 常驻高频项：翻转镜头、麦克风、摄像头、场控入口、结束直播；低频项进入控制面板。
- 控制台是半屏/独立页能力，完成操作后回到直播间；不得以控制台替代主播直播间。
- 结束直播必须二次确认，并显示直播时长、在线和未处理麦位；断网时进入“重连保护期”，不能立即误判结束。

### 4.4 副播、场控与管理后台

- 副播：申请 → 候场 → 主播批准 → 设备预检 → 主动确认开麦 → 已连入 → 静音/弱网 → 下麦，状态逐步可见。
- 场控：评论治理、麦位审批、商品置顶、提示卡、风险提醒；每项权限独立授予并记录操作者。
- 管理后台：房间、流状态、内容风险、用户举报、礼物/订单、实时质量、结束复盘互相可追溯。

### 4.5 OBS 工作台

- 展示可复制但默认脱敏的推流服务器与一次性/可轮换密钥；严禁在日志、截图和页面源代码中明文长期暴露。
- 提供场景/来源、分辨率、帧率、关键帧、编码器、码率、音频和网络预检清单。
- 以回调和监播事实展示“等待推流、推流中、弱网、断流保护、已结束”；不能用前端按钮自我宣告成功。
- 展示实时码率、帧率、丢帧、音频、最近回调和诊断建议；支持主动轮换密钥和异常结束。

## 5. 核心状态机

### 5.1 房间生命周期

`DRAFT → SCHEDULED → READY → CONNECTING → LIVING ↔ RECONNECTING → ENDING → ENDED → REPLAY_PROCESSING → REPLAY_READY`

- 每次转换必须有操作者/事件来源、时间、幂等键和审计记录。
- 推流回调可以推进 `CONNECTING/LIVING/RECONNECTING`，但用户权限和房间归属仍由业务服务裁决。
- `RECONNECTING` 设保护窗口；超时才自动结束。迟到或重复回调不得复活已结束房间。

### 5.2 连麦生命周期

`IDLE → REQUESTED/INVITED → WAITING_APPROVAL → DEVICE_CHECK → READY → CONNECTING → CONNECTED ↔ MUTED/WEAK_NETWORK → DISCONNECTING → ENDED`

- 拒绝、取消、超时、踢下麦和主动下麦均幂等。
- 主播远端离开回调只更新本地媒体状态；业务麦位已删除时不得再制造 404 告警。
- 支持 1v1 及 2/4/6/9 自适应布局：单人突出主体，多人提供 Panel/Grid/Fixed；音频席位显示清晰的发言、静音和网络状态。

### 5.3 播放生命周期

`PRELOAD → CONNECTING → FIRST_FRAME → PLAYING ↔ BUFFERING → RETRYING → ENDED/FAILED`

- 首帧前展示封面骨架，不出现纯白/纯黑无说明页面。
- 重试指数退避且有上限；用户始终能退出、切房或查看诊断。

### 5.4 普通观众多人舞台生命周期

`ORIGIN → GUEST_RTC_READY → MIX_STARTING → MIXED → MIX_DEGRADED/ORIGIN`

- 主播原流固定为 `room_{id}`；混流固定使用独立 `room_{id}_mix`，禁止覆盖原流。
- 嘉宾业务审批不等于媒体就绪；只有原生 TRTC 进房成功并续租后才创建混流。
- 合流失败、租约超时、TaskId 丢失或腾讯云异常时，普通观众立即保留/回退主播原流；不得黑屏等待混流。
- 客户端根据服务端 `streamMode` 变化切流；主播和连麦嘉宾继续走低延时 TRTC，普通观众走 CDN 合流。
- 最后一位嘉宾下麦和房间结束必须停止 TaskId；任务状态、RequestId、费用和失败码只记录脱敏证据。

### 6.1 场景组合覆盖

验收不能只测“主播 + 一名观众”。至少覆盖：移动主播单播、移动主播 + 语音嘉宾、移动主播 + 视频嘉宾、2/4/6 人连麦、纯音频席位与视频席位混合、主播邀请与观众申请同时到达、场控代管、OBS 单播、OBS + 移动嘉宾、带货讲解、礼物高峰、敏感评论处置、主播/嘉宾/普通观众分别断网、直播自然结束和违规中断。每个组合都要验证观众画面、主播画面、公屏、声音、按钮、业务状态、后台状态和退出清理。

## 7. 数据口径（唯一标准）

- **累计观看人数**：同一场直播内，登录用户按 `userId` 去重；匿名用户按客户端会话标识去重。详情刷新、轮询和多节点请求不增加。
- **实时在线**：最近 45 秒内发送心跳且当前未离开的唯一观看身份数；离开、切房、结束和超时均移除。
- **峰值在线**：按采集分钟内实时在线最大值，不使用累计观看替代。
- **观看次数**：如运营确需 PV，单独命名和存储，不得显示为“人数”。
- **平均停留**：所有有效观看会话时长之和 / 有效观看会话数；少于防刷阈值的会话单列。
- **互动率**：发生至少一次有效互动的唯一观众 / 累计观看人数；评论条数和点赞次数另列。
- **礼物/GMV/订单**：只统计支付或账务最终态，退款和撤销按财务口径回冲。
- **显示延迟**：实时在线允许 5 秒内收敛，运营分钟数据允许 90 秒内落库；界面标明更新时间。

## 8. 安全、合规与消费保护

- 开播前校验实名认证、直播权限、圈子权限和内容声明；敏感场景要求人工审核。
- 摄像头/麦克风在用户动作前说明用途，只在直播或连麦所需阶段开启；离开立即释放。
- 评论具备敏感词、频率限制、慢速模式、超时禁言、隐藏、拉黑、举报和管理员审计。
- 礼物与充值执行年龄、限额、二次确认、余额事实和退款规则；不得用强制弹窗或误触诱导消费。
- 首次打赏必须让用户设置单次与日累计限额，消费提醒默认开启；未完成年龄与监护规则校验时禁止进入付费链路。
- 不向普通观众公开用户消费统计、金额榜或以打赏金额主导的排序；礼物经营统计仅主播本人和授权管理员可见。
- 付费不能换取禁言、踢人、插队连麦等治理特权，连麦与评论资格不能由送礼金额决定。
- 商品价格、库存、优惠和销量来自服务端；下架、售罄、价格变化实时降级，禁止静态伪造。
- 推流密钥短期有效、可轮换、最小暴露；回调必须验签、幂等、限流并保留脱敏审计。
- 录制、截图、内容审核、违规中断和申诉流程在开播前可见。

## 9. 性能与可靠性门槛

- 预热命中时点击到首帧 P50 ≤ 1.5 秒、P95 ≤ 3 秒；冷启动 P95 ≤ 5 秒。
- 直播间切换 P95 ≤ 1.5 秒看到新房间首帧或清晰封面状态。
- 连续滑动 20 间无明显内存持续增长；播放器实例最多当前与相邻预加载所需数量。
- 评论和点赞高峰采用合并更新；主线程卡顿、ANR、崩溃和音视频资源泄漏为零容忍。
- Wi-Fi/蜂窝切换、来电/锁屏、前后台、权限拒绝/撤销、服务器滚动重启均有恢复测试。
- 音视频主观验收覆盖回声消除、噪声抑制、耳机/扬声器切换、双向同时说话和弱网降级。
- 音画同步偏差目标 ≤ 150ms；连麦端到端主观延迟目标 ≤ 500ms；普通 CDN 观众延迟需在界面和运营后台明确，不伪装成实时连麦延迟。
- 混流启动/停止成功率、任务存活时长、回退次数、MCU 转码分钟数和 CDN 带宽必须进入监控；混流失败不计作整场播放失败。

## 10. 分阶段交付与禁止降级

### P0：事实与主链路

1. 修复观看/在线/峰值口径和连麦退出竞态。
2. 观众/主播页恢复完整视觉层、运行时安全区、公屏和高频操作。
3. 进入即播、首帧状态、前后台恢复、正常/异常下播。
4. 单人双向连麦真实双机验收；按钮、状态和错误均可见。
5. 第三台普通观众设备看到相同多人合流舞台；嘉宾下麦后 5 秒内回到主播原流。

### P1：主流完整体验

1. 纵向多直播间切换、相邻预加载、结束 3 秒跳转/返回。
2. 多人连麦与自适应布局、邀请/申请队列、场控权限。
3. 礼物、消费保护、商品、分享、举报和治理工具接入真实后端；不发布未经同意的消费排行榜。
4. 主播控制台与 OBS 推流状态、诊断、回调、密钥轮换闭环。

### P2：运营与精细化

1. 画中画、投屏、多码率、提词、场景模板和高级互动。
2. 自动复盘、推荐优化、实验平台和更细的人群/转化分析。

禁止以 P2 的视觉演示掩盖 P0/P1 的真实链路缺失；所有暂不可用入口必须隐藏或明确标注，不能展示假成功。
