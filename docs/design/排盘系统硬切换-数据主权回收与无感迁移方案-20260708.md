# 排盘系统硬切换：数据主权回收与用户无感迁移方案

> 定位：这是平台最高优先级的战略工程。老排盘系统握着 570 万注册 / 10 万日活的入口与数据，
> 是新平台"存量用户 B 端化"整个商业模式的源头活水。本方案解决：如何在不与外包方撕破脸的前提下，
> 把本就属于董事长的用户数据平稳搬回自有系统，实现用户无感的硬切换。
>
> 编制：2026-07-08。本文只写策略与技术路径，不含任何具体操作实施。

---

## 一、局面定性（先看清筹码）

**事实基础（董事长陈述）**：
- 老排盘系统由董事长委托第三方开发，**软件所有权、数据所有权均属董事长**，开发款已结清。
- 第三方无合同层面的继续合作义务，但以"运维配合"为筹码施加软性拿捏（不给一键导出、后台各种不配合）。
- 现状：H5 嵌入新系统，但用户点击排盘后的**付款、客户管理后台都在第三方侧** → 用户同时存在于两套系统，割裂感强。
- 董事长有老后台登录账号，**能逐页查看全部用户信息**，但一键导出未开放。
- 排盘记录：后台只显示排盘数量，**内容存于第三方的阿里云服务器，董事长无访问权限**。

**关键判断**：
1. 这不是"权利之争"（数据确权清晰，都是董事长的），是**"操作便利之争"**——第三方占的是物理访问与运维操作的便利，不是法律权利。
2. 因此正解不是打官司（赢了关系僵，反噬 570 万用户体验），是**在维持表面合作的同时，把数据平稳搬回家**。
3. 时间站在董事长一边：自研排盘工具在秘密推进，一旦成熟，第三方的筹码归零。

---

## 二、目标拆解

| 资产 | 现状 | 回收难度 | 目标 |
|---|---|---|---|
| 用户信息（手机号/昵称/生辰等） | 后台可逐页看，无导出 | 中 | 全量搬进自有库 |
| 排盘记录**结果** | 阿里云，无访问权 | 高（大概率拿不回原表） | **不搬原表，用生辰重算** |
| 用户 UGC（批注/收藏/笔记） | 后台部分可见 | 高 | 能带则带，带不了则话术平滑 |
| 会员/付费状态 | 第三方后台 | 中 | 随用户信息一并回收 |
| 排盘入口 | H5 指向第三方 | 低（一行配置） | 切向自研工具 |

**战略要点**：把目标从"搬走那张排盘结果表"（做不到）**重定义为"拿到生辰输入 + 自研引擎重算"**（做得到）。
排盘是确定性算法——同样的出生年月日时 + 盘型，必然算出同样的盘。只要拿到用户的生辰（属于"用户信息"范畴，可回收），
新系统重算即可 1:1 还原历史盘，且从此结果掌握在自己手里。这一步同时倒逼并复用了自研排盘引擎，一举两得。

## 三、用户信息回收：三路并进（软→硬）

### 路 A：正当理由索取（先谈，成本最低）
以**数据备份 / 合规审计 / 投资尽调**为由，书面要求第三方提供一次全量用户数据导出（CSV/Excel）。
- 话术不提"切换/迁移"字眼，避免打草惊蛇。用"等保合规要求数据方提供备份"或"投资人尽调需要数据资产清单"。
- 法律底气：拒绝提供**董事长自己的数据**在《数据安全法》《个人信息保护法》下站不住脚，但话术上给对方台阶。
- 产出物：一封正式需求函（见配套文档《致第三方-数据备份需求函话术》）。

### 路 B：合法账号自动化取数（技术中性，可自研执行）
董事长拥有合法后台账号、有权查看每一页 → 用浏览器自动化**模拟人工翻页**，把有权看到的信息逐页记录落库。
- 本质：把"人有权看、但人力翻不完"的 500 万页，交给程序 7×24 翻。用的是自己的合法凭证，不涉及入侵、不破解、不越权。
- 前置评估（需要一个后台测试账号先探路）：翻页是否有频率限制 / 验证码 / IP 封禁 / 单账号并发限制。
- 风险控制：低速率、拟人化间隔、单账号串行，避免触发风控；只取董事长本就有权查看的字段。
- 若路 A 谈成，路 B 可省；两者同时启动，哪条先通走哪条。

### 路 C：法律施压（备用，不轻易动）
《数据安全法》第三方作为**受托处理方**，有配合数据控制者迁移、删除的义务。
必要时律师函要求"配合数据可携带性"，这是法定义务而非请求。仅在 A/B 均受阻时启用。

**推荐组合**：A（谈）+ B（技术验证）并行，C 留作底牌。

## 四、排盘记录：放弃搬运，改为重算

**结论：历史排盘结果表大概率拿不回，但这不重要。**

- 排盘 = 用户生辰输入经确定性算法产出。生辰随"用户信息"回收（路 A/B），自研引擎重算 → 结果完全一致。
- 真正会丢的只有用户手写的**批注 / 收藏 / 笔记**（UGC，非算法可复现）。占比极小。
  - 能通过路 A 带出则带；带不出则用"系统升级，历史收藏请重新标记"话术平滑，用户可接受。
- **副产品价值**：这一步强制自研排盘引擎必须先跑通并与老站结果比对校验，正好把"自研工具能否替代"这件事提前验证了。

---

## 五、无感硬切换：手机号是那把钥匙

用户在老系统与新系统的共同身份锚点 = **手机号**。迁移设计：

1. **静默建档**：把回收的用户（手机号 + 生辰 + 基本信息 + 会员状态）预灌进自有库，标记为"待激活/影子账号"。
   历史盘由自研引擎按生辰**预重算**并入库。
2. **无感认领**：用户用该手机号在新系统登录（或收到迁移引导短信登录）时，系统自动把影子账号与登录用户绑定，
   历史盘、会员身份、收藏一并归位 → 用户感知"我的东西都在，还更好用了"。
3. **切换入口**：待自研排盘工具成熟到可用，把 H5 嵌入入口从"指向第三方"改为"指向自研工具"——一行配置。
   此后用户点排盘，进的是自有系统，付款、记录、后台全部自持。
4. **灰度**：先小比例用户切自研工具、与老站双跑比对，无异议再全量。第三方 H5 保留一段时间作回退保险。

**技术地基已就绪**：新平台的手机号体系（M4 加密 + phoneHash 唯一）、排盘过渡策略（壳层收纳）、
影子账号可复用现有用户模型。切换本身是配置与数据工程，不是架构重建。

---

## 六、AI 推荐：不依赖第三方配合

第三方不配合 AI 推荐 → **绕过，不求人**。
- **硬切换后**：排盘结果在自有系统，AI 解读 / 推荐是在自己的结果页上加功能，与第三方无关。
- **过渡期（仍嵌 H5 时）的轻量方案**：老站排盘完成跳回壳层时带一个信号（`postMessage('paipan_done')` 一行），
  新平台在壳层浮出 AI 解读入口。若第三方连这一行都不给，就等硬切换后做，零依赖。
  （此方案已在《无痕商业化触点体系》触点 #2 中设计。）

3. 路 A 谈判由董事长主导，技术侧提供话术弹药。

## 八、风险与红线

- **不撕破脸**：全程维持表面合作，路 C 法律手段是底牌不是首选，避免第三方在切换前恶意搞破坏影响用户。
- **只取有权数据**：路 B 仅抓董事长本就有权在后台查看的字段，不破解、不越权、不触碰无权限的阿里云存储。
- **数据安全**：回收的用户数据（含生辰等敏感信息）入库即走 M4 加密存储体系，不明文落地。
- **用户体验优先**：任何切换以"用户无感"为最高准则，宁可慢、灰度、双跑，不可让 570 万用户感到割裂或丢失。
- **合规**：迁移过程符合《个人信息保护法》——数据控制者身份明确，用户知情同意通过服务条款/迁移告知覆盖。
