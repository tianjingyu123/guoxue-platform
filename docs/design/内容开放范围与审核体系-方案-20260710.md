## 0. 现状差距（一句话）

- 四类内容（文章/课程/短视频/直播）**都没有"开放范围"字段**；直播连审核状态都没有。
- 有一张设计完整的 `ContentAuditRecord` 表（机器审→人工审→AI复审→审核员/时间/驳回全字段），但**代码里 0 引用、从未接过**。
- admin 只能审文章/课程；没有"向平台开放必审"的业务逻辑。
- 有一套 UGC 文本/图片审核（敏感词→腾讯云→DeepSeek 三层漏斗），但只在文章/帖子发布时调用。

**结论：地基有一半（审核表结构、UGC 机审漏斗都在），缺的是"开放范围字段 + 统一审核记录 + 向平台开放必审的业务规则 + admin 五类内容审核面板"。**

## 1. 设计

### A. 开放范围字段（统一四类内容）

给 Article / Course / Video / LiveRoom 各加一个统一字段：

```prisma
visibility  String  @default("CIRCLE_ONLY")  // CIRCLE_ONLY=仅本圈可见 / PLATFORM=面向全平台
```

- `CIRCLE_ONLY`：内容只在所属圈子内可见（圈子封闭内容，不进平台公共池）。
- `PLATFORM`：面向全平台（进公共池、可被圈外人看到）——**必须审核通过才真正对外可见**。
- 短视频已有 `isPrivate`（仅自己可见）→ 保留，与 visibility 正交（isPrivate 优先级最高）。
- 圈内内容隔离 feed（详情页短视频/直播上下滑）据此过滤：本圈 CIRCLE_ONLY+PLATFORM → 补平台公共池 PLATFORM → **绝不展示他圈 CIRCLE_ONLY**。

### B. 统一审核记录：激活 ContentAuditRecord

- **它作为五类内容（ARTICLE/POST/COURSE/VIDEO/LIVE）的统一审核台账**（谁发的、属于哪个圈、机审/人审结果、审核员、时间、最终态、驳回原因——字段都现成）。
- 各内容表保留一个 `auditStatus` 作为**当前审核态快照**（PENDING/APPROVED/REJECTED，便于列表过滤），审核链路明细进 ContentAuditRecord。直播/短视频要补 auditStatus 字段。

### C. 核心业务规则：向平台开放必审（责任到人）

发布时按 visibility 分流：

```
发布内容
├── visibility = CIRCLE_ONLY（仅圈子）
│     → 走现有 UGC 机审（敏感词/腾讯云）通过即在圈内生效
│     → 圈主自治，不进平台人工审核队列
│
└── visibility = PLATFORM（全平台）
      → 先过 UGC 机审
      → 创建 ContentAuditRecord（submitterId=发布者, circleId=归属圈, contentType/contentId）
      → auditStatus=PENDING，内容"圈内可见、平台不可见"
      → 平台审核员人工审 → finalStatus=APPROVED → 才进公共池对外可见
                        → REJECTED → 记 rejectReason，发布者可见驳回原因
```

- **责任到人**：ContentAuditRecord 记 `submitterId`（谁发）+ `circleId`（哪个圈）+ `humanAuditorId`（谁审）+ 时间。全链路可追溯。

### D. 自动过审规则（统一）

- 平台管理员 / 官方圈发布 → 自动 APPROVED（沿用现有 Article/Course 的 isAdmin/autoApprove，统一成一处规则）。
- 普通圈主/成员发的 PLATFORM 内容 → 进人工审核队列。

### E. admin 审核面板扩展

- 现有 `ContentAudit.vue` 只支持文章/课程 → 扩展为**五类内容统一审核队列**：查 `ContentAuditRecord where finalStatus=PENDING`，按 contentType 分类，审核通过/驳回时回写对应内容表的 auditStatus + ContentAuditRecord。
- 权限：SUPER_ADMIN / CONTENT_AUDITOR（角色已有）。

### F. 前端对接（V0 正在设计）

- 发布页：开放范围选择器（仅圈子/全平台）+ "全平台需审核"提示 + 提交后审核状态（审核中/已驳回带原因）。
- 详情页/feed：按 visibility 过滤，实现内容隔离。

## 3. 🔴 需要你拍板的决策点

1. **默认开放范围**：新内容默认 `CIRCLE_ONLY`（仅圈子）还是 `PLATFORM`？
   - 我的建议：**默认 CIRCLE_ONLY**（安全、符合"圈子封闭内容"直觉），发布者主动选"全平台"才进审核。

2. **圈内内容（CIRCLE_ONLY）要不要平台人工审？**
   - 我的建议：**不要**。圈内内容走现有 UGC 机审（敏感词/腾讯云）即可，圈主自治。只有"向全平台开放"才进平台人工审核队列——审核资源用在刀刃上。

3. **短视频/直播现在是"先发后审/无审"，要不要统一改成"平台开放必先审"？**
   - 我的建议：**是**。圈内发直接可见（机审即可），但选"全平台"必须审核通过才进公共池。直播特殊（实时）：开播前审封面/标题，直播中走现有 LiveAuditLog 机审。

4. **文章是"对外窗口"，它的默认范围要不要特殊化（默认就 PLATFORM）？**
   - 我的建议：文章也**默认 CIRCLE_ONLY**，但发布界面把"全平台开放"作为**推荐选项**引导（因为文章是获客窗口）。保持规则统一，用引导而非默认值区别对待。

5. **谁能自动过审**：仅平台管理员 + 官方圈？还是"信誉好的圈主"也给一定自治额度？
   - 我的建议：**先只给平台管理员 + 官方圈自动过审**；圈主信誉分体系是二期，先不做。

## 4. 风险与备注

- schema 加字段是"只增不删"的安全迁移，对存量数据无损（visibility 默认值兜底）。
- ContentAuditRecord 表已存在，激活它不需要建表，风险低。
- 审核会增加平台人工工作量 → 自动过审规则 + 只审"全平台"内容，控制审核量。
- 与已还原前端的衔接：详情页 feed 隔离、发布页 visibility 选择，都等这套后端就绪后接入（已在还原台账标记为降级待补）。
