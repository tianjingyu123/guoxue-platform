## 一、多租户蓝图（任务十）

### 1.1 需求形态判断
未来租户是**少而重的品牌租户**（道商世界等·个位数到十位数），不是海量小 B——这决定选型。要求：数据绝对隔离、性能互不影响、运维可控。

### 1.2 选型决策：**database-per-tenant（一租户一库）**

| 方案 | 隔离 | 改造量 | 判定 |
|---|---|---|---|
| 共库加 tenantId 列 | 弱（一处漏 where 即串数据·资金灾难） | 292 表全改+每查询审计 | ❌ 否决：资金体系下风险不可接受 |
| PG schema-per-tenant | 中 | Prisma 多 schema 支撑一般 | 备选（未来海量小 B 白标再启用） |
| **一租户一库** | **绝对**（连接串级隔离·可独立备份/迁移/私有化） | 应用层近零改造 | ✅ 推荐：租户少而重时运维成本完全可控 |

部署形态：同机多库起步（PG 多 database + pm2 多实例 + nginx 按域名分流）→ 大租户可平移独立服务器/私有化（天然支持——这正是一租户一库的红利）。

### 1.3 共享与隔离的边界（关键决策）
- **必须隔离**：用户/资金/订单/内容/配置（全库）
- **可共享（平台服务层）**：AI 网关（按租户计量）、审核漏斗、短信/支付通道适配器、古籍公版内容库（只读挂载或复制）
- **绝不共享**：任何涉资金与个人信息的表

### 1.4 平滑迁移路径（四步·第一步现在就有收益）
1. **T0 品牌抽象（可先行·独立价值）**：新建 BrandConfig（站名/logo/主题色/协议主体/客服/域名）收敛现散落的"热卜"硬编码——同时服务当前的协议主体填充与将来换肤
2. T1 配置外置完成度检查：ThirdPartyConfig 已 DB 化✅；补齐 env 中租户相关项进 DB
3. T2 租户开通自动化：一键脚本=建库→migrate→种子（含 SettlementRule/等级/类目）→pm2 实例→nginx 站点→admin 租户注册表
4. T3 道商世界试点：用 T2 脚本开第二租户·超管 admin 加租户切换视图（只读聚合·不跨库写）

## 二、国际化蓝图（任务十一）

### 2.1 总判断：**国际化第一步不是翻译主 App，是官网+繁体**
主 App 200+ 页 uni-app 硬套 i18n 成本巨大且现阶段无收益。出海的正确载体是 **rebu-official 官网**（Next.js+next-intl 四语言已搭好）：内容（古籍/博客）+ 在线工具 + 下载引流——先用官网验证海外需求，再决定主 App 国际版。

### 2.2 分层差异清单（真正的深水区不是文案）
| 层 | 差异 | 方案方向 |
|---|---|---|
| 文案 | 简/繁/英/日/韩 | 官网 next-intl✅；主App暂不动；繁体=OpenCC 机转+人校（成本最低收益最快） |
| **历法/排盘算法** | 时区与真太阳时（出生地经度）、各国夏令时历史表、日韩四柱流派差异 | 排盘引擎 tz-aware 改造是前提（输入加出生地→经度→真太阳时）；日韩流派需本地顾问合作，**不可机械移植** |
| 支付 | 微信/支付宝海外不通 | 官网接 Stripe/PayPal（B 端 API/课程先行）；定价分区+汇率 |
| 内容审核 | 各国对命理内容政策差异大 | 目标市场排序：**华语圈（港澳台/马新）→日韩→欧美华人**；欧盟暂不进（GDPR 数据出境成本） |
| 合规 | 数据出境/隐私法域 | 海外用户数据存海外节点（官网 Vercel/CF 天然满足）；主库不出境 |

### 2.3 路线图
P0（随官网完成计划）：官网四语言内容填充+Stripe 收单 → P1：繁体版工具页（OpenCC+真太阳时改造）→ P2：日韩=先内容站后工具（需流派本地化合作）→ 主 App 国际版：待官网数据验证后立项。
