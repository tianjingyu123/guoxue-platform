# 平台性能与框架层优化 · 总体方案（对标国际顶级）

> 2026-07-05 · Fable 设计（董事长授权："商业与体验线已收口，开始性能框架层优化，对标国际顶级平台标准"）
> **方法论：先体检后开方**。以下每个结论都来自当日生产实测，不是拍脑袋。

## 一、生产体检结论（2026-07-05 实测基线）

| 维度 | 实测 | 判定 |
|---|---|---|
| 后端 API 本机延迟 | home 11ms / classics 5ms / courses 4ms / discover 25ms | ✅ **优秀**（缓存层起效·不是瓶颈） |
| 端到端 API 延迟（客户端视角） | 同样的接口 1.9-2.9 秒 | 🔴 **差距全在网络分发层**（线路 RTT+TLS+无 HTTP/2 复用） |
| H5 首屏 JS | index 728KB + 540KB ≈ 1.27MB（gzip 前） | 🟠 慢线路上首屏必慢·需分包瘦身+CDN |
| 进程模型 | PM2 **fork 单进程跑在 8 核机**上 | 🟠 7 核闲置·并发容量隐患（当前流量未爆） |
| nginx | gzip ✅ / 无 brotli / HTTP/2 未确认 / 静态资源无长缓存头验证 | 🟠 分发层还有免费性能可拿 |
| 数据库 | 68MB·最大表 ClassicChapter 19MB·pg_stat_statements 已装 | ✅ 体量很小·此前 DB 专项已优化过 |
| Redis | 用 1.96MB·**maxmemory 未设限** | 🟡 埋雷：无上限终会 OOM |
| 架构 | **一台服务器承载 API+DB+Redis+H5+admin 全部** | 🔴 单点故障=全平台不可用 |
| 备份 | 手动 pg_dump（部署时才做）·无自动化·无异地 | 🔴 数据安全底线未焊死 |
| 部署 | 全手动（bundle+scp+build+pm2）·曾发生 build OOM 删 dist 险情 | 🔴 无 CI/CD·人为风险高 |
| 可观测性 | 无 APM/RUM/告警面板（有埋点底座 TrackEvent+经营简报） | 🔴 出问题靠用户报告·顶级平台的最大差距 |

**一句话诊断：应用代码层已经很快，平台的短板全在"工程底座"——分发、容灾、可观测、自动化。这恰好是国际顶级平台与普通平台的真正分水岭。**

## 二、对标国际顶级平台的标准（我们的北极星）

| 领域 | 国际顶级标准 | 我们现状 | 目标（6个月） |
|---|---|---|---|
| 前端体验 | Google Core Web Vitals：LCP<2.5s / INP<200ms / CLS<0.1（75分位真实用户） | 未测量 | 国内 4G 实测 LCP<2.5s·建立 RUM 持续测量 |
| API 性能 | p95<300ms 端到端（含网络） | 本机 25ms·端到端 2s+ | CDN/边缘接入后 p95<500ms→300ms |

## 三、分四阶段实施（每阶段独立可验收·先免费后花钱）

### P0 免费即得（本周·零采购·纯配置与代码）
1. **PM2 cluster 模式**：fork→cluster×4（留 4 核给 DB/Redis/构建）。前置核查：cron 任务已有分布式锁（T11 修过）需逐一确认防多实例重复执行；websocket/内存态排查。容量立涨 4 倍。
2. **nginx 榨干**：确认/开启 HTTP/2（TLS 已有）·brotli 模块·H5 静态资源 `immutable` 长缓存头（文件名带 hash 天然可永久缓存）·API 响应 gzip 覆盖核查。
3. **H5 首屏瘦身**：分析 index 两个大包构成（uni-app manualChunks），把 flv.js（163KB·仅直播用）等重件确认异步化；首页非首屏组件懒加载。目标主包 <400KB。
4. **Redis maxmemory + LRU**：设 512MB + allkeys-lru，拆雷。
5. **数据库自动备份**：cron 每日 pg_dump + 保留 7 天 + **异地**（先推备份到 cnb/对象存储任一）。RPO 从 ∞ → 24h。
6. **k6 压测基线**：对 5 个核心接口建立当前容量基线（单进程 vs cluster 对比），留档作为以后每次架构变更的对照。

### P1 可观测性（第二周·核心是"出问题我们先于用户知道"）
1. **RUM 真实用户测量**：H5 接 web-vitals，上报走现有 `/track/batch` 埋点底座（零新基建），看板进现有 admin 数据看板（DashboardDaily 加性能页）。
2. **服务端指标**：node 进程指标+接口耗时分位数（NestJS 拦截器聚合→现有 metrics 底座）·nginx 访问日志分析（p95/错误率 cron 聚合入看板）。
3. **告警**：错误率/延迟/磁盘/内存阈值 → 复用简报的站内信+（配好后）你的管理群 webhook。分钟级 cron。
4. **慢查询哨兵**：pg_stat_statements 周报 Top10 慢查询进简报。

### P2 分发与容灾（第三四周·需要少量采购·见§四拍板）
1. **CDN 接入**（最大的用户体验单点提升）：H5/admin 静态资源+图片走 CDN 边缘，API 走 CDN 动态加速或至少边缘 TLS 终结（把 2s 网络耗时打到 <500ms）。国内 CDN 需备案域名（与官网备案同题）。
2. **对象存储归口**：图片/视频上传已走 COS，核查静态资源全量归口+图片自动压缩/WebP 转换（COS 数据万象）。
3. **数据库容灾升级**：WAL 归档连续备份（RPO→分钟级）；预算允许则云数据库 RDS 或第二台服务器做流复制热备（RTO→分钟级）。
4. **恢复演练**：从备份完整拉起一套环境的 runbook + 实际演练一次（没演练过的备份=没有备份）。

### P3 工程效能与架构前瞻（第二个月起·顶级平台的底座）
1. **CI/CD 流水线**：cnb.cool 自带 CI（国内快·仓库已在）：推送→tsc+jest 全量→构建产物→一键部署脚本→自动冒烟→失败自动回滚。消灭手动部署的全部人为风险。
2. **蓝绿/滚动发布**：PM2 cluster reload 实现零停机发布（配合 CI）。
3. **容量规划**：基于 P1 数据做月度容量报告；用户量增长触发线（如 API p95>500ms 或 CPU>60% 持续）→ 扩容预案（第二台应用服务器+nginx 负载均衡·DB 独立）。
4. **架构预留核查**：多租户 T0 已做品牌抽象；API 无状态化核查（session 全在 Redis/JWT ✅）为水平扩展铺路。
5. **安全加固**：云 WAF·依赖漏洞扫描（npm audit 进 CI）·年度渗透测试（外采·预算项）。

## 五、验收指标（每阶段收口时向你汇报的数字）

- P0 收口：cluster 压测 QPS ≥ 基线×3；H5 主包 <400KB；备份每日落桶可验证
- P1 收口：admin 看板能看到真实用户 LCP/INP 分布 + API p95 + 错误率；模拟故障告警 5 分钟内进站内信
- P2 收口：国内 4G 实测首屏 LCP <2.5s；API 端到端 p95 <500ms；恢复演练 RTO 实测 <1h
- P3 收口：一次 git push 全自动到生产（含测试与冒烟）；容量报告月度进简报
