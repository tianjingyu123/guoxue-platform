# 运维守护体系：智能监控告警 · 自动应急降级 · 数据库灾备

> 2026-07-05 · Fable 设计 · 原则：**全部基于存量底座增量搭建，零新基建**。存量盘点：health 端点已检查 9 项依赖、MetricsService 已有、TrackEvent 埋点底座、DashboardDaily+每日简报 cron、站内信通知、经营简报（管理群 webhook 等密钥后接入）。

---

## 一、智能监控与告警（设计）

### 1.1 三层监控模型

| 层 | 监控什么 | 数据源（已有） | 频率 |
|---|---|---|---|
| L1 系统层 | 进程存活/内存/磁盘/DB/Redis 延迟 | health 端点 checks + pm2 | 每分钟 |
| L2 服务层 | API 错误率/p95 延迟/慢查询 | nginx access log + pg_stat_statements（待开启·任务包T1）| 每 5 分钟聚合 |
| L3 业务层 | **支付成功率/下单量/日活曲线/退款率/分佣异常/AI 失败率** | Order/TrackEvent/CommissionRecord/AiAnalysisRecord 表直查 | 每 5-15 分钟 |

### 1.2 业务哨兵规则（首发 8 条·阈值可配 ConfigSystem）

1. **支付成功率**：15 分钟窗口内 (PAID 订单数)/(发起支付数) < 70% 且样本 ≥ 5 → P1 告警（可能回调断了/渠道故障）。
2. **支付回调静默**：有 PENDING 支付发起但连续 30 分钟零回调到达 → P1（回调地址/验签故障）。
3. **【资金对账】日志出现**：logger 含"资金对账"关键字（金额不符/找不到订单）→ P1 即时。
4. **日活暴跌**：当日小时活跃 < 上周同时段 40% 且时间在 9-23 点 → P2（可能前端白屏/登录故障）。
5. **退款率飙升**：24h 退款申请/订单 > 20% 且样本 ≥ 10 → P2。
6. **登录失败率**：15 分钟登录失败/尝试 > 60% 且样本 ≥ 20 → P2（短信通道故障/撞库攻击双重可能）。
7. **AI 失败率**：15 分钟 AI 调用失败 > 30% → P3（供应商故障，触发降级提示）。
8. **磁盘水位**：> 85% → P2（build/日志/备份把盘吃满是本机已知风险）。

### 1.3 告警分级与通道

- P1（资金/全站不可用）：站内信(管理员) + 群 webhook + 短信（密钥后）——**即时**，且附"初步定位信息"（触发规则+最近错误日志摘要 tail 20 + health 快照）。
- P2（功能性故障）：站内信 + 群 webhook，15 分钟聚合去重（同规则 1 小时内不重发）。
- P3（降级类）：站内信，日报汇总。
- 恢复通知：告警解除时发"已恢复"（避免半夜白紧张）。

### 1.4 实施任务包 O-T1（给普通模型·预计 1 天）

```
【贴项目Prompt知识库万能头】
任务：新建 modules/sentinel 业务哨兵模块。
1. sentinel.service.ts：实现上表 8 条规则，每条一个探针方法（SQL 直查，参数阈值从 ConfigSystem 读，key 前缀 sentinel.*，缺省用文档默认值）。
2. @Cron 每 5 分钟跑 L3 探针、每分钟跑 L1（复用 health 端点内部 service 勿重复实现），全部包 runExclusive("sentinel_xxx", 240)。

```

## 二、自动化应急降级（设计）

### 2.1 依赖降级矩阵（前端已大多有空态，本设计补"系统性开关"）

| 依赖故障 | 自动动作 | 用户看到 |
|---|---|---|
| 腾讯云直播/VOD | health 检查连续 3 次 fail → 写 feature:live_degraded=true（TTL 10min 自动恢复探测）| 直播/短视频页顶部横幅"服务维护中，稍后再试"，列表保留 |
| IM | 同上 feature:im_degraded | 私信页降级提示，站内信兜底 |
| AI 供应商 | ai-gateway 已有 fallback 模型链；连续失败再降级 → 缓存兜底/礼貌降级文案 | "AI 老师休息中" |
| 短信 | 发送失败率哨兵触发 → 告警（**不自动切**，登录还有密码通道）| 提示改用密码登录 |
| 支付某渠道 | 回调静默哨兵触发 → 告警 + 手动开关 feature:pay_channel_xx | 收银台隐藏该渠道 |
| Redis | 已内建内存降级 + 资金 cron 拒跑（M5 done）| 无感 |
| DB | 无降级可言 → P1 告警 + pm2 自动重启 | — |

**设计要点**：降级开关统一走已有的 feature flag 体系（ConfigSystem feature:* + 缓存），前端用现有的 flag 查询通道读取——**不发明第二套开关**。自动写开关的只有"探测明确、恢复明确"的（直播/IM/AI）；支付类只告警人工拍板，避免误杀。

### 2.2 实施任务包 O-T2（给普通模型·预计 0.5 天）

```
【万能头】
任务：health 检查接自动降级。
1. health service 的 live/vod/im 检查结果写连续失败计数（Redis incr）；连续 3 次失败 → set feature:xxx_degraded=true TTL 600 + 发 P3 告警；恢复探测成功 → del。
2. mobile 端直播/短视频/IM 入口页 onLoad 查 flag（复用现有 feature 查询 api），degraded 时顶部展示横幅组件（新建 components/degraded-banner.vue，文案 props 传入）。
3. spec + vue-tsc + mock 扫描全绿。
```

## 三、数据库灾备（设计+手册）

### 3.1 备份策略（RPO 从 ∞ → 24h → 未来分钟级）

- **每日全备**（立即做·任务包 T1 内）：cron 每日 03:30 `pg_dump -Fc` → /opt/backup/guoxue-YYYYMMDD.dump → 保留本地 7 天 → **coscmd 推 COS 低频存储桶保留 30 天**（异地·约 ¥10-50/月·已在采购清单第 3 项）。备份后校验：pg_restore --list 能读 + 文件大小 > 上次的 50% 才算成功，失败发 P2 告警。
- **WAL 归档**（P2 阶段·把 RPO 打到分钟级）：archive_command 推 WAL 到 COS。等 CDN/容灾采购一并拍板。
- **备份监控**：哨兵加第 9 条规则——最新备份文件时间 > 26 小时 → P1。

### 3.2 恢复手册（Runbook·贴在这里·演练时照做）

```
场景 A：数据误删/逻辑损坏（DB 还活着）
1. 立即 pm2 stop guoxue-server（防持续写坏）
2. pg_dump 现场再备一份（保留事故现场）
3. createdb guoxue_restore && pg_restore -d guoxue_restore 最近备份
4. 在 restore 库定位正确数据 → 手工修复主库（能修表就别全量回滚）
5. 全量回滚（最后手段）：ALTER DATABASE 换名切库 → 改 .env DATABASE_URL → pm2 restart
场景 B：服务器整机故障
1. 新机器：装 PG15+Redis+Node.js 22/24 LTS+pnpm+PM2+nginx（版本对齐）
2. git clone 或 bundle 恢复代码 → 恢复 .env（【关键】ENCRYPTION_KEY=b6e5712d... 必须原值，丢失=全库密文报废，此 key 另存密码管理器）
3. 从 COS 拉最新备份 pg_restore
4. prisma generate → build → pm2 start → health 全绿 → 改 DNS/nginx
预计 RTO：场景 A 30-60 分钟，场景 B 2-4 小时（演练后修正此数）
```

### 3.3 演练要求（没演练过的备份=没有备份）

上线后 30 天内做一次场景 A 演练（在测试库），出演练记录修正 RTO 数字。任务包给运维/普通模型均可执行。

## 四、本设计的哨兵与 P1 可观测（T3）的关系

哨兵（业务异常→告警）是 P1 可观测（RUM/指标看板）的**先行子集**——先保命后看盘。O-T1 落地后，P1 批的服务端指标聚合可复用 SentinelAlert 表和通知通道，不冲突不重复。
