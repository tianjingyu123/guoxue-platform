# T1 统一结算引擎 — 设计方案 V1（待逐节探讨）

> 2026-07-02 · 七日冲刺 D1 交付物 · 基于两路侦察 + 代码核实（详见作战计划「T1 现状侦察结论」）
> 目标：把散落在 12 个模块的分账/结算/提现逻辑，收编为一个**配置驱动、合规内置、可对账、可追回**的统一结算引擎。

---

## 〇、设计原则

1. **合规铸进架构**：两级计酬、真实交易计酬等红线做成引擎硬约束——不合规的配置根本配不出来。
2. **渐进迁移，不停机**：现有明细表（StationEarning/OperatorEarning/UserEarning/CircleRevenueRecord/MerchantSettlement）保留为分账明细，引擎先收编「入口和配置」，再收编「时机和提现」。
3. **每一分钱可解释**：任意订单可查完整分账链（谁、多少、依据哪条规则、何时可提、是否被冲正）。

## 一、现状问题（侦察结论摘要）

| # | 问题 | 后果 |
|---|---|---|
| 1 | 分账逻辑散落 12 个模块，比例部分硬编码（直播/咨询 rate=0.5 写死） | 改比例要改代码；场景间规则不一致 |
| 2 | 结算时机不一致：佣金/打赏/咨询**实时入账**，商家/驿站 T+N 结算单 | 实时入账 → 诈骗/退款时钱已可提走，追不回 |
| 3 | 两套提现表（Withdrawal / WithdrawalApplication）+ 多套账户余额 | 口径分裂，提现审批未走 FundApproval |
| 4 | 无对账模块 | 错账难发现难追溯 |
| 5 | 退款冲正只覆盖 station/operator/platformFee，UserEarning 场景（打赏/咨询）无冲正 | 退款后收益侧不回退 |

## 二、合规硬约束（引擎内置铁律）

| 铁律 | 实现方式 |
|---|---|
| L1 计酬 ≤ 两级 | 分账规则 splits 数组中 `role=PROMOTER` 类目至多 2 条；引擎校验，超出抛错拒绝落库（已在 commission.service 实现，引擎化后上升为通用校验） |
| L2 真实交易计酬 | 每条 LedgerEntry 必须挂 refType+refId（订单/通话/礼物记录），无凭据不入账 |
| L3 自买自卖防护 | 分账前校验：付款人 == 收益人（或其分站/推荐链）时标记 SELF_DEAL，佣金类目不发放（服务类目如讲师课酬不受限） |
| L4 结算缓冲期 | 收益默认 `PENDING → availableAt 后 SETTLED`，缓冲期内可整单冻结/冲正（对接风险隔离框架第 4 道墙） |
| L5 冲正全覆盖 | reverse(refId) 对该凭据下**所有场景**的正向记录生成负向冲正（幂等），缓冲期内直接扣回，已提现部分进追偿队列 |

## 三、核心抽象

### 3.1 SettlementRule 场景规则表（新表，取代硬编码+扩展 CommissionConfig）

```prisma
model SettlementRule {
  id            String   @id @default(uuid())
  scene         String   @unique // COURSE_ORDER / PRODUCT_ORDER / CIRCLE_JOIN / LIVE_GIFT / AUDIO_CALL / QUESTION / STATION_COURSE / EBOOK_ORDER / MEMBER_PURCHASE ...
  splits        Json     // [{ role: "PROVIDER"|"CIRCLE_OWNER"|"STATION"|"OPERATOR"|"PLATFORM", rate: 0.5, basis: "GROSS"|"PARENT_SPLIT" }]
  bufferDays    Int      @default(7)  // 结算缓冲期（0=实时）
  requireApproval Boolean @default(false) // 单笔超阈值走 FundApproval
  approvalThreshold Decimal? @db.Decimal(10,2)
  enabled       Boolean  @default(true)
  updatedBy     String?  // 修改走 COMMISSION_CONFIG 审批流（已有）
  updatedAt     DateTime @updatedAt
}
```

- `basis: GROSS` = 按订单总额分（讲师课酬、平台抽成）；`basis: PARENT_SPLIT` = 按上一级分账结果再分（管理奖按站长佣金计）。
- **引擎启动时校验每个 scene 的 PROMOTER 类 splits ≤ 2 条（铁律 L1），校验失败拒绝加载该规则并告警。**
- 现有 CommissionConfig 保留读兼容一个版本，数据迁移脚本把 20+ configKey 转成 SettlementRule。

### 3.2 SettlementEngine 统一入口（新模块 modules/settlement）

```ts
// 唯一入账入口 —— 各业务模块不再自行创建收益记录
async settle(params: {
  scene: string;          // 场景 key
  refType: string; refId: string;   // 交易凭据（铁律 L2）
  amount: number;         // 交易总额（元）
  payerId: string;        // 付款人（铁律 L3 校验用）
  parties: {              // 各角色的具体主体，由业务方提供
    providerId?: string; circleId?: string; stationId?: string; ...
  };
}): Promise<LedgerEntry[]>

// 唯一冲正入口（铁律 L5）
async reverse(refType: string, refId: string, reason: string): Promise<void>

// 结算 cron：把过了 availableAt 且未冻结的 PENDING 记录批量置为 SETTLED，同步各余额
async settlePending(): Promise<SettlementBatchReport>
```

### 3.3 LedgerEntry 统一分账流水（新表，明细表之上的总账）

```prisma
model LedgerEntry {
  id          String   @id @default(uuid())
  scene       String
  refType     String
  refId       String
  beneficiaryType String // USER / STATION / OPERATOR / MERCHANT / PLATFORM
  beneficiaryId   String
  role        String   // PROVIDER / CIRCLE_OWNER / STATION / OPERATOR / PLATFORM
  amount      Decimal  @db.Decimal(12,2) // 正=入账，负=冲正
  rate        Decimal  @db.Decimal(5,4)
  status      String   @default("PENDING") // PENDING / SETTLED / FROZEN / REVERSED
  availableAt DateTime // 缓冲期到期时间（铁律 L4）
  batchId     String?  // 归属结算批次
  createdAt   DateTime @default(now())
  @@index([refType, refId])
  @@index([beneficiaryType, beneficiaryId, status])
  @@index([status, availableAt])
}
```

- **现有明细表继续写**（渐进期双写：引擎写 LedgerEntry + 兼容写旧明细表），余额与提现逐步切到以 LedgerEntry 为准。
- 「可提现余额」= SETTLED 之和 −（占用中提现），替换现在按各自明细表 sum 的分裂口径。

### 3.4 统一提现 WithdrawalRequest（合并两套表）

- 合并 Withdrawal（分站/运营商）与 WithdrawalApplication（用户/创作者）为一张 WithdrawalRequest（beneficiaryType 区分），保留旧表只读归档。
- 提现审批统一走 FundApproval（新增 type=WITHDRAWAL），沿用防自审自批守卫；限额/手续费/税费逻辑从 wallet.service 抽到引擎。
- 追偿队列：已提现后发生冲正 → 生成 ClawbackTask（先抵扣未提余额，不足记欠款并冻结账号提现权限）。

### 3.5 对账与报表

- 每日 cron 对账：`sum(订单实付) == sum(LedgerEntry 正向) + 平台留存`，按 scene 分组，差额 > 0.01 元告警（对接工作台 alerts）。
- SettlementBatch（结算批次）+ 管理端报表页：按周期/角色/场景汇总应结/已结/冻结/冲正，替代商家/驿站各自的结算单口径（MerchantSettlement 收编为引擎的一种 batch 输出）。

## 四、与风险隔离框架的对接点

| 防火墙 | 引擎提供的能力 |
|---|---|
| 事中墙（异常交易） | 风控服务可调 `freeze(refId)` 冻结缓冲期内整单分账；解冻/冲正二选一 |
| 资金墙（缓冲期） | bufferDays 按场景配置：建议 打赏 T+3 / 咨询 T+7 / 推广佣金 T+7 / 课程 T+7（过退款窗口）；商家保持周期结算单 |
| 处置墙（投诉退款） | 投诉成立 → reverse() 全场景冲正 + 钱包退款，缓冲期内资金 100% 可追回 |

## 五、迁移路径（不停机，四阶段）

| 阶段 | 内容 | 风险 |
|---|---|---|
| P1 配置收编 | 建 SettlementRule + 迁移 CommissionConfig + 收编硬编码 rate=0.5（直播/咨询/提问改读规则表）；行为不变 | 低（纯配置化） |
| P2 引擎入口 + 缓冲期 | 建 settlement 模块 + LedgerEntry；**新交易**走 settle() 双写；打赏/咨询/佣金加 availableAt 缓冲；可提现口径切换（历史记录视为已 SETTLED） | 中（余额口径切换需灰度+对账验证） |
| P3 提现统一 | WithdrawalRequest + FundApproval 接入 + 追偿队列 | 中 |
| P4 对账报表 | 对账 cron + SettlementBatch + 管理端报表页 | 低 |

每阶段独立可上线、可回滚（引擎不可用时降级回旧路径的开关）。
