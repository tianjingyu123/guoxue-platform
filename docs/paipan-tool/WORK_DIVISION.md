# 排盘工具 — Claude × Pixso 分工方案

> 分工目标是：**各做最擅长的事，通过标准化交接物无缝衔接**。

---

## 一、三方角色

| 角色 | 负责 | 强项 | 弱项 |
|------|------|------|------|
| **Claude** | 代码实现 + 后端架构 | 写业务逻辑、API、数据库、算法 | 视觉审美、布局创意 |
| **Pixso** | 移动端 C 端视觉设计标准 | 视觉设计、交互创意、品牌感 | 国学领域知识、算法理解 |
| **Paico** | 管理后台 UI 设计 | 管理后台视觉 | 同上 |

---

## 二、为什么是 Pixso 出标准而不是出代码

```
V0 直接出代码的问题：
  V0 代码风格 ≠ Claude 代码风格
  → V0 的裸 div / 硬编码色值 / 无 Props 接口
  → Claude 拿过来要把 V0 代码逆向理解，再用项目规范重写一遍
  → 100+ 个组件，逆向成本不可接受

Pixso 出标准的优势：
  Pixso 产出的是"视觉事实"（这个组件长这样 / 间距多少 / 颜色是什么）
  Claude 拿到的是"靶子"，用项目已有的 shadcn/ui + COLOR_TOKENS 直接实现
  → 不需要逆向任何东西
  → 设计稿是目标，代码是结果，Claude 直接从 0 写
```

**关键差异：**

| | V0 出代码 | Pixso 出标准 |
|------|----------|------------|
| 产出物 | Vue 组件代码 | 带标注的设计稿 |
| Claude 工作 | 逆向理解 → 重写 | 直接按图实现 |
| 代码一致性 | 差（两种风格混合） | 好（Claude 统一风格） |
| 组件架构 | V0 不知道三层架构 | Claude 在设计稿约束下自由组装 |
| Props 接口 | V0 代码可能没有 | Claude 在设计前定义，设计稿对齐 |
| 迭代效率 | 改代码要 V0 重新出 | 改设计稿 Claude 跟着改代码 |

## 三、核心分工矩阵

### Claude 负责（代码实现层）

```
✅ 后端 API（NestJS/Prisma/PostgreSQL）
✅ 排盘计算引擎（纯函数）
✅ 数据模型设计（Prisma Schema）
✅ 组件 Props 类型定义（TypeScript 接口）—— 在设计稿出来之前先定义
✅ 模板组件代码实现（5 种模板：PageTool/PageWorkspace/PageCompare/PageDashboard/PageList）
✅ 业务组件代码实现（根据 Pixso 设计稿 + Props 定义写代码）
✅ API 对接（前端 → 后端数据流）
✅ 数据库表设计 + 迁移脚本
✅ 用户定制机制（user_paipan_preference）
✅ 颜色令牌文件（COLOR_TOKENS.ts）—— Pixso 设计稿的取色来源
✅ 设计约束文件（DESIGN_CONSTRAINTS.md）—— Pixso 设计的边界
✅ 全部代码文件的创建和维护
✅ 单元测试 / 集成测试
```

### Pixso 负责（视觉设计标准层，不写代码）

```
✅ 5 种模板页面的视觉设计稿（带标注）
✅ 每种工具盘面的视觉呈现（四柱表样式、九宫格样式、卦象样式...）
✅ 业务组件的视觉设计稿（每个组件：正常/悬停/点击/禁用/加载/空/错误 多状态）
✅ 移动端/平板/桌面三断点的布局方案
✅ 色彩方案微调（在 COLOR_TOKENS.ts 定义的色值范围内）
✅ 间距/字号/圆角的视觉调优（在 DESIGN_CONSTRAINTS.md 范围内）
✅ Pixso 设计文件（含标注：间距/字号/颜色令牌引用）
✅ 移动端特有的手势交互方案建议
✅ 视觉还原度验收（开发完成后截图对比设计稿）
```

### Pixso 交付物格式

```
🎨 设计稿交付标准（每次提交包含）：
  ├── 页面/组件完整设计稿（Pixso 文件链接）
  ├── 标注模式：所有间距标注（与 DESIGN_CONSTRAINTS.md 允许值对齐）
  ├── 颜色标注：引用 COLOR_TOKENS.ts 中的令牌名（如 "WUXING.huo"）
  ├── 字号标注：引用规则值（text-sm / text-base / text-lg）
  └── 组件状态覆盖：每个组件至少覆盖正常/悬停/禁用/空态 4 种
```

### Paico 负责（管理后台设计）

```
✅ 管理后台排盘工具相关页面视觉设计
✅ 客户管理 / 命例库 / 报告管理等后台页面
✅ 后台特有的表格/表单/数据展示视觉
```

### 都参与的

```
🔄 交互规则（Claude 出初稿 → Pixso 视觉验证 → Claude 代码实现）
🔄 组件目录（Claude 出 Props 定义 → Pixso 出视觉稿 → Claude 写代码）
🔄 设计约束（Claude 出框架 → Pixso 视觉调优 → Claude 锁定为文件）
```

## 四、交接流程（关键）

### 场景 A：新工具开发（如新增八字排盘页面）

```
Claude 产出（Step 1）：
  1. API 接口就绪（calculate / input-schema / mock）
  2. API 对接文档（入参/出参/data.result 结构）
  3. 该工具的"Pixso 设计需求单"（使用 PIXSO_HANDOFF_TEMPLATE.md）
  4. 涉及的业务组件 Props 接口定义

         ↓ Claude 将需求单 + API 文档 + Props 定义 发给 Pixso

Pixso 产出（Step 2）：
  1. Pixso 设计文件（工具页完整稿 + 标注）
  2. 各业务组件的独立设计稿（多状态覆盖）
  3. 三断点布局方案（≥1024 / 768-1023 / <768）

         ↓ Pixso 将设计稿交给 Claude（Pixso 不写代码）

Claude 产出（Step 3）：
  1. 读设计稿 → 提取视觉参数（间距/颜色/字号）
  2. 用模板组件 PageTool + 业务组件（根据设计稿实现）组装页面
  3. 对接 API，跑通完整数据流
  4. 对照 DESIGN_CONSTRAINTS.md 自查
  5. 对照 Pixso 设计稿做视觉还原度自检

         ↓ Claude 自测通过 → 截图发给 Pixso

Pixso 验收（Step 4）：
  1. 截图 vs 设计稿 对比
  2. 列出偏离项（间距不对/颜色偏差/字号不一致）
  3. Claude 修正
```

### 场景 B：已有工具改版

```
Claude 产出：
  1. 当前页面截图 + 标注问题点
  2. 改版需求单（改哪里、为什么改）

         ↓

Pixso 产出：
  1. 改版后设计稿（仅改动部分）
  2. 差异标注（before → after）

         ↓

Claude 产出：
  1. 按设计稿修改代码
  2. 回归测试（确保无功能退化）
```

### 场景 C：新增通用组件

```
Claude 产出（Props 定义先行）：
  1. 组件 Props 接口定义（TypeScript）
  2. 组件业务需求（这个组件在哪些工具中用、展示什么数据）
  3. 参考示例（竞品截图或已有相似组件）

         ↓

Pixso 产出（视觉设计）：
  1. 组件视觉设计稿（多状态：default/hover/active/disabled/loading/empty/error）
  2. 各断点下的尺寸
  3. 标注间距/颜色/字号

         ↓

Claude 产出（代码实现）：
  1. 组件代码实现（按 Props 定义 + Pixso 设计稿）
  2. 登记到 COMPONENT_CATALOG.md
```

## 五、Pixso 需要知道的国学领域知识（最小集）

Pixso 不需要懂八字/奇门，只需要知道以下"视觉事实"：

### 数据本质（这些是 Pixso 要画的东西）
```
- 八字排盘 = 一个4列的表格（年/月/日/时 × 天干/地支/藏干/十神/神煞）
- 奇门排盘 = 一个3×3的九宫格（每格内有5-6个元素）
- 六爻排盘 = 6行堆叠的线（每行有7-8个属性）
- 紫微斗数 = 12个格子的圆形/方形布局
- 大六壬 = 4行输入 + 3行输出 + 标签列表
```

### 用户操作模式
```
- 老师排盘 = 高频、快速、需要看到尽可能多的数据（信息密度高）
- 学生看盘 = 需要解释、需要看到推导过程
- 客户看盘 = 只需要结论、美观、易懂
```

### 视觉禁区（这些绝对不能改）
```
- 五行色不能用于装饰，只能用于属性标注（木绿火红土橙金黄水蓝）
- 八卦符号有固定形状，不能变形
- 天干地支不能拆分换行（"甲子"必须在同一行）
- 排盘数据必须用等宽字体（保证上下对齐）
- 吉凶色：吉=深绿 凶=深红 平=灰（不能换色）
```

## 六、Pixso 不需要做的（避免浪费时间）

| 不要做 | 原因 |
|--------|------|
| 写任何代码（Vue/HTML/CSS） | Claude 负责全部代码 |
| 设计"AI 分析区"的对话气泡样式 | 排盘工具不显示 AI 对话，AI 在智能体广场 |
| 设计复杂的数据可视化图表 | 图表样式由 ECharts 配置驱动，Claude 负责 |
| 设计"分享到微信/微博"的社交卡片 | 分享用预设模板，Claude 负责 |
| 从零设计图标系统 | 已有 Element Plus Icons + Lucide Icons |
| 设计音效/震动反馈 | 排盘工具不涉及 |
| 设计品牌 Logo/标识 | 已有品牌体系 |
| 考虑后端数据格式/API 接口 | Claude 负责，Pixso 只需看数据说明文档 |

## 七、交付物清单

### Claude → Pixso 的交付物

每次交给 Pixso 一个任务时，打包以下内容：

```
📦 Claude → Pixso 任务包
├── 📋 设计需求单（按 PIXSO_HANDOFF_TEMPLATE.md 格式）
├── 📊 工具数据说明（这个工具输出什么、这些数据长什么样、带真实示例值）
├── 🖼️ 竞品参考截图（问真/热卜的同功能截图 + 标注优缺点）
├── 📐 组件 Props 接口（如果是新组件）
├── 🎨 颜色/间距约束引用（指向 COLOR_TOKENS.ts + DESIGN_CONSTRAINTS.md）
└── 📝 视觉禁区清单（这个工具特有的不能改的东西）
```

### Pixso → Claude 的交付物

```
📦 Pixso → Claude 产出包
├── 🎨 Pixso 设计文件链接（页面完整稿 + 各组件独立稿）
├── 📏 标注模式截图（关键间距/字号/颜色全部标注，颜色引用 COLOR_TOKENS 令牌名）
├── 📱 三断点布局（≥1024 / 768-1023 / <768 各自的设计稿或差异标注）
├── 🔄 状态覆盖（正常/加载/空数据/错误/悬停/禁用 6 种状态）
└── ⚠️ 设计说明（如果有任何超出 DESIGN_CONSTRAINTS.md 范围的设计决策，在此说明理由）
```

## 八、协作节奏

| 阶段 | 时间 | 内容 | 谁做 | 产出 |
|------|------|------|------|------|

| **模板实现** | 第 5-7 天 | 5 个模板组件代码 | Claude | 5 个模板 Vue 组件 |

## 九、常见分歧预判

| 分歧 | 谁说了算 | 理由 |
|------|----------|------|
| 颜色用哪种红 | 颜色令牌（`#C41E3A` 不可改） | 已锁定在 COLOR_TOKENS.ts |
| 间距用 12px 还是 16px | `DESIGN_CONSTRAINTS.md` 允许范围内 | Pixso 设计建议优先，Claude 保证可实施 |
| 交互用点击还是长按 | `INTERACTION_RULES.md` 已定义 | Claude 出初版实现，Pixso 可挑战但需理由 |
| 信息密度高还是低 | 用户优先（老师用→高密度） | 产品决策，不由设计或开发单方决定 |
| 移动端断点设置在多少 px | Pixso 决定 | 设计专业领域 |
| 视觉还原度不达标 | Pixso 验收 | Pixso 有一票否决权（截图 vs 设计稿） |
| 某个视觉效果技术上很难实现 | Claude 判断 | Claude 给出替代方案，Pixso 确认可接受 |
| Props 接口需要加字段 | Claude 决定 | 代码架构责任 |
| 颜色令牌需要新增 | 双方同意 | Claude 在文件里加，Pixso 在设计中用 |

## 十、核心原则

```
Pixso = 视觉标准的制定者（出设计稿、出标注、做验收）
Claude = 代码标准的制定者 + 执行者（出 Props 定义、出约束文件、写代码）
Paico = 管理后台的设计者

Pixso 不出代码。
Claude 不做设计决策。
Paico 不管 C 端。

三者通过 COLOR_TOKENS.ts + DESIGN_CONSTRAINTS.md + COMPONENT_CATALOG.md + PIXSO_HANDOFF_TEMPLATE.md
四份文件实现无缝交接。
```
