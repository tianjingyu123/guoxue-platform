## 明天拿到新资源后的执行顺序

### 1. 只读预检

先上传固定包和校验文件，不解冻生产发布，不修改主机配置：

```bash
export PROJECT_DIR=/opt/guoxue/package-check
export ENV_FILE=/opt/guoxue/shared/.env.production
export DOMAIN=new.example.com
bash scripts/release/preflight-host.sh
```

预检失败时停止初始化；不得通过降低 CPU、内存、磁盘、时钟同步或包身份要求绕过。

### 2. 初始化与完整环境验收

按迁移手册完成 Docker、目录、证书、私有配置和监控初始化，随后执行完整环境检查。报告必须写入本次发布专属证据目录，不得包含密钥值。

### 3. 数据库恢复和对账

使用受控导出、SHA-256、目标库非空保护和恢复后逐表行数/业务完整性/序列校验。首次恢复前创建目标库快照；旧库至少保留 72 小时。回滚只恢复流量，不用旧库覆盖切流后新数据。

### 4. 固定包激活

生产包必须由干净工作树生成，发布标识在本地、归档、服务器目录、容器环境和健康报告中完全一致，提交 SHA 必须与发起任务的默认分支 GitHub 源提交一致。生产任务还必须用正式公网变量重建并审计 Admin、H5、微信小程序、App、Harmony 五端成品，并在服务器实际构建前通过客户端公开配置指纹复核；数据库迁移默认关闭，只有已评审并另行输入 `migrate:<release_id>` 确认值的迁移才允许显式启用。

### 5. 预览验收和演练

在 DNS 切流前通过受控 Host/预览入口完成：核心用户流程、支付退款、对象存储、WebSocket、监控告警、备份恢复、单节点摘除和版本回滚演练。

### 6. DNS 切流与最终证据

DNS 已指向新环境后，手动运行 GitHub Actions 的 `Verify Production Cutover`，输入与发布完全一致的 `release_id` 和确认值。该工作流只负责 SSH 调用固定发布包内的 `verify-production-cutover.sh`，GitHub 与人工应急不再维护两套命令。脚本会确认同一版本的最终数据库迁移核验证据和 `/opt/guoxue/shared/infrastructure-intake.json` 存在，在服务器刷新主机预检、新基础设施接入、客户端配置绑定、完整环境、公网运行时和版本保留报告；腾讯部署还会使用 CVM 实例角色只读审计监控、CLB、CDN 与证书。标准部署聚合九份证据，腾讯部署聚合十份证据。`launch-decision.json` 为 `GO` 后，还必须完成结构化 P0 双签并生成 `final-launch-decision.json`；只有最终判定为 `GO`，才允许把结论改为“正式上线”。

## 机器证据（标准九份 / 腾讯十份）

同一 `TARGET_RELEASE_ID` 的证据目录必须包含：

1. `host-preflight-readiness.json`：实际新服务器 CPU、内存、磁盘、inode、时钟、基础命令、Node、PostgreSQL 客户端、Docker、Compose、DNS、端口、环境文件权限与固定发布包身份的脱敏预检证据；
2. `infrastructure-intake-readiness.json`：新服务器、数据服务、域名、对象存储、责任人、恢复演练，以及源库/目标库/DNS 权限、迁移演练、停写窗口和旧环境回退保留的 `launch` 阶段验收；
3. `package-verification.json`：固定包本地/服务器验真；
4. `release-directory-verification.json`：已部署目录验真；
5. `client-config-binding-verification.json`：当前服务器公开客户端配置与 CI 审计输入的指纹、发布标识和源提交复核；
6. `database-migration-verification.json`：最终一致性快照、逐表计数与业务完整性对账；
7. `environment-readiness.json`：完整生产环境检查；
8. `runtime-verification.json`：公网真实实例、依赖和入口验收；
9. `retention-audit.json`：当前/前序/迁移版本保护和磁盘余量。

当且仅当 `deployTarget=tencent` 时还必须包含：

10. `tencent-cloud-readiness.json`：由目标 CVM 实例角色只读生成，绑定本次发布标识和生产环境中的目标地域、CLB、CDN 域名及证书域名；监控策略、CLB 监听器、目标 CDN 或证书任一查询失败、权限不足或资源为空都会阻断上线。

聚合命令：

```bash
node /opt/guoxue/current/scripts/release/aggregate-launch-evidence.mjs \
  --release-id "$TARGET_RELEASE_ID" \
  --evidence-dir "/opt/guoxue/release-evidence/$TARGET_RELEASE_ID" \
  --max-age-hours 24 \
  --report "/opt/guoxue/release-evidence/$TARGET_RELEASE_ID/launch-decision.json"
```

任一来源缺失、过期、版本不一致、允许降级、存在错误或磁盘余量不足，聚合器都会输出 `BLOCK` 并返回非零退出码。

机器聚合通过后，在同一目录执行 `finalize-launch-acceptance.mjs --init` 初始化 `production-cutover-acceptance.json`，由不同技术与业务负责人填写九项 P0 检查及对应归档证据，再运行该脚本生成 `final-launch-decision.json`。最终脚本会校验路径越界、符号链接、证据新鲜度、双人同名、缺项和逐文件 SHA-256；任何一项异常均输出 `BLOCK`。机器 `GO` 不能替代最终双签 `GO`。

`client-artifact-audit.json` 和固定包内的 `client-config-binding.json` 是客户端成品审计与指纹基线，必须与五端成品和变更单一并归档；主机预检生成的 `host-preflight-readiness.json`、数据库最终核验生成的 `database-migration-verification.json`、服务器从权限受控原始接入清单生成的 `infrastructure-intake-readiness.json`、重新生成的 `client-config-binding-verification.json`，以及腾讯部署的 `tencent-cloud-readiness.json` 均属于“现场运行可信链”。
