## 2. 上线架构边界

> 2026-08-21 更新：新系统首发已改为自研排盘。下述第三方链路只作为回滚预案保留，不再是默认首发链路。

首发阶段必须同时保留两条独立链路：

1. 新系统业务：新 App/H5/小程序 → `pre-api.rebugx.cn`（正式切换后再使用生产域名）→ CLB → 两台 CVM → PostgreSQL/Redis/COS。
2. 旧排盘回滚：仅在显式开启回滚开关时，新 App 的“工具”入口 → 新后端签发入口 → 第三方 `www.yrydai.com` H5。

排盘第三方的约 500 万用户、排盘记录、排盘支付和佣金仍留在排盘方，不进入本次旧通用系统数据迁移。两家第三方不能混为同一个数据源。

项目已增加 `PAIPAN_LEGACY_MODE`：

```dotenv
PAIPAN_LEGACY_MODE=false
PAIPAN_H5_BASE=https://www.yrydai.com/guoxueApp.php
```

默认关闭时直接使用自研排盘。仅在受控回滚期间临时启用后，移动端才向
`GET /api/v1/legacy-paipan/entry` 获取第三方签名地址并内嵌 H5。

已确认的第三方协议只有：

```text
mobile = 当前用户手机号
key = md5(mobile + "@rebuguoxue" + mobile)
go = tool
```

因此当前代码不会再调用不存在的 JSON 同步 API，也不会生成虚假的分站推广链接。

## 3. 仍必须向排盘第三方确认的最小事项

个人工具入口已经可以按现有协议接入，但“新注册用户如何归属某个分站”仍缺协议。必须只向排盘第三方索取以下最小信息：

1. 新用户首次打开排盘时，如何传入旧系统分站 ID/推广 ID；
2. 已有用户按手机号匹配后，是否保持原分站归属，是否会被新参数覆盖；
3. 分站推广链接中推荐 ID 的参数名、签名规则和有效期；
4. 新用户创建成功、匹配成功、失败时分别返回什么；
5. 测试手机号和测试分站，供上线前做“新建—归属—下单—佣金”闭环；
6. 小程序内嵌所需的业务域名校验文件或授权配合。

在这六项没有答复前：

- 既有用户可继续进入排盘；
- 已迁入的真实分站链接可继续保留；
- 不得承诺新用户的分站推荐奖励一定正确；
- 不得把自研分站关系直接当作排盘方佣金关系。

## 4. 旧通用系统最小迁移数据

第三方不需要交付完整数据库，只需导出下列逻辑数据，并保留稳定旧主键、订单号和 `updated_at`：

| 文件                      | 用途                                 | 即使零行也必须交表头 |
| ------------------------- | ------------------------------------ | -------------------- |
| `users.csv`               | 用户身份、手机号、昵称、状态         | 是                   |
| `wechat_auth.csv`         | `openid/unionid` 与用户关系          | 是                   |
| `members.csv`             | 会员级别、到期时间、购买凭据         | 是                   |
| `wallet_balances.csv`     | 截止时点余额                         | 是                   |
| `wallet_transactions.csv` | 余额变动流水和余额后值               | 是                   |
| `withdrawals.csv`         | 待审、处理中、已支付提现，防重复出款 | 是                   |
| `stations.csv`            | 站长、分站码、有效期、旧排盘推广链接 | 是                   |
| `orders.csv`              | 少量会员和课程订单、退款状态         | 是                   |
| `course_entitlements.csv` | 已购课程持续学习权益                 | 是                   |

规范化字段契约见 `config/migration/legacy-export-contract.json`。第三方原始 Excel 必须原样只读归档；转换后的导入文件使用 UTF-8 CSV：

- 手机号必须按文本导出，禁止科学计数法和丢失前导字符；
- 时间必须带时区，例如 `2026-07-30T18:00:00+08:00`；
- 金额统一为元、最多两位小数；
- 空表也要提供表头，不能用“没导这个文件”表达零数据；
- 每次全量/增量导出都要附表行数、导出截止时间和 SHA-256。

只读审计命令：

```bash
pnpm migration:audit-legacy-export <规范化CSV目录> --strict \
  --report artifacts/migration/<批次>-audit.json
```

该命令只检查列、主键、枚举、金额、时间、重复行和跨表关系，不写数据库。

## 5. 账号合并规则

迁移不能简单地“一行旧用户插一行新用户”，必须按以下优先级归并：

1. 已确认的同一 `unionid`；
2. 同一合法手机号；
3. 同一应用上下文中的 `openid`；
4. 都没有时保留为待认领账号，不允许按昵称合并。

注意：

- `openid` 只在对应微信 AppID 下稳定，不能跨不同 AppID 直接认定为同一人；
- 需要确认旧 App 微信登录所用的微信开放平台 AppID、主体及是否与小程序绑定到同一开放平台；
- 若拿不到旧密码哈希算法和参数，不迁移密码；手机号用户用短信登录/重置密码；
- 若短信服务尚未正式联调，不得先切断旧登录入口；
- 手机号写入新库时必须生成 `phoneHash` 和 `phoneEnc`，不能只落明文；
- 一名用户可能同时有手机号与微信认证，迁移后只能生成一个 `User`、多个 `Auth`。

## 6. 幂等、干跑和回滚

数据库已增加：

- `LegacyMigrationBatch`：记录批次、截止时间、源清单、状态和校验结果；
- `LegacyMigrationMap`：保存“旧系统实体 ID → 新系统 ID”映射及源行校验和。

迁移程序必须满足：

1. 同一源实体重复执行不产生第二条用户、余额、订单或权益；
2. 源行内容变化时报告差异，不静默覆盖资金字段；
3. 每个批次可查询新增/更新的目标记录；
4. 回滚只处理该批次创建的数据，不删除已被新系统继续使用的数据；
5. 资金、会员、提现、分站、课程权益全部先干跑，人工核对后再提交。

当前还没有真实导出样例，所以只完成了契约、审计和映射表；不能在未知列名下编写“猜字段”的正式导入器。

## 7. 推荐切换时序

### T-14 至 T-7：第一次全量干跑

1. 第三方导出全量数据和字段说明；
2. 原始文件只读归档并计算 SHA-256；
3. 转成规范化 CSV，执行契约审计；
4. 在隔离数据库导入；
5. 对账用户、会员、余额、流水、提现、分站和课程权益；
6. 抽样登录至少覆盖：纯手机号、纯微信、手机+微信、会员、站长、有余额、有课程用户。

### T-7 至 T-1：应用商店审核

1. 用原 Android 签名、原 iOS Bundle ID/Team、原 Harmony 签名生成正式包；
2. 三端先提交审核，不触发旧版强制更新；
3. 所有商店均审核通过后再确定统一切换时间；
4. 在发布前完成 COS、短信、微信登录、支付、IM/TRTC 真机联调；
5. 正式包必须访问新后端，不能残留第三方通用系统 API。

### T0：最终增量与切换

1. 至少冻结旧系统的注册、会员购买、余额、提现、课程购买写入；
2. 记录统一截止时间；
3. 导出 `updated_at > 上次截止时间` 的增量；
4. 先导入普通用户，再导入认证、会员、余额/流水/提现、分站、订单、课程权益；
5. 全量对账通过后启用新后端；
6. 发布各商店已审核版本；
7. 最后才修改旧版更新 JSON，开启强制升级。

如果第三方完全不能暂停写入，也不给增量导出，则无法保证余额、提现和订单“零丢失、零重复”。最低限度也必须暂停资金相关写入。

## 8. 旧版强制升级桥

旧版 App 把版本配置写死在：

```text
https://www.choofine.cn/liftera-service/api/v1/download/ver_rebu/json
```

当前线上 JSON 已核实为 Android `1.0.8/127`、iOS `1.0.5/128`、HarmonyOS `1.0.3/127`。旧版代码支持：

- `androidForce`
- `iosForce`
- `hmosForce`
- `androidShichang`
- `androidShichangurl`
- `appStoreUrl`
- `hmappStoreUrl`

安全顺序是：

1. 各商店的新版本 `1.1.0/200` 全部审核通过并可下载；
2. Android 使用一个由我们控制的 HTTPS 下载落地页，根据品牌跳对应应用商店，避免直接下发 APK；
3. 第三方更新 JSON 把三端版本提升到新版本，并开启对应强制标志；
4. 旧 JSON 端点至少保留 12 个月，最好长期保留为纯静态文件；
5. 新版 `1.1.0` 以后改用我们的 `/api/v1/system/version/check`，不再依赖第三方更新服务。

不能先关闭第三方服务器再指望强制升级。旧 App 访问不到写死的版本 JSON 时，我们自己的域名和新后端都无法补救。即使应用商店可能显示原生更新，也不等于所有旧用户会被强制升级。

## 9. 旧服务下线门槛

第三方通用业务 API 不能在商店发布当天立即关闭。建议同时满足：

- 新版本活跃设备升级率 ≥ 98%；
- 连续 14 天无迁移对账差异；
- 待处理提现为 0，或已逐笔移交并锁定幂等流水号；
- 旧版登录/升级失败率可接受；
- 客服已准备短信、公众号、应用商店更新引导；
- 旧数据完整备份、校验和和字段字典已交付；
- 仍保留旧版静态更新 JSON。

旧系统可先变为只读，再逐步关闭业务 API；域名不要直接回收或解析到无关服务。

## 10. 上线验收门槛

- Android/iOS/Harmony 真机覆盖安装旧版成功，用户本地登录态处理符合预期；
- 手机号和微信用户均能找回同一个新账号；
- 会员到期时间、余额、提现、分站和课程权益抽样 100% 一致；
- 第三方排盘既有用户可看原记录；
- 分站新用户推荐链路完成一次真实闭环；
- 两台应用服务器同时健康，单节点下线时 CLB 不影响用户；
- PostgreSQL 恢复演练、Redis 降级、COS 上传、CDN、防盗刷和告警完成；
- 新版强制更新地址和商店版本在正式切换前再次核验；
- 腾讯云临时调试密钥在应用商店提交前按约定轮换。

1. 腾讯云登录 MFA，用于滚动部署、COS 运行密钥、告警提交和故障切换；
2. Android/iOS/Harmony 原发布签名资料与真机；

5. 第三方确认长期保留版本 JSON，并补充排盘分站归属协议；
6. 微信小程序把第三方排盘域名配置为业务域名；
7. 应用商店审核全部通过后的统一强制升级确认。
