## 一、数据库本体优化

| 项 | 问题 | 处置 | 成效 |
|----|------|------|------|
| 统计失真（头号） | 全库 `analyze_count=0`，计划器用空统计裸奔（ClassicChapter 实 46.5万行却显示 0） | 全库 `VACUUM ANALYZE` | 统计全对齐 |
| 索引膨胀 | CircleKnowledge 12 行占 808MB（embedding 反复 update 未回收） | `VACUUM FULL` | **808MB→104KB** |
| 外键缺索引 | 18 个 FK 列无索引，join/级联全表扫描 | 补 18 个 `CREATE INDEX` | 已落库 |
| 冗余索引 | `ClassicChapter_title_trgm_idx` 103MB 且 0 scans，代码无章节标题搜索 | `DROP INDEX` | 回收 103MB |
| autovacuum 从不触发 | 开发期数据量未达默认阈值，统计长期陈旧 | 8 张高频表设表级 `scale_factor` | 防复发 |
| 金额用浮点 | `StationTeacherBooking.price` 等 3 列 `double precision` | 改 `numeric`，含代码 `Number()` 兼容 | 合规「金额用 DECIMAL」 |
| 僵尸表评估 | ToolRecord「32工具系统」5 表全空 | **深查后保留**（未实装规划表非垃圾，转产品决策） | 避免误删路线图 |
| 约束完整性 | 外键 222 个全有删除规则（健康）；CHECK 仅 8 个业务约束覆盖率低 | 补 5 个库存防负 CHECK（`db-opt-08`） | 防超卖脏数据 |

全程写库只走 `db execute --file`（SQL 留痕 `prisma/manual-sql/db-opt-0{1..7}-*.sql`），P0/P1 不停机，金额改造一次停机批次走完整启停闭环，最终 `schema-check 0 不一致`。

## 二、M4 敏感数据加密（手机号 + 生辰）

| 阶段 | 成果 | 验证 |
|------|------|------|
| 灰度双写 | `User` 加 `phoneHash`(HMAC@unique)/`phoneEnc`(密文)，5 处写入双写 | 回填 38 用户 0 失败，全唯一 |
| 切读 | 9 处 `where phone`→`phoneHash`（登录/注册/改手机/找回密码） | 真机回归：注册+密码登录+短信登录全 200 |
| Auth 表加密 | PHONE provider 的 openId/credential 改存 `phoneHmac`（4 处） | 真机回归：credential 落库 64hex hash，全表明文=0 |
| 生辰 | 3 条 `enc:AES-256\|明文生辰` 假加密（明文裸露）真加密化 | clientBirth 8 条全密文，明文残留 0 |
| 返回脱敏 | 评估 25 个 phone 返回点；后台真号接口鉴权核查 | ~14 处已 maskPhone；8 后台接口鉴权全到位 |

**结论**：手机号在 User 表、Auth 表、登录链路全部以 hash/密文存在，生辰已真加密。**加密存储核心目标 100% 达成**。返回脱敏无硬漏洞（C 端泄露他人号已被 maskPhone 覆盖，后台真号接口鉴权全到位），剩余为产品决策。

## 三、🔴 意外排雷：ENCRYPTION_KEY 定时炸弹

做 M4 时撞到的**预先存在、与本次无关**的隐患：根 .env 的 `ENCRYPTION_KEY` 被写成 **40 字节无效值**（`getKey()` 要求严格 32 字节），而 pm2 运行时进程内存是**有效 32 字节 key**——文件与进程不一致。一旦带 env 重启，全平台 `encrypt`（生辰/身份证/银行卡/bot密钥/M4）**全部 500**，靠"进程没重载"苟着。**已把运行时 32 字节 key 固化回根 .env**（备份 `.env.bak-20260629-keyfix`），回填脚本读新 .env 成功即验证拆除。

## 六、整体评价
数据库从「能跑」提升到「运行态健康」：拆掉了统计失真这颗随放量会引爆的雷，回收近 1GB 膨胀，补齐外键索引，规范了金额类型。敏感数据从「明文/假加密」提升到「存储层全加密 + 登录链路 hash 匹配」，并顺手拆掉了一颗会让全平台加密瘫痪的 ENCRYPTION_KEY 炸弹。剩余事项都是产品决策或远期收尾，无阻塞、无救火项。
