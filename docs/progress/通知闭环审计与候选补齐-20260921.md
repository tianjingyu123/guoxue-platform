## 通知矩阵

分类口径：已真实接入发送 = 候选代码已接入触发点，但仍未做真实线上发送；仅有设计或表结构 = 有模型、接口或任务入口但没有统一发送事实；仍缺真实触发入口 = 尚未找到可证明的最终状态触发器；线上状态未知 = 没有真实环境证据。

| 事件 | 站内通知 | 外部渠道 | 当前证据与结论 |
|---|---|---|---|
| 支付成功 | 已真实接入发送（候选代码、本地合成验证） | Webhook 外发箱；微信/小程序模板仅在配置模板 ID 时尝试；线上状态未知 | 原支付事务、权益后处理和 Webhook 已有；原先缺用户站内成功通知。候选用 `ORDER_PAID:<orderId>` 幂等。 |
| 权益到账/履约完成 | 未形成独立统一事件；部分课程/线下报名有提醒入口 | 未核实线上启用 | 支付后处理在事务内授予权益，但通知没有统一“授予成功”事实；不能用支付成功代替履约成功。 |
| 权益异常/人工/超期 | 任务、审计和日志入口存在，未见统一用户通知闭环 | 未核实 | 需产品定义超期 SLA、人工队列和用户可见文案后再补。 |
| 退款申请 | 售后状态和详情页存在 | 未核实 | 申请落库与站内通知未统一接通。 |
| 退款完成 | 已真实接入发送（候选代码、本地合成验证） | Webhook `ORDER_REFUNDED`；外部模板依配置；线上状态未知 | 退款 CAS 与权益冲正先完成，再通知；幂等键 `ORDER_REFUNDED:<orderId>`。 |
| 退款失败/关闭/异常 | 已真实接入发送（候选代码、本地合成验证） | 未核实 | 幂等键包含渠道终态，失败通知不宣称成功，并链接订单售后详情。 |
| 客服回复/反馈结果 | 客服与反馈后台入口存在 | 未核实 | 未发现统一“结案→用户可见状态→通知”事务；列为缺口。 |
| 课程开通/到期 | 课程/线下报名有 reminder 触点 | 未核实 | 课程开通没有统一事件；到期/直播提醒口径分散。 |
| 直播预约/开播 | 圈内 LIVE 分类能力存在 | 未核实 | 预约与开播触发器需业务核验。 |
| 圈子申请/审核/回复/管理结果 | 圈内 `INTERACT/TRADE/GOVERN/LIVE` 分类和治理通知已存在 | WebSocket/推送入口存在，线上状态未知 | 代码入口较完整；仍需真实环境验收点击目标和关闭偏好。 |

## 关键审计结论

- `Notification` 目前只有用户、类型、正文、目标和已读字段；没有持久化业务幂等键、发送尝试、失败原因或重试状态。候选实现先复用 Redis 幂等键，TTL 30 天；这能防重复回调重复建站内通知，但 Redis 丢失后无法靠数据库追溯，属于发布前仍需决定的增强项。
- `send()` 会先落站内通知，再按偏好尝试推送；推送失败只记录日志，用户仍可在站内查看。外部渠道未配置模板 ID 时不会发送，不能宣称短信、微信或 App 推送已启用。
- 用户详情读取按 `id + userId` 查询，点击目标由客户端按 `targetType/targetId` 跳转；服务端未对目标资源做统一二次授权。订单、售后等页面必须继续使用各自资源权限校验，不能把通知 ID 当访问凭证。
- 候选支付通知只在 `ORDER_PAID` 外发箱成功后触发，避免业务失败时发送成功文案；退款通知只在退款 CAS/权益冲正完成后触发。通知异常不会回滚已经完成的资金事务，日志仍需进入运维待办。
- 通知内容仅含“已支付/退款已完成/退款未完成”和订单目标，不含金额、支付流水、手机号等不必要个人或支付信息。

## 实际代码改动

- `notification.dto.ts`：增加可选 `idempotencyKey` 字段，作为事件语义记录。
- `notification.service.ts`：增加 `sendOnce()`，以 `userId + 业务键` 使用 Redis `SET NX`，成功落库后保留，落库失败释放以便重试。
- `shop-payment.service.ts`：支付最终 Webhook 成功后补“支付成功”站内通知；通知写入失败只记日志，不改变支付结果。
- `shop-refund.service.ts`：退款最终成功后补“退款完成”；微信退款 `FAIL/CLOSED/ABNORMAL` 回调补“退款未完成”。
- `shop.module.ts`：接入现有 `NotificationModule`，未引入 Novu。

## Novu 评估

结论：**复用现有能力并小范围补齐，不引入 Novu**。

Novu 官方仓库近期仍有版本发布，支持工作流、多渠道和自托管；官方自托管文档要求 Docker Compose、API、worker、web 等组件，云版按 workflow runs 分级计费。参考：[Novu Releases](https://github.com/novuhq/novu/releases)、[自托管部署文档](https://github.com/novuhq/novu/blob/next/docs/community/self-hosting-novu/deploy-with-docker.mdx)、[官方价格](https://novu.co/pricing)。当前平台已有 Notification、Redis、Webhook 外发箱、微信模板和圈内分类；引入会增加迁移、运维、渠道费用与数据边界，现阶段收益不足。若未来要支持多租户工作流、短信/邮件/WhatsApp 等编排，再单独立项比较许可证、供应商费用和迁移成本。

## 主线接收顺序与撤回

1. 先在隔离环境复用本次依赖恢复方式运行通知、支付、退款单测；再补专门的支付/退款通知集成测试，确认支付失败和权益事务失败不会产生成功通知。
2. 评审通过后按提交顺序接收 `notification` → `shop-payment` → `shop-refund` → `shop.module`；任何一步失败可按提交逆序 `git revert`，不触碰订单、余额、权益或生产数据。
3. 接收后先做本地合成回归，再由业务和环境负责人决定是否配置真实模板、CORS/微信域名和线上开关。
