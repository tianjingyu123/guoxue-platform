## 二、本轮审计发现(实证)

- **库结构**:272 表 / 968 索引(执行优化前)/ 缓存命中率 **98.46%** / pg_stat_statements、pg_trgm 已装、无 pgvector。

## 三、本轮已执行优化(写库留痕 `prisma/manual-sql/`)

### ✅ db-opt-10 清理冗余索引
删除 15 个被唯一约束覆盖的重复普通索引(User_phone_idx、Station_code_idx、HuifuSplitRecord_orderId/outTradeNo_idx、Tenant_apiKey_idx、BigScreenToken_token_idx、ReferralLink/CircleInviteCode/CompetitionInviteCode_code_idx、CompetitionInvitation_inviteCode_idx、OrderLogistics_orderId_idx、VirtualCoinRecharge_orderNo_idx、UserKnowledgeProfile_userId_idx、CheckIn_userId_checkInDate_idx、ToolShare_shareToken_idx)。
**收益**:写入路径少维护 15 个索引、回收空间。复查 `remaining_redundant=0`。

### ✅ db-opt-11 TOAST 压缩 lz4(增量)
- 对照实验(content 列 3 万行采样):lz4 vs pglz = **305MB vs 326MB**,lz4 省 6.4% 且解压快 2-3x。
- 决策:`SET COMPRESSION lz4`(ClassicChapter 5 个文本列)+ 库级 `default_toast_compression=lz4` → 未来新增章节自动受益(零锁,利好古籍索引 task 批量插入)。
- **存量 3GB 全表重写未做**:收益仅 ~190MB,不抵停机 + 2x 磁盘风险 → 文末留可选 SQL。

### ✅ db-opt-12 参数调优(库级,owner 权限)
`ALTER DATABASE guoxue SET`(对新连接持久生效):
- `work_mem` 8MB→**32MB**(排序/哈希不落盘)
- `maintenance_work_mem` 128MB→**512MB**(VACUUM/建索引加速)
- `effective_cache_size` 512MB→**16GB**(planner 倾向走索引)
- random_page_cost 已 1.1(SSD 合理)保持。
> ⚠️ 已建连接(pm2 后端连接池)需重连/重启 pm2 才用上新值。

## 七、铁律备忘(承接第一轮)
1. 写库只用 `prisma db execute --file`;**ALTER SYSTEM / VACUUM / CREATE INDEX CONCURRENTLY 不能在事务块** → db execute 会包事务报错,需 superuser 单条或改 conf。
2. `ALTER DATABASE ... SET` 可在事务块、库 owner 权限、对新连接持久 → 这是非 superuser 调 user-context 参数的正路。
3. 改数据/删对象前先查根因语义(冗余索引经 pg_index 精确比对确认覆盖关系才删)。
4. mcp postgres 只读核对;`guoxue` 非 superuser(ALTER SYSTEM / pg_reload_conf 无权;**但 pg_stat_statements_reset 有权**)。
5. partial / 表达式索引 Prisma schema 无法表达 → 只在 DB 层维护,schema 仍声明全列,因禁 db push 不会被重建。

### ✅ db-opt-13 软删除索引 partial 化(已执行)
`ClassicChapter_deletedAt_idx`(3168kB→**8KB**)、`ClassicBook_deletedAt_idx`(136kB→**8KB**):46.5万行 deletedAt 全 NULL(0 软删),全列索引海量 NULL 几乎无用。改 `WHERE deletedAt IS NOT NULL` partial → 省 ~3.3MB + 减少大表写入维护(利好古籍索引 task 批量插入),查"已删"仍走索引,功能不变。

### 📋 生产放量前 checklist(触发条件式,届时按需执行)
1. **时序表分区**:AuditLog / TrackEvent / AiAnalysisRecord 等 append-only 表,当行数破百万或查询变慢 → 按月 RANGE 分区 + 老分区归档/冷存。
2. **全文检索 trgm 索引**:若某张被 `content contains` 搜的表涨过 ~5 万行且无前置过滤、搜索成热点 → 加 `gin (col gin_trgm_ops)`(pg_trgm 已装);中文长正文搜索建议上 zhparser/pg_jieba 分词 + tsvector。
3. **shared_buffers 再调**:放量后据缓存命中率(<99% 且磁盘读高)在 Windows 上谨慎上调(当前 1GB)。
4. **连接池**:`DATABASE_URL` 未配 `connection_limit`(Prisma 默认 ~25),多实例部署时按 `max_connections=100` 与实例数分配,必要时上 PgBouncer。
5. **统计目标**:多表 join 估算失真时对相关高基数列 `ALTER TABLE … SET STATISTICS 500` + ANALYZE。
6. **基线观察**:已挂 Windows 计划任务 `GuoxueDBBaseline` 每日采集 pg_stat_statements 到 `db-baseline-log.md`,真实负载积累后据此定位新热点。
