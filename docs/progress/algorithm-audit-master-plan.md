# 全算法系统性排查方案

## 一、排查方法论

### 三层交叉检验框架
```
第一层：算法溯源 → 经典古籍/权威教材对照
第二层：多源交叉 → 3+独立数据源比对验证
第三层：竞品对照 → 主流产品(问真/热卜/其他)结果比对
```

### 校验优先级
1. **数学/天文正确性**（日柱、节气、闰月等基于公历数学的部分）→ 必须100%准确
2. **流派规则正确性**（起运排法、用神取法、神煞规则）→ 默认取主流，分歧做多版本
3. **数据表完整性**（64卦、72局、神煞表等）→ 逐条交叉验证
4. **边界条件处理**（跨年、跨月、早晚子时、节气交界）→ 逐一测试

### 分歧算法处理策略
- 默认算法 = 应用最广泛、最权威、最被公众认可的版本
- 备选算法 = 作为排盘工具的"流派"选项供用户选择
- 每个分歧点标注：争议来源、各版本依据、平台默认选择理由

## 三、通用问题模式（需全局修复）

### 问题1: 日柱计算使用 Date.getTime()
**影响范围**: 奇门、六爻、大六壬、万年历
**风险**: 时区不一致导致日柱偏移1天
**修复方案**: 统一使用 bazi-engine 的 pure math `calcRiZhu()` 或复用 `daysSince1900()`

### 问题2: 节气计算使用近似日期表
**影响范围**: 奇门、大六壬、万年历
**风险**: ±2天误差，导致用局/月将错误
**修复方案**: 统一使用 bazi-engine 的 Meeus 天文算法

### 问题3: 三元日判断基于特定基准日
**影响范围**: 奇门
**风险**: 基准日若不对则所有三元判断错误
**修复方案**: 从日柱60甲子序号推导三元(甲子旬=上元)

### 问题4: 64卦/72局等静态数据表无交叉验证
**影响范围**: 六爻、梅花、奇门、山向奇门
**风险**: 数据录入错误
**修复方案**: 从经典权威来源重新生成数据表
