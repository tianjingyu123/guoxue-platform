# 旧排盘独立支付接入（v239 本地候选，未发版）

## 用户确认的业务边界

- 用户进入排盘板块后，Android 与 iOS 均沿用旧排盘支付体系。
- 旧系统继续负责旧订单、旧商户收款、退款和旧会员/工具权益。
- 新 App 只适配旧页面与原生微信 SDK 之间的调用和返回，不创建新商城订单，不将旧会员转换为新会员，不用新商城代收。
- 本次旧排盘支付不接 Apple IAP；新系统已有的 Apple 支付逻辑保持独立不变。
- 以上是技术与业务分界，不等于 App Store 支付审核已通过。正式分发门禁须单独核定，不做隐藏功能、审核差异或伪装微信浏览器的处理。

## 已确认的旧协议与当前实现

旧版 1.0.8 App 的 `user/pages/h5/h5View.js` 明确接收 `action=pay` 与 `payload.trade_no`，访问固定接口 `https://www.rebu.net.cn/app/getTrade.php`，参数为 `app=guoxue` 与旧交易号，然后以 `provider=wxpay` 调用原生微信支付。

本地候选恢复上述流程：

1. 仅当前可见、受信旧排盘子页面可触发 `payWX`、iOS `webkit.messageHandlers.payWX` 或 `webUni` 支付消息。
2. 网页只交付合法交易号，不能指定商户、金额、支付地址或签名。新系统令牌不发送给旧接口。
3. 先确认 App 含微信支付模块，再从固定旧服务端读取签名参数。只接受完整白名单字段与匹配的应用标识，不从网页拼接支付参数。
4. iOS 与 Android 都调同一原生微信通道；不再降级到要求微信内打开的 `/my.php?mod=pay` 网页。
5. 同一时刻只允许一个支付尝试；页面已变更时不继续拉起微信。SDK 没有终态时不自动重试付款。
6. SDK 返回后只请求原旧页面 `resumeUpdate()`，缺失或同步异常时重新载入原旧页。不会调用 `payOk()` 假定到账，也不直接修改会员状态。最终结果仍由旧服务端确认。
7. 支付回调早于 App 恢复时仅在内存等候；切换子窗口、同 URL 重载或离开原页面后，迟到结果不注入新页面。

## 正式收款前必须补齐的证据

- 旧接口当前可用、交易号归属校验、商户/AppID/签名包绑定正确；只有历史 APK 协议证据不能替代现场验真。
- 新签名包在 iPhone 与 Android 分别完成：调起微信、取消返回、弱网/超时、重复点击、App 后台恢复。
- 受控交易完成后在旧系统核对订单、旧会员/工具权益；退款后的旧权益处理由旧系统承担并核验，不迁入新系统。
- 微信 SDK 的 `success` 和页面刷新均不作为到账证明。
- App Store 分发审核要求独立保留；未经相应授权不发起真实交易、商店审核或公开发布。
