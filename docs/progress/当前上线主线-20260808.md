# 当前上线主线（2026-08-08）

> 本文件自 2026-08-08 起作为上线工作的唯一当前执行主线。更早的进度、迁移、基础设施采购和发布证据文档只用于追溯，不再直接决定当前任务优先级。

## 一、已确认的范围边界

1. 轻量服务器仅用于开发调试，其中全部为测试数据；不迁移其业务测试数据。
2. 从轻量服务器迁移的对象仅包括：已验证代码、运行配置、第三方集成配置、已完成智能体定义及其必要知识资源。
3. 新服务器、新数据库和新域名作为待上线正式环境，从干净数据库基线开始初始化。
4. 古籍由独立本地流程完成版权、标点和规范整理；上线前只接收通过验收的最终导入包，不在本主线重复建设古籍加工流水线。
5. 正式数据迁移仅针对第三方旧平台中的真实用户、必要身份映射、少量未完成交易和继续运营所需的关键数据；历史数据按成本尽力迁移，允许非关键记录不完整。
6. 第三方旧平台在新系统完成迁移、切流和稳定观察前保持可回退；确认新系统持续正常后再关停。

## 二、上线主线

### 阶段 1：新正式环境功能基线

目标：现有系统在新服务器、新数据库和新域名上达到与轻量服务器调试环境一致的功能状态。

- [ ] 最终代码基线提交、合并并冻结，工作树保持干净。
- [ ] 新数据库执行正式 Prisma migration，以空库/必要基础种子启动。
- [ ] 新域名完成 DNS、TLS、Cookie、CORS、WebSocket 和静态资源配置。
- [ ] H5、管理后台、API、定时任务、队列、缓存和对象存储正常。
- [ ] 备份、健康检查、日志、监控和可回退版本可用。

完成标准：新环境核心健康检查全部通过，主要用户流程可在新域名完成，且不依赖轻量服务器测试数据。

### 阶段 2：第三方集成与智能体迁移

目标：所有上线范围内的外部能力在新环境真实可用。

- [ ] 微信登录、小程序合法域名和微信支付回调。
- [ ] 汇付下单、支付确认、退款和回调验签。
- [ ] 腾讯云 COS/CDN、内容审核、VOD/直播、ASR/TTS/TRTC（按首发范围启用）。
- [ ] AI Gateway、模型供应商和流式回复。
- [ ] 短信、邮件、快递100及回调验签。
- [ ] 导出并导入轻量服务器上已完成的智能体定义、提示词、模型配置和必要知识资源。
- [ ] 每项集成至少完成一次无副作用探测；支付、退款、短信等完成受控小额/测试闭环。

完成标准：第三方依赖健康、回调和关键业务闭环通过；未纳入首发的能力明确关闭开关，不以残缺配置上线。

### 阶段 3：官方内容与首发数据

目标：用户进入平台后能够理解定位、规则和主要功能，并有足够内容可浏览和体验。

- [ ] 建立官方账号、官方圈子和统一品牌身份。
- [ ] 补充覆盖主要场景的官方智能体，并完成逐个对话验收。
- [ ] 导入通过版权、标点、结构和质量验收的古籍成品。
- [ ] 发布平台定位、功能规则、用户操作指引、常见问题等官方文章。
- [ ] 发布对应的短视频、直播预告/回放和功能演示内容。
- [ ] 检查推荐流、搜索、分类、详情页、分享和举报审核链路。

完成标准：首屏、推荐、搜索和各主要板块不存在明显空场；官方内容能够引导新用户完成核心操作。

### 阶段 4：客户端正式发布与软上线

目标：H5、小程序和 App 使用同一正式后端，完成渠道侧验收。

- [ ] 使用正式域名和生产公开变量重新构建所有客户端。
- [ ] H5 完成多端浏览器和支付回跳测试。
- [ ] 小程序完成合法域名、隐私协议、支付、审核和真机测试。
- [ ] App 完成正式签名、原生插件、升级覆盖和商店材料检查。
- [ ] 先进行受控软上线，不立即导入全部旧用户或关闭旧系统。

完成标准：各客户端可安装/访问，登录、浏览、下单、支付、退款、消息和分享等首发主流程正常。

### 阶段 5：第三方旧平台真实用户迁移

目标：在不拖延新系统替换旧系统的前提下，优先保证真实用户能够进入新系统，并尽量保持关键身份与未完成业务连续。数据完整度低于功能完整度和系统健康度优先级。

- [ ] 先确定最低必迁集合：可识别用户、手机号/第三方身份绑定、少量未完成交易及经业务确认必须连续的权益。
- [ ] 建立旧用户 ID 到新用户 ID 的稳定映射和幂等导入规则。
- [ ] 先做脱敏样本演练，再做可承受范围内的全量预演和关键数量/金额对账。
- [ ] 设计旧密码不可迁时的首次登录、短信验证或重置方案。
- [ ] 在正式窗口执行关键数据导入；历史数据迁移失败时记录缺口并转人工补偿，不因少量非关键历史缺失长期阻塞新系统切换。
- [ ] 抽样验证老用户登录、身份、权益和关键历史数据。

完成标准：新系统功能和运行健康不受旧平台数据限制；重点旧用户可识别并能继续使用，少量未完成交易和关键权益有处理结果。非关键历史数据可在切换后继续补录或归档查询。

### 阶段 6：正式切流、观察与旧系统关停

- [ ] 正式公开流量切换到新系统。
- [ ] 持续观察登录、支付、退款、回调、AI、内容、消息和性能指标。
- [ ] 在约定观察期内保留旧系统只读和回退能力。
- [ ] 无 P0/P1 问题且业务负责人确认后，停止第三方旧系统写入并归档备份。
- [ ] 完成旧系统关停和相关第三方资源清理。

## 三、停止投入的非必要工作

- 不迁移轻量服务器中的测试用户、测试订单、测试内容和测试文件。
- 不为测试数据制作生产级全量迁移、长期双写或复杂对象存储对账。
- 不为第三方旧平台数量很少的非关键历史数据建设高成本长期双写或追求绝对全量一致；无法经济迁移的记录形成缺口清单后人工处理。
- 不在古籍加工已由独立流程负责的情况下重复建设同类流水线。
- 不把与首发范围无关的远期能力、商店渠道或外部 SDK 强行作为当前环境迁移阻塞项；应通过功能开关明确延后。
- 不用大量报告替代真实功能验收；发布证据只保留可恢复、可核验和合规所必需的部分。

## 四、不能省略的上线底线

1. 正式数据库 migration、发布前备份和可验证回滚。
2. 登录、支付、退款、第三方回调和用户权益的真实闭环。
3. 正式域名、TLS、Cookie、CORS、WebSocket 和客户端合法域名。
4. 密钥不入库，生产配置与客户端公开配置严格分离。
5. 旧平台迁移必须优先保证账号识别、关键权益和少量未完成交易；非关键历史允许缺失，但缺口必须可追踪并有人工处理口径。
6. 新系统稳定运行并完成业务确认前不得关停旧平台。
