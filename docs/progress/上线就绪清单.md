# 上线就绪清单（Deployment Readiness Checklist）

> 生成于 2026-06-25。目标：把散落在 38 个里程碑里的「本地待部署 / 待配置 / 待验证」项归集成一份**可执行的部署手册**，让项目达到「真实环境/密钥/数据一接入就能上线」的状态。
> 权威进度仍看 `进度跟踪-实时更新.md`；本文件是**上线操作纲领**，按 P0（阻断上线）→ P1（影响功能完整）→ P2（打磨）排序。

---

## 〇、先校正一个认知

这个后端是**写好的真后端**（76 模块 / 1560 接口 / 248 表），绝大多数页面对接的 API **已经存在**。所以「等 API 接进来」准确说是三件事：

1. **部署**——所有改动都在本地开发库（靠 `prisma db push` + 原生 SQL 脚本维持），全新生产库需正式 migrate，且有几张表/列**只在 db push 存在、无 migration 也无脚本**。
2. **真实环境配置**——支付回调 / TRTC 音视频 / 直播推流需真实商户号/密钥，本地起不来。
3. **剩余 mock 比里程碑宣称的多**——除已真连的 C 端主链路 + 圈子 + 主播端，**商家后台、线下驿站、视频创作者中心、排盘结果计算、IM、钱包充值提现**等仍是死数据（详见第五节，这是距离上线的最大工作量）。

**推荐做法（二选一）：**
- **A（推荐）**：开发库 schema 已是最终态，跑 `npx prisma migrate dev --name deploy_pending_models` 生成一份覆盖全部 11 model + needApproval 的正式 migration，再 `migrate deploy` 到生产。**生成前先解决 1.2 的 drift**（否则 migrate dev 会要 drop）。
- **B（保守）**：生产 migrate deploy 后，按序手动跑 `scripts/` 下 5 个建表脚本 + **为 LiveReview/LiveTeamMember 手写 DDL**（参照 schema.prisma:1183/1198）。

### 1.2 必须处理的 prisma drift（3 类）

1. **Content.deletedAt 等软删列漂移**：`schema.prisma` 有 11+ 处 `deletedAt`（Content:539、Circle:351 等），但 `manual_20260623_audit_fixes` 只补了 `User.deletedAt`。**生产 migrate deploy 后除 User 外的 deletedAt 列会缺 → 任何 Content 全列 findMany 触发 `P2022 column does not exist`（500）**。里程碑35 A组就因此踩坑（用显式 select 规避）。→ 正式 migration 需包含这些列。
2. **`_quality_snapshot` 表**：由 `scripts/data-quality-monitor.sql` 创建，不在 schema.prisma。`migrate dev/diff` 会判定为漂移要求 DROP。→ **migration 中排除它**（独立管理），别误删。
3. **CircleKnowledge 复合唯一约束**：`schema.prisma:4342 @@unique([contentHash, circleId])`，业务代码 `circle-knowledge.service.ts:42/178` 按 `contentHash_circleId` 访问，但**无任何 migration 建立此约束**（只靠 db push）。→ 确认生产库存在该复合唯一约束，否则 RAG 知识入库 `ON CONFLICT` 失败。

> 另：`prisma/migrations/manual_20260623_audit_fixes/migration.sql` 是手写 migration（需 `psql -f` 执行）：User.deletedAt + 2 索引。确认已应用。

## 二、【P0】功能开关（FeatureFlag）

**机制**：`@RequireFeature("key")` + `FeatureFlagGuard`，DB 查不到该 key 或 `enabled=false` → **HTTP 404（刻意隐藏）**。带 Redis 30s 缓存。

**⚠️ 关键**：seed.ts 预置的 24 个开关用的是另一套命名（`live_streaming`/`shop_feature` 等，无人 `@RequireFeature` 引用）。而**真正守卫端点的 9 个 key，除 merchant_onboarding 外都不在 seed** → 全新库只跑 seed 会让这些功能全 404：

| 开关 key | 守卫的功能 | 上线动作 |
|---|---|---|
| `content_publish` | 圈子图文/文章发布 | `scripts/enable-publish-features.ts` 已含 |
| `course_publish` | 课程发布 | 同上脚本已含 |
| `shop_checkout` | 商城下单结算 | **需手动 upsert enabled=true** |
| `live_start` | 开播 | 需手动 |
| `member_purchase` | 会员购买 | 需手动 |
| `commission_withdrawal` | 分销佣金提现 | 需手动 |
| `risk_fraud_scan` | 风控扫描（3端点） | 按需 |
| `recommend_algorithm` | 推荐算法（3端点） | 按需 |
| `merchant_onboarding` | 商家入驻 | seed 有但 enabled=false，需开 |

**上线动作**：生产 `FeatureFlag` 表为需开放的 key 写 `enabled=true, percentage=100`。管理 API：`feature-flag.controller.ts`（upsert/list/delete）。建议扩展 `enable-publish-features.ts` 把要开的 key 一次性 upsert。

## 四、【P1】资金代码 review + e2e（上线前必做）

**总体良好**：核心扣费链路（入圈/续费/通话预扣/付费提问/打赏/悬赏冻结）事务边界已达标（spend 传入 tx，钱货同事务）；提现金额校验（`@IsPositive @Max(50000)` + Redis 锁 + 余额复核）达标。

**代码内已标 ⚠️ 的 e2e 点**：
- `circle-refund.service.ts:195` executeRefund —「上线前须人工 review + 真实付费数据 e2e」
- `consult-call.service.ts:15` —「端到端结算未做 e2e」
- `huifu.dto.ts:7` — pay_type 字符串需按汇付商户文档核对

**需人工确认的可疑点（agent 抽查发现）**：
1. **`circle.service.ts:1516` rewardPost 打赏帖子**：扣了付款方币，但**收款方（帖子作者）无任何 revenue.record 入账** → 疑似打赏只进平台不分作者。需确认产品预期。
2. **退款/通话分账的异步补偿缺失**：`executeRefund` 的 `reverseCommission` 和 `consult-call.end` 的 `revenue.record` 都在主事务外 fire-and-forget，**失败仅 logger.warn，无补偿重试任务**。主操作成功但分账/冲正失败时会账目不一致。需补偿落点。
3. **两套钱包体系**：退款入账写 `UserWallet`（原生 SQL 表），而 `wallet.service` 可提现额来自 `UserEarning`。退款到账的钱能否被提现/消费需 e2e。
4. **`question.service.ts:114/192` 退款裸调 coin.refund**：靠状态机防重复，无显式幂等锁，并发场景需确认。

> circle-refund + consult-call 大量 `$executeRawUnsafe` 直写资金表（绕 Prisma 校验），是 e2e + 上线 review 重点。

## 五、【P1】剩余 mock 代码就绪化（距离上线的最大工作量）

**两种形态**：① data 层 `if(true) return mock` 短路（**287 处 / 39 文件**，页面 import 了 xxxApi 但 api 内部返回死数据）；② 页面直接 import mock 数组（违反铁律，连 api 通道都没接，更顽固）。

### 5.1 整包页面级 mock（重灾区，需先把页面切到 api 层）
- **pkg-merchant 商家后台（~14 页）**：dashboard/orders/order-detail/revenue/products/product-edit/analytics/reviews/profile/shop-preview/content-stats/inquiries/circle-bindding/notices —— 多数**没调用 merchantApi**，直接 import mock。★订单/订单详情/收益是核心。
- **pkg-offline 线下驿站（6 页）**：courses/stations/station-detail/course-detail/teacher-booking/checkin —— 直 import mock 数组/mock 函数，未接 offlineApi。★报名/签到核心。
- **pkg-video/creator 创作者中心（5 页）**：creator/withdraw/sales/analytics/earnings-history —— 直 import mock，未接 creatorApi。★收益/提现核心。

### 5.2 核心路径仍是死数据
- **视频**：`pkg-video/detail`→`mockVideos`（播放/详情）、`pkg-video/search`→死数据
- **排盘结果**：bazi/liuyao/ziwei/qimen/yangpan 的 `calculate` 全部 data 层短路；`pkg-paipan/ziwei/result`→直读 `ziweiData` 常量。★★排盘是平台核心卖点
- **直播观看间**：getWatchRoom/getVerticalRoom/getHorizontalRoom（实时，需 LIVING 直播+IM，真机批次）
- **IM**：sendMessage/会话/群聊 15 处短路
- **钱包**：mine-data 的 recharge 充值 / withdraw 提现短路
- **电子书/课程播放**：ebook checkoutInfo/readerChapter、course getPlayerContent/getPurchaseCourse 短路

### 5.3 已基本真连（残留极少，✅）
圈子主体（circle-data/detail/growth/refund/consult/manage）、商城 mall/shop 消费页、课程消费页、poetry/classics 主体、home 首页、discover、auth。

### 5.4 建议改造顺序（按用户价值 × 后端就绪度）
1. **排盘结果 calculate**（★★核心卖点，先确认后端 paipan 算法端点是否就绪）
2. **视频播放/详情**（mockVideos → videoApi）
3. **商家后台三页**（orders/order-detail/revenue，先确认 merchant 后端端点）
4. **线下驿站报名/详情**（确认 offline 后端）
5. **创作者中心收益/提现**（确认 creator 后端）
6. 其余按需

> 每个模块改造前先核对后端是否有对应端点（用 `grep '@Controller'` + 读 controller），有则真连+三态+降级+防重复，无则补 BFF 或诚实降级。**直播观看间实时页留真机批次**。

## 七、推荐上线执行顺序

1. **预发环境** 用生产快照库演练 migrate：先解决 1.2 drift（Content.deletedAt 补列 / 排除 _quality_snapshot / 确认 CircleKnowledge 约束）→ 生成覆盖 11 model 的正式 migration（含 LiveReview/LiveTeamMember）→ migrate deploy。

3. 跑 enable-publish-features + 手动开 shop_checkout 等需要的功能开关。
4. 第四节资金 e2e：用真实小额订单跑通 圈子付费/通话/退款 全链路，确认分账+补偿。
5. 按需跑演示数据脚本。
6. 剩余 mock（第五节）按 5.4 顺序持续真实化——**这部分可与上线并行推进**（已真连模块先上，未真连模块灰度/隐藏入口）。
