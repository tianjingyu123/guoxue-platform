# M4 敏感数据加密改造方案（2026-06-29 立项）

> 来源：数据库优化审计 M4。手机号/生辰明文存储，违反《个人信息保护法》对敏感个人信息「加密存储」要求。
> 性质：架构级改造，影响注册/登录/改手机/存量回填/返回脱敏——**资金账号级逻辑，须单独立项、评审后执行**。本文件是设计，未动代码。

## 一、现状

- `User.phone` = `text` **明文**（抽样 `1390xxxxxxx`）；`PaipanRecord.clientName` 及生辰字段明文。
- 项目**已有加密工具** `src/common/crypto.util.ts`：
  - `encrypt(plaintext)` / `decrypt(ciphertext)`：AES-256，**随机 IV**（`encrypt("test")` 两次结果不同，spec 已验证）。
  - `maskPhone(phone)`：脱敏掩码（如 `139****0000`）。
- **问题**：`maskPhone` 目前只用于**返回值脱敏**，存储仍是明文；且 `encrypt` 随机 IV **无法做等值查询**（同明文→不同密文，`WHERE phone = encrypt(x)` 失效）。

## 二、核心难点

手机号既是**敏感数据**（要加密）又是**账号标识**（注册去重、登录匹配、改手机查重都要按它精确等值查询）。随机 IV 加密与等值查询互斥 → 不能单列加密了事。

## 三、推荐方案：`phoneHash` + `phoneEnc` 双列

| 列 | 算法 | 用途 | 约束 |
|----|------|------|------|
| `phoneHash` | **HMAC-SHA256**(phone, KEY)，确定性（同明文→同哈希） | 注册去重、登录匹配、改手机查重——所有**等值查询**走它 | `@unique`，建索引 |
| `phoneEnc` | 现有 `encrypt()`（AES 随机 IV） | 存密文，展示时 `decrypt()` + `maskPhone()` | 无需索引 |

- 原 `phone` 明文列：迁移期保留（回填用），切换完成后**最终删除**。
- 生辰：`PaipanRecord.clientName`/生辰字段**只需 `encrypt`**（不按生辰等值查询，无需 hash），展示时 `decrypt`。
- KEY 复用根 `.env` 的 `ENCRYPTION_KEY`；HMAC 可另用 `PHONE_HMAC_KEY`（与加密 key 分离更安全）。

## 四、改造点清单（执行时逐项落地）

1. `crypto.util.ts` 新增 `phoneHmac(phone): string`（HMAC-SHA256）。
2. schema：`User` 加 `phoneHash String? @unique`、`phoneEnc String?`（迁移期与 phone 并存，故可空）。
3. **写入路径**：注册（`auth` 模块 `PhoneRegisterDto` 流程）写入时同时算 `phoneHash`+`phoneEnc`；改手机 `account.service.ts:93` 同步。
4. **查询路径**：全量 `grep 'where: { phone'` 改为 `where: { phoneHash: phoneHmac(x) }`——已知点：`account.service.ts:88`（改手机查重）、`auth` 登录（password/sms）、任何按 phone 的 findUnique/findFirst。
5. **返回路径**：所有返回 `phone` 的接口改为 `maskPhone(decrypt(phoneEnc))`，禁止裸返回。
6. 生辰：`PaipanRecord` 写入 `encrypt`、读取 `decrypt`。

### 4.5 已 grep 定位的全部改造点（执行清单）
**新发现：phone 不止在 `User.phone`，还明文写进 `Auth.openId` / `Auth.credential`**（sms/wechat 登录，`auth.service.ts:157/470/478/480`）——加密范围必须覆盖 Auth 表，否则 phone 仍明文泄漏。

- 写入（需双写 phoneHash+phoneEnc）：`auth.service.ts` `phoneRegister`(76/85)、`smsLogin`(149/156/157/162)、`wechatPhone`(312/337)、`bindPhone`(464/470/478/480/482)、`account.service.ts`(88/93)。
- 等值查询（改走 phoneHash）：`phoneLogin`(111)、`smsLogin`(149)、`resetPassword`(418)、`bindPhone`(464)、`phoneRegister`(76)、`account`(88)，以及 `Auth` 表按 openId=phone 的查询(470)。
- 返回脱敏（decrypt+maskPhone）：`getProfile`(366)、`getDevices`(518) 等所有 select phone。
- redis key（`login:lock:${phone}`/`login:fail:${phone}`，`auth.service.ts:106/136`）：可改用 phoneHash 做 key，避免明文 phone 进 redis。
- webhook（`fireUserRegistered` 传 phone，502）：按需脱敏。

> 改造点 15+ 处、全在登录/注册/改密关键路径，任一处错 → 用户登不上。**必须真机登录/注册/改手机/找回密码全回归**才能上线。

## 五、存量数据回填（前台 tsx 脚本，连 5433）

```
对每个 User：phoneHash = phoneHmac(phone); phoneEnc = encrypt(phone); 批量 update。
对每个 PaipanRecord：生辰字段 encrypt 回填。
```
幂等（已回填的跳过）、分批（避免大事务）、回填后校验 `decrypt(phoneEnc) === phone` 全量一致。

## 六、迁移步骤（灰度，可回滚）

1. 加列（`db execute`，可空，不动原 phone）→ generate → 发布（双写：新老列同写，查询仍走 phone）。
2. 跑回填脚本 → 校验 100% 一致。
3. 切查询到 `phoneHash` → 发布观察（登录/注册/改手机回归）。
4. 稳定后：停写明文 `phone`、返回全脱敏。
5. 最终：删 `phone` 明文列（`db execute`，先 `pg_dump` 备份 User 表）。

## 七、风险与回滚

- **最高风险**：登录/注册查询切错 → 用户登不上。故第 3 步灰度发布、保留 phone 列可秒回退查询。
- HMAC key 一旦更换，所有 phoneHash 失效 → key 必须固定、备份、纳入密钥管理。
- 唯一约束冲突：回填前先查明文 phone 是否已有重复（脏数据），否则建 `phoneHash @unique` 会失败。
- 验证：jest（auth/account 全回归）+ 真机登录/注册/改手机 + mcp 抽样确认密文存储、无明文。

## 八、工作量与排期建议

- 非「顺手」可完成：涉及 auth 核心链路 + 存量回填 + 灰度发布，估 1–2 个独立工作窗口。
- 建议作为**独立安全专项**排期，与本轮 DB 本体优化解耦（避免在一个窗口里仓促动登录/资金级逻辑）。

### 🔴 修复了一个预先存在的定时炸弹（ENCRYPTION_KEY）
- 发现根 `.env` 的 `ENCRYPTION_KEY` 被写成 **40 字节无效值**（`getKey()` 要求严格 32 字节），而 pm2 运行时进程内存里是**有效的 32 字节 key**（二者不一致）。
- 后果：一旦带 env 重启（`--update-env`/重启机器/重新部署），全平台 `encrypt`（生辰/身份证/银行卡/bot apiKey/M4）**全部 500**，靠"进程没重载新 env"苟着。
- 已把运行时 32 字节 key **固化回根 .env**（备份 `.env.bak-20260629-keyfix`），文件=运行时一致，炸弹拆除。回填脚本读新 .env 成功加密 38 个即验证 key 有效。
