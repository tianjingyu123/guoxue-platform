## 一、P1 高危（按修复优先级，均已对抗性验证）

### T1｜资金状态流转 TOCTOU（check-then-act 非原子）— 最高优先
同一类根因，4 处可直接资损/账务错乱：

1. **达人通话 end/cancel 并发双重退款+双重分账** `P1`
   `consult-call/consult-call.service.ts:77-106`
   事务外读校验 `status==='ONGOING'`，事务内 UPDATE 仅 `WHERE id=$1` 无状态守卫。两个并发 end 都过检查 → 各退一次预扣 + 各记一次达人 50% 分账。cancel(WAITING) 同样、且 end↔cancel 竞态。
2. **圈子退款 adminReview/ownerReview 并发双倍入账钱包** `P1`
   `circle-refund/circle-refund.service.ts:128-147,197-251`
   预读 `adminStatus==='pending'` 后 UPDATE 无 CAS 守卫；`executeRefund` 钱包入账 `ON CONFLICT DO UPDATE balance+=actualRefund` 在 `if(member)` 守卫之外无条件执行 → 第二次并发仍重复入账。
3. **reverseCommission 无幂等，重复倒扣站长/运营商收益** `P1`
   `commission/commission.service.ts:179-246`
   仅查正向 earning 存在即冲正，无 `type='REFUND'` 幂等判断。三条 fire-and-forget 路径（shop.service.ts:1214/1261、circle-refund.service.ts:255）+ 退款回调重投 → 重复倒扣为负。
4. **赛事/驿站报名名额 count-then-create 无锁超卖** `P2`
   `competition/competition.service.ts:209-216`、`offline/offline.service.ts:193-201`
   唯一约束只防同人重复，不防名额超额。付费赛事场景敏感。

**统一修复范式**：所有资金状态推进改 `UPDATE ... WHERE id=$1 AND status='<当前态>'` + 检查受影响行数=1，行数=1 才执行退款/分账。已有正确范式可抄：`fund-approval.service.ts:81-91` 的 claim、`video-creator.service.ts:655` 的条件更新。

### T2｜资金审批缺职责分离（maker-checker）`P1`
`fund-approval/fund-approval.executor.ts:28-53`
`review()` 只校验单据 PENDING，不比对审批人 `reviewerId` 与发起人 `requestedBy`。发起角色（SUPER_ADMIN/OPERATION_ADMIN）与审批角色（SUPER_ADMIN/FINANCE_ADMIN）交集 SUPER_ADMIN → 同一人可既发起又审批同一笔充值/退款/分佣变更，四眼原则被架空（CLAUDE.md 明确要求退款/价格变更走审批）。
**修复**：`review()` 开头加 `if (requestedBy===reviewerId) throw FORBIDDEN`，并收紧角色使发起/审批不重叠。

### T3｜加密/配置启动期健壮性 `P1`
1. **ENCRYPTION_KEY 启动只验存在不验长度** `P1`
   `config/server-config.ts:111-127` + `common/crypto.util.ts:10-16`
   `validateRequiredEnv` 只查非空；`getKey()` 运行时强制 32 字节否则 500。无效长度 KEY 能通过启动校验、显示健康，首笔加密才炸 500 —— 正是历史「根.env 40字节 vs 运行时 32字节」事故的同一失效模式，至今无启动期防线。
   **修复**：启动期断言 `Buffer.byteLength(key)===32` 并实跑一次 encrypt→decrypt 往返自检，失败即 fail-fast 拒绝启动。
2. **decrypt 失败静默返回密文原文** `P1→验证降 P2`
   `common/crypto.util.ts:27-42`
   catch 仅 stderr 一行后 `return ciphertext`。密钥轮换/错配时，所有历史密文解密失败 → 把 base64 乱码当明文返回给银行卡/身份证/生辰/apiKey/SMTP 密码等展示字段（commission/merchant/bot/email/paipan），从「显式 500」退化为「静默脏数据」，无告警。
   **修复**：区分「非本系统密文格式」（走明文兼容）与「GCM authTag 校验失败」（密钥错配，计数+notifyAlert 告警/抛错）。

### 验证后降级说明
- **circle-refund 写端点无 DTO**（`P1→P2`）：内联 body 绕过 ValidationPipe 属实，但端点有 RolesGuard、金额服务端计算、参数化 SQL，缺校验只导致保守的「静默驳回」非资损；且原报告称「dto.ts 存在但为空」不实（文件不存在）。
- **decrypt 静默吞错**（`P1→P2`）：见 T3-2，无即时资损路径。

## 二、P2 中危（按主题）

### 资金事务补偿（事务外 fire-and-forget 无补偿）
- 圈子退款站长佣金追回 `circle-refund.service.ts:253-258`：事务外 `.catch(warn)`，失败即平台多付佣金无重试。
- 达人 50% 分账 `consult-call.service.ts:99-103`：事务外 fire-and-forget，失败致主叫被扣而达人未入账。
- 运营商管理奖 `commission.service.ts:486-572`：多笔写未包事务、在主收益事务之外，部分提交致账不一致。
**修复**：建 outbox 待补偿表 + 定时重试 + 失败告警，或纳入主事务（reverseCommission 支持传入 tx）。

### 资金正确性
- **MerchantSettlement 用 Int 存「元」四舍五入丢分** `schema.prisma:4402-4407` + `merchant-settlement.service.ts:96-104`：`Math.round` 把 Decimal 元截整，跨周期累积误差，违反「金额用 Decimal」铁律。→ 改 Decimal(12,2)。
- **商城取消订单库存恢复硬编码 +1** `shop.service.ts:1356-1367`：下单按 qty 扣减、取消只回 1 件，多件订单库存永久丢失。→ order 表加 quantity 字段。
- **huifu.createRefund 退款后不更新本地订单/不触发冲正/无金额上限** `huifu.service.ts:463-493`：网关已退、本地仍 PAID，账实不符 + 超额退款风险。

### 鉴权与校验
- **鉴权 fail-open** `main.ts:77`：无全局 JwtAuthGuard，靠每路由手动 @UseGuards，新端点漏加即未鉴权。→ 全局 APP_GUARD=JwtAuthGuard + @Public() 显式标注公开端点。
- **circle-refund / finance 用户开票端点内联 body 绕过 ValidationPipe** `circle-refund.controller.ts:31,67,89`、`finance.controller.ts:95-101`。
- **资金金额缺下限校验**（可传负/零）`finance.dto.ts:64,202`。
- **分页 pageSize 无上限**（DoS）`finance.dto.ts:41,81,127,164,235`。

### 可观测性
- **notifyAlert 企微告警通道全代码库零调用** `http-exception.filter.ts:70` / `logging.interceptor.ts:45` / `queue-monitor.processor.ts:32`：5xx 风暴、慢请求、队列积压只进日志无人触达。→ 接到 5xx/CRITICAL/队列积压三处。
- **审计仅成功路径、内容偏浅** `audit.interceptor.ts`：失败/越权尝试不入审计，无金额/审批结论快照。
- **圈子退款审核未挂 @Auditable 且审批人 id 被丢弃** `circle-refund.service.ts:128`（`_adminId` 下划线刻意丢弃）。

### PII 脱敏一致性（内部员工可见明文手机号）
- 国学币后台交易/充值流水 `coin.service.ts:216,234`（CUSTOMER_SERVICE 角色可批量看明文手机号）
- 佣金提现列表漏 maskPhone `commission.service.ts:385`（银行卡脱敏了却漏手机号）
- 排盘后台记录明文手机号+客户姓名 `paipan.service.ts:572`
- **订单/提现 CSV 导出明文手机号** `export.service.ts:70,161`（落地文件，外泄面更大）

### 数据库
- **软删 deletedAt 半成品** `schema.prisma:52,355,...`：10 模型有列但全库 0 处写入、仅 ~10 处过滤，Product/Article 反用物理 delete，登录不校验 → 「激活即泄露」债务。→ 二选一彻底贯彻。

### 性能（无资损）
- **古籍馆首页对 46.5 万行 ClassicChapter 无缓存全表 count()** `classics-bff.service.ts:163`：公共热路径 TTFB 大头。→ 加 Redis 缓存/汇总快照表。
- **多处「取全量再内存切片」**：圈子活跃度排行 `circle.service.ts:1206`、圈子经营看板 take:20000 `circle-dashboard.service.ts:159`。→ 改库内 orderBy/groupBy + skip/take。
