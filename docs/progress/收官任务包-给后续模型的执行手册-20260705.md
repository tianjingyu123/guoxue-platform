## T1 免费即得批（性-P0③·零采购·预计 1-1.5 天）

### T1a 小程序主包瘦身【发布阻断级·最优先】
```
现状：主包 5.81MB（微信上限 2MB），static 独占 4.98MB——图片体积回潮（此前 WebP 化后又有大图混入）。
步骤：
1. pnpm --filter @guoxue/mobile build:mp-weixin 后用 du 按目录排 static 体积 top30，列清单。
2. 处置三板斧（按优先级）：①>50KB 的营销/装饰图迁 COS 走 URL（上传后替换引用，源文件删除）②必须本地的 PNG/JPG 全部转 WebP（质量80）③按使用分包就近放置（只被 pkg-x 用的资源移进该分包目录）。
3. 死资源排查：grep 每个 static 文件名在 src 的引用，零引用即删。
4. 验收：主包 < 1.8MB（留缓冲）；H5 与小程序双端 build 成功；抽查 10 个页面图片正常显示。
5. 防回潮：给 package.json 加 size-check 脚本（build 后主包超 1.9MB 报错），并在 CLAUDE.md 前端规范补一行"新增图片>50KB 必须走 COS"。
```

### T1b 开启 pg_stat_statements（O1 观测盲区）
```
服务器操作（sudo 免密）：
1. psql 确认扩展已装：SELECT * FROM pg_available_extensions WHERE name='pg_stat_statements';
2. postgresql.conf 加 shared_preload_libraries='pg_stat_statements' + pg_stat_statements.max=5000 + track=all。
3. 【需重启 PG·选凌晨 3-5 点低峰】sudo systemctl restart postgresql → 立即 curl health 确认 db ok → CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
4. 验收：SELECT query,calls,mean_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10; 有数据。
5. 顺手把"慢查询周报 Top10 进简报"接上（daily-brief 或 weekly-brief 加一段查询）。
风险：重启 PG 期间全站不可用 1-2 分钟，提前在管理群知会。
```

### T1c Redis maxmemory
```
redis.conf（或 CONFIG SET 后写回配置文件双保险）：maxmemory 512mb + maxmemory-policy allkeys-lru。
验收：CONFIG GET maxmemory 返回 536870912。
注意：当前仅用 1.96MB，512MB 很宽裕；allkeys-lru 下持久性数据别放 Redis（现有用法已符合——refresh token 丢失=用户重登，可接受）。
```

### T1d 数据库自动备份（设计见 docs/design/运维守护体系 §三·照做）
```
1. 服务器写 /opt/scripts/backup-db.sh：pg_dump -Fc → /opt/backup/guoxue-$(date +%Y%m%d).dump → 校验（pg_restore --list + 大小>上次50%）→ find -mtime +7 -delete → coscmd upload 到低频桶（桶需用户在腾讯云控制台开通并给密钥，若未就绪先做本地备份部分，COS 段留 TODO 注释）。
2. crontab: 30 3 * * * bash /opt/scripts/backup-db.sh >> /var/log/guoxue-backup.log 2>&1
3. 验收：手动跑一次，产出文件且 pg_restore --list 可读；第二天确认 cron 产出。
```

### T1e nginx 榨干
```
1. nginx -V 确认 http2/brotli 模块；server 块 listen 443 ssl http2；有 brotli 则开（无则 gzip_comp_level 5 + gzip_types 全集确认）。
2. H5 静态资源（文件名带 hash）：location ~* \.(js|css|png|webp|woff2)$ { expires 365d; add_header Cache-Control "public, immutable"; }——注意 index.html 必须 no-cache。
3. 验收：curl -I 静态资源看 cache-control；浏览器二次访问 304/memory cache；curl --http2 -I 确认协议。
4. nginx -t 通过再 reload；改前备份配置文件。
```

## T2 开 PM2 cluster + 压测基线（前提已就绪·预计 0.5-1 天）

```
前提确认（已全部完成，可直接开）：ws redis-adapter ✅ cron 全量分布式锁 ✅ 限流/预算入 Redis ✅ 会话无状态 ✅。
步骤：
1. 压测先行（改前基线）：本机装 k6，写 5 接口脚本（home BFF/classics 列表/courses 列表/登录/排盘），从低档爬坡（10→50→200 VU），记录 QPS/p95/错误率 → 存 docs/progress/性能基线-单进程.md。
2. 服务器 ecosystem.config.js：instances: 4, exec_mode: "cluster"（8核留4给 DB/Redis/构建）→ pm2 delete + pm2 start ecosystem --update-env（fork→cluster 必须 delete 重建，restart 无效）。
3. 冒烟：health 全绿 + 登录/refresh + websocket 连接（两个浏览器分别连，验证跨实例互见消息——这是 adapter 的端到端验证）+ 观察 pm2 logs 无 EADDRINUSE/重复 cron 执行（看锁日志"抢不到直接跳过"出现即正确）。
4. 复测 k6 同脚本 → 存 docs/progress/性能基线-cluster4.md。验收：QPS ≥ 基线×3。
5. 【高并发极限测·代替"模拟100万并发"】：k6 爬坡到错误率>1% 或 p95>2s 为止，记录极限容量数字和第一个瓶颈（CPU/DB连接池/Redis）。真实结论比"100万并发"的噱头有用——单机物理上限就是几千并发，重要的是知道极限在哪、瓶颈是什么、扩容路径（见战略课题四路线图）。
6. 回滚预案：pm2 delete + 按 fork 配置重启（保留旧配置文件副本）。
风险提示：压测对生产库有真实写入压力，压测账号数据事后清理；避开业务高峰（选凌晨）。
```
