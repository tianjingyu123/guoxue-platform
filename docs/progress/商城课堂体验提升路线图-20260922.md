## 判断标准

从用户看，每一步都应能快速找到所需内容、看懂价格与权益、知道下一步和失败后的恢复方式；从经营看，转化信息必须可信，不能用虚假时限、未核实承诺或假成功换点击。优先处理导致误购、重复下单、无法学习或无法自助恢复的问题，再处理视觉密度和细节一致性。

## 本候选逐项落地顺序

1. 优先修复有源码证据的错误状态与误导信息，每项改动保留可回退的独立提交，记录失败与未覆盖项。
2. 对支付、课程权限和售后路径补合成数据验证；若需要数据库，仅使用独立本地环境。对服务端幂等和金额规则提出接口验收清单，不在前端伪造保证。
3. 用真实测试环境及目标设备完成视觉、触控、辅助技术和业务路径验收后，再讨论主线接收与发布；本候选不部署。

## 验收指标与取数

在有合法埋点与测试环境数据后，按商城“首页曝光→详情→结算→支付成功→售后结果”和课堂“课程曝光→详情→试看/开通→首次播放→继续学习”分别计算漏斗。每一步同时记录加载失败率、重试成功率、重复提交率、从返回到恢复原任务的耗时；按 H5/微信小程序、屏宽及网络条件分组。当前没有可信基线，不设拍脑袋的转化率提升百分比，也不把构建通过当作业务指标。

主线评审前以可复现的场景验收：筛选取消不影响结果；价格无上限可查；评价接口失败仍能查看课程和目录；慢推荐不遮挡主内容；“新上架”按服务端最新排序；部分建单失败后不错误复用不同结算选择；支付和权益以服务端最终状态为准。

## 当前决策点

- 批量商品订单仍是逐单创建。客户端只能防止本页面已收到成功响应后的错误复用；请求超时但服务端已建单的情形，需要服务端幂等键或恢复查询，不能由页面内存缓存根治。
- 课程详情已把权限查询失败与未购分开，免费课也复用本人课程列表按 ID 核对是否已收录；播放器仍使用布尔降级。合成 HTTP 浏览器测试覆盖评价失败、免费课收录及 320/375/430px 按钮布局；支付回跳后的权益同步、真实后端会话失效和目标设备操作，仍需测试环境逐渠道核验。
- 发货、售后、课程有效期和证书资格必须有可核验规则来源，展示文案与真实订单/权益状态一致。

## 订单超时恢复的服务端接收条件

静态核对 `CreateOrderDto`、`ShopOrderService.createOrder` 和 Prisma `Order`：普通商品订单没有客户端请求键或对应唯一约束。订单创建与库存扣减已在同一事务内，但网络超时后客户端不知道事务是否提交，直接再次 POST 仍可能再建单、再扣库存。页面缓存只覆盖收到成功响应的情况。

当前隔离候选已添加商品订单可选的 `clientRequestId`、参数摘要及 `(userId, clientRequestId)` 唯一约束迁移草案；同键先查询已提交订单，事务内用 PostgreSQL advisory lock 串行并再次查询，再扣券、建单和扣库存。单测覆盖同键复用、改数量拒绝、事务失败重试，Prisma schema 与服务端类型检查通过。现有移动端尚未发送稳定请求键，所以此提交单独接收也不会修复用户侧超时重复下单。下一步必须补客户端跨重载保存每个清单行的键，且在独立本地库验证并发、响应丢失、券和库存只扣一次、取消后新购买；当前没有本地数据库口令，未执行任何迁移，不能声称资金链路已验收。
