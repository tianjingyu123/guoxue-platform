# 生产 git 对齐 · 操作清单与安全步骤（2026-07-13）

> 目标：让**生产 git 记录**追上**实际运行代码**，消除"git 停在旧 commit、实际靠 scp dist 领先"的长期脱节。
> 本清单只做**记账对齐**（让 git 指针指对），默认**不重新部署、不重启**，做到零运行风险。

## 一、生产实况（已实测·2026-07-13）

| 项 | 事实 | 含义 |
|----|------|------|
| 生产 git HEAD | `bec27de4`（6/10 排盘批） | git 记录停在这 |
| 生产分支 | `master` | 无异常分支 |
| 跟踪文件本地改动 | **0（M=0）** | 无分叉，reset 不会丢改动 |
| 未跟踪项 | 64 个，全是 `dist.bak.*` / `.deploy-backups`（部署备份垃圾） | 无害，不影响 git |
| 仓库所有权 | `ubuntu:ubuntu` | git 操作不会 Permission denied |
| dist 产物 | **全部被 .gitignore（未跟踪）** | **reset 只动源码、不碰正在运行的 dist** |
| 本地 master 领先 | **35 个 commit**（含本轮卡片治理/文档/admin按钮修复固化） | 要对齐的差距 |
| admin 已同步 | 本轮已把 admin 部署为 master 版 | admin 侧已= master |

## 二、为什么"reset 对齐"是零运行风险

生产**运行的是编译产物**（后端 `dist/main.js`、H5/admin 静态 dist），**不是源码**。而：
- dist 全被 gitignore → `git reset` 不会碰到它们 → 进程照常运行、不重启；
- 跟踪文件 M=0 → reset 不丢任何本地改动；
- 未跟踪的 dist.bak/.env 等 → `reset --hard` 一律保留（.env 是 gitignore）。

所以 `git reset --hard master` 在生产上**只把源码文件更新到 master、只移动 git 指针**，运行中的服务完全不受影响。**回滚也是一行**：`git reset --hard bec27de4`。

## 三、执行步骤（记账对齐 · 推荐）

```bash
# —— 本地：打增量 bundle（github 国内直连易断，走 bundle 绕开）——
cd D:/guoxue-platform
git bundle create /tmp/align.bundle bec27de4..master
scp /tmp/align.bundle rebu-server:/tmp/align.bundle

# —— 生产：备份指针 → fetch → reset —— （ssh rebu-server）
cd /opt/guoxue
git rev-parse HEAD > /tmp/git-head-before-align.txt   # 记下 bec27de4，回滚用
git fetch /tmp/align.bundle master                    # 拉入 master 的增量提交
git reset --hard FETCH_HEAD                            # 源码对齐 master（dist 不动·进程不重启）
git log --oneline -1                                  # 应显示 master 顶端 commit

# —— 验证：服务仍正常（reset 未重启，本应无影响，确认一下）——
curl -s localhost:3001/api/v1/health                  # 后端健康
curl -s https://api.rebugx.cn/admin/ | grep -o 'index-[^"]*\.js' | head -1   # admin 仍在
```

回滚（任何异常）：`cd /opt/guoxue && git reset --hard $(cat /tmp/git-head-before-align.txt)`

## 四、对齐之后要知道的两件事

1. **对齐 = 记账，不等于"生产运行了 master 全部代码"**。生产运行的后端/H5 dist 仍是此前 scp 的那份；对齐只是让 git 记录诚实。真正让生产运行 master 最新代码，是另一件事——**下一次受控部署**（见第五节）。
2. **对齐后，下一次谁在生产 `pnpm build` 就会基于 master**。所以对齐后到下次正式部署之间，别在生产误触发 build/重启即可（正常不会）。

## 五、真要把 master 新代码上线时（高风险·另走）

这才是"部署新功能"，风险在 570 万 C 端，必须：
- 部署 owner 在场；
- 先 `pg_dump` 备份库；
- 分模块灰度（先后端 `NODE_OPTIONS=--max-old-space-size=6144 nest build` 出 dist 再 `pm2 restart`，再 H5）；
- 每步 curl 健康检查 + 关键端点；
- 保留 dist.bak 可秒回滚。
- **支付这条链路**：还需先决条件（小程序发布含 pay-relay 的 release 版 + 商户号绑定小程序 appid），见 [[guoxue-huifu-h5-pay]]。

## 六、需要 owner 拍板的点

- 第三节的**记账对齐（reset --hard master）**是否现在执行？（零运行风险、可一行回滚）
- 第五节的**新代码上线**按模块、按时间窗单独安排（不在本清单执行）。

## 七、附：顺手可清的垃圾（非必须）

生产 `/opt/guoxue/apps/admin/` 下 64 个 `dist.bak.*` 备份目录占空间，确认无需回滚的旧版本后可清：

```bash
cd /opt/guoxue/apps/admin && ls -d dist.bak.* | head -n -3 | xargs -r rm -rf   # 保留最近3个
```
