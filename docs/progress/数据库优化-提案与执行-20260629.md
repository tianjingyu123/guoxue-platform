### M4 — 手机号 / 生辰明文存储（合规风险）
- `User.phone` = text，抽样 `1390xxxxxxx` **完全明文**；`PaipanRecord.clientName` 及生辰字段同。
- 违反《个人信息保护法》对敏感个人信息「加密存储」要求。
- **这是架构级改造，非单纯改字段**，须单独立项，因为：
  - 登录/注册需按手机号精确匹配 → 明文加密后无法直接 `WHERE phone=?`。标准解法：**确定性加密**（同明文→同密文，可等值查询）或**单独存 `phoneHash`（HMAC-SHA256）做查询 + 密文 `phoneEnc` 做展示脱敏**。
  - 涉及：注册去重、登录、短信、后台检索、已存量数据回填加密。
  - 项目已有 `ENCRYPTION_KEY`（根 .env），可复用做字段级加密。
- **建议**：本项单列为「敏感数据加密改造」专项，先定加密方案（推荐 phoneHash + phoneEnc 双列）再排期，避免与本轮 DB 优化混做。
- ✅ **完整方案已立项产出**：`docs/progress/M4-敏感数据加密改造方案-20260629.md`（含双列设计、改造点清单、存量回填、灰度迁移、回滚预案）。关键依据：项目已有 `crypto.util.ts`（encrypt/decrypt/maskPhone），但 `encrypt` 是随机 IV 不可等值查询 → 必须 phoneHash(HMAC) 承担登录/注册的精确匹配。用户已确认本项**单独立项设计后再执行**，本轮不动代码。

## ✅ 排期 #2 执行记录 — CircleKnowledge 60万次查询定性与就地优化（2026-06-29 续）

**前置判断（先量是否真高频）**：
- pg_stat_statements top1：`SELECT … FROM CircleKnowledge WHERE …`（命中 `circleId_sourceType_idx`），**598983 calls / 184 秒 / 占全库执行时间 99.9%**，mean 仅 0.308ms。
- **两次采样 calls 完全不变（598983 → 598983）**；按 stats_reset 算 avg 仅 4.3 calls/s，是 38.7 小时的**历史均值**，非实时增量。→ **结论：当前并非实时读热点**，原排期"list 加缓存"方案**否决**（过早优化，缓存无收益）。

**真因定位**：`apps/server/src/modules/classic/classic-index.task.ts` 的 `@Cron(EVERY_DAY_AT_4AM) indexClassicChapters()`——嵌套循环遍历 ClassicBook→ClassicChapter，**每章一次 `circleKnowledge.findFirst` 查重**（N+1）。每天 4AM 全量跑一遍即产生数十万次查询；当前静止是因非 4AM，下次 4AM 会再爆。

**就地优化（开发阶段授权·纯性能·不改业务语义）**：循环外**一次性 `findMany` 载入全部已索引 `sourceId` → 内存 `Set` 查重**，替代逐章 findFirst。每次 4AM 的数十万次查询压到 **1 次**；并对同批新建用 `indexedIds.add()` 防重复。
- 验证：`tsc --noEmit` exit 0；`nest build` exit 0；`pm2 restart guoxue-api` → online、`home=200`。下次 4AM 生效。

**顺带发现（未改·留待专项，非 DB 范畴）**：
- `take: 200` → 每本古籍**只索引前 200 章**，超出部分永不索引（功能缺陷）。
- 该 task 向量化依赖坏掉的 embedding（deepseek-embedding 404 → 字符哈希向量），索引产物语义检索可能无效——需先修 embedding 再谈全量索引。
