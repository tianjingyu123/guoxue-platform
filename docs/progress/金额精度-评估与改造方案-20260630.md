# 金额精度（Float→Decimal）评估与改造方案 — 2026-06-30

> 触发：DB 优化 P3 提案「金额 Float→Decimal」。本方案**先评估后改造**（遵 CLAUDE.md 架构变动方案先行）。
> 结论先行：**schema 层已达标无需改造；真正的金额精度风险在代码运算层**——改造方向需从「改 schema 类型」修正为「治理代码层金额运算」。

---

## 一、核心结论

1. **schema 存储层已达标，无需改造。** 全库金额字段已是 `Decimal(10/12, 2)`（元）或 `Int`（分/币），**0 个金额语义的 Float**。3 个历史金额 Float（`StationTeacherBooking.price`/`AiAnalysisRecord.cost`/`AiCapability.costPerCall`）早在 2026-06-29 已转 Decimal（见 `数据库优化-提案与执行-20260629.md` 与 `manual-sql/db-opt-05-money-decimal.sql`）。schema 现存 29 个 Float **全部是评分/权重/进度/置信度/比率/难度**（非金额，Float 合适，不应转）。

2. **真正的金额精度风险在代码运算层，而非 schema。** 后端 `modules` 下 **0 处** 使用 Decimal 对象运算（`Prisma.Decimal`/`decimal.js` 的 `.plus()/.times()/.toNumber()`）；金额一律 `Number(decimalField)` 转 JS **float** 后做四则运算。

3. **已确认的高风险实例**——分佣 `commission.service.ts:136-137`：
   ```js
   const rate = Number(config.rateA);  // Decimal 比例 → JS float
   const earned = amount * rate;       // JS 浮点乘法算分账金额，未规整到分
   // ...
   data: { earned },                              // float 结果存回 Decimal 列
   data: { totalEarning: { increment: earned } }, // 且 increment 累加该 float
   ```
   例：`amount=99.9, rate=0.7 → earned=69.93000000000001`。展示时 `toFixed(2)`（:166）才规整，但**存储的 earned 是未规整的浮点值**。后果：各方分账之和可能 ≠ 订单总额（分账不平）、`increment` 累积漂移。`finance.service:77` 对账已用 `Math.abs(... ) > 0.01` 容差——这正是在**容忍浮点误差**。

## 二、证据

### 2.1 schema 金额字段全景（grep 验证）
- **法币金额**：`price/amount/payAmount/originalAmount/balance/fee/deposit/revenue/income/earning/refund/platformFee/...` 约 70+ 字段，**已全部 `Decimal @db.Decimal(10,2)` 或 `(12,2)`**。
- **虚拟币/积分/分**：`flashPrice/balance(币)/giftAmount(分)/entryFee(分)/rewardAmount(分)/unlockPrice(分)/pointsCost` 等用 `Int`——**整数无浮点问题，是金额存储的正确做法之一**。
- **29 个 Float 全非金额**：`progress`(进度)、`score/qualityScore/qualityRating/totalScore/activityScore/scoreThreshold`(评分)、`successRate`(成功率%)、`confidence`(置信度)、`accuracy/completeness/readability/professionalism/overall`(AI质量分)、`weight`(权重)、`similarityScore`、`difficultyLevel`、`ruleValue`、`outcomeExpected/outcomeActual`(通用效果指标)。这些是统计量/近似值，**Float 合适，转 Decimal 无收益**。

### 2.2 代码层运算现状
- `grep .plus(|.times(|Prisma.Decimal|.toNumber()` over `modules` → **0 匹配**：全后端无 Decimal 对象运算。
- `grep Number(<金额字段>)` → **大量**：金额读出即转 float。其中：
  - **只读聚合/展示**（多数）：`dashboard/role-dashboard`、`finance`(对账/汇总 reduce sum)、`discover`/`recommendation`(返回前端 price)——float 误差仅影响展示，不写回 DB。
  - **写回 DB 的资金运算**（少数但关键）：`commission`(分账 earned)、`circle-refund`(actualRefund) 等。

## 三、风险分级

| 类别 | 示例 | 风险 | 处置 |
|---|---|---|---|
| **写回 DB 的资金运算（乘除/比例）** | commission 分账 `earned=amount*rate`、退款、扣费、结算分成 | **高**：浮点尾数存回、分账不平、累加漂移 | **必治** |
| 写回 DB 的加减 | 余额 `increment/decrement` | 中：若走 Prisma 原子 increment（DB 端 Decimal 运算）则安全；若 JS float 算后存回则有风险 | 审计区分 |
| 只读聚合 / 展示 | dashboard 统计、finance 对账 reduce、返回前端 price | 低：仅影响展示，已用 0.01 容差 | 可不动 |
| Int 分 / 币 字段 | coin balance、giftAmount、entryFee | 无：整数无浮点问题 | 不动 |

## 四、改造方案（代码层，schema 不动）

### 4.1 原则
- 资金**写运算**：用「整数分」或 `decimal.js`（Prisma 自带 `Prisma.Decimal`）做乘除，结果 `ROUND_HALF_UP` 规整到 2 位（分）再存。
- **比例/乘除尤其要规整**（乘法最易产生尾数）。
- 加减优先用 Prisma 原子 `increment/decrement`（DB 端 Decimal 运算，避免读-改-写竞态 + JS 浮点）。

### 4.2 范围与优先级
1. **P0 资金写操作治理**（逐一审计 `Number()` 后乘除存回点）：`commission`(分账/回滚 reverseCommission)、`coin`(扣费/退款)、`merchant`(结算/保证金)、`user/wallet`(退款/提现)、`circle-refund`。
2. **P1 配套**：新增 `common/money.util.ts`（`mulYuan(amount, rate)`、`splitYuan(total, rates[])` 等，内部整数分或 decimal.js，返回规整到分的值）；资金写操作改用之。
3. **P1 单测**：分账各方之和 == 订单额、退款 ≤ 已付、`increment` 后余额精确、边界（99.9×0.7、三方分账除不尽）。
4. **不做**：只读聚合/展示的 `Number()`（改造收益低、风险高，保留 + 容差）。

### 4.3 实施方式
- 先**全面审计** P0 五个 service 的金额写运算，列出每个 `Number()*/÷ → 存回` 点（预计十余处）。
- 引入 `money.util` 统一规整，逐点替换。
- 补单测，`jest` 全绿；用户重启后端 e2e 走查一笔真实分账验证求和平账。
