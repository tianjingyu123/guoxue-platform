# 多租户客户模型预算与继续推进

本批仅补齐一期本地隔离候选的客户模型技术预算，未合主线、推远端、上云或调用真实供应商。真实客户授权、具体额度、费用及供应商对账仍待实际条件满足后的独立验收。

## 行为与授权

此前只有单账号十分钟20次技术限流，不足以限制多个账号和应用合计的请求。本批在客户签名核验记录增加 `callBudget`，必须明确 `maxRequests`（1至1000000整数）和 `maxUnresolved`（1至100整数，不超过总上限）。这些是维护配置的技术范围，不是合同默认额度。客户端不能指定或修改预算。

只读GET核验仍默认不授付费调用。只有已获得实际人类授权，维护人员才可使用既有 `--authorize-paid-calls` 并在受限输入文件同时给出预算；缺失或非法预算在HTTP前拒绝，正式入口拒绝旧无预算付费记录。不得在聊天、日志、仓库保存密钥或实际受限输入。预算与客户、空间、模型、密钥指纹及核验有效期一起签名，改值使签名无效。

`maxRequests` 是固定客户数据库现存全部历史消息的累计预留次数，计入COMPLETED、DISPATCHING、UNKNOWN、ABORTED，不因重新核验、重启或跨日清零，也不依据HTTP失败自动退款。`maxUnresolved` 统计全客户DISPATCHING和UNKNOWN；完成只释放此占位，未知结果保持占位，不按60秒、核验过期或重启自动释放。同键查询已有结果在预算耗尽时仍可进行，不重新派发；不同内容继续409。运行角色不能删除消息以恢复额度。

预留事务依次获取客户级、账号级advisory锁和会话行锁，检查预算并保存消息及审计后提交。不同进程、账号、应用共用客户预算；外部调用发生在提交后，供应商等待不持有预算锁。依据[PostgreSQL 16事务级advisory锁文档](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS)，锁随事务结束释放；跨进程行为仍以本批真实数据库演练证明。

## 运行限制

预算不等同金额、余额、供应商账户额度或实际token计费上限。客户直接使用供应商密钥、平台其他入口及恶意宿主均不受这个入口约束。多进程的签名配置在启动时读取；维护登记必须单写并协调所有客户进程使用同一份已授权配置，旧进程不会热加载新上限。真实撤销/减额的运行窗口须后续部署验收，不声称本批完成。

未实现真实供应商查询和人工对账后的解占位。未知请求可能阻断新调用，需要保留事实后另行授权维护，不通过删除历史、换会话或自动补发解决。完整数据库恢复保留消息才保留累计事实；不得用较旧快照抹去新增调用。在正式部署前还须结合45秒停机、网关与真实模型超时做Linux验证。
