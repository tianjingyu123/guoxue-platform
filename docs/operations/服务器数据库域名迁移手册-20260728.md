# 服务器、数据库与域名迁移手册

适用范围：API、H5、管理端、小程序、App、PostgreSQL、Redis、对象存储、直播、点播、支付、物流和第三方回调。

原则：先并行预部署，再隔离验收，最后短暂停写切流；旧环境至少保留 72 小时。禁止在 DNS 切换当天删除旧服务器、旧数据库或旧对象存储。

## 1. 迁移工单必须记录

- 新服务器：云厂商、地域、系统版本、CPU、内存、磁盘、内外网 IP、SSH 用户。
- 新数据库：PostgreSQL 版本、地址、端口、库名、TLS、备份和恢复策略。
- Redis：地址、端口、TLS、持久化方案，是否允许清空短期会话。
- 新域名：API/H5、管理端、CDN、直播推流和播放、点播，以及最终权威 DNS 至少双 NS。
- 对象存储：Bucket、地域、CDN 域名、CORS、防盗链及旧文件保留策略。
- 第三方平台：微信、支付、物流、IM、直播、VOD、短信、邮件和 AI 服务。

密钥、密码和私钥只能进入服务器私有配置，不得提交到 Git。

### 明日首次接入的最小资料包

先提供下列非敏感信息，即可开始预部署和配置骨架；密码、Secret 和私钥只在新服务器的
私有配置中心或 `/opt/guoxue/shared/.env.production` 中录入：

- 新服务器：云厂商、地域、系统版本、CPU/内存/磁盘、内外网 IP、SSH 用户和放行端口。
- PostgreSQL：版本、内网地址、端口、数据库名、TLS 要求、是否迁移旧库及可接受停写窗口。
- Redis：版本、内网地址、端口、TLS、持久化策略，以及短期会话是否允许失效。
- 域名规划：API、H5、管理端、静态资源/CDN 的最终域名；DNS 托管方和证书申请方式。
- 对象存储：Bucket、地域、CDN/CORS/防盗链策略及旧文件迁移方式。
- 主体控制台权限：微信、小程序、支付、物流、直播、VOD、IM、短信、邮件和 AI 服务的配置负责人。

资料不齐时也可先完成主机加固、目录和 Compose 骨架，但不得猜测生产域名、创建空库覆盖旧数据，
也不得切换 DNS。获得真实配置后，先用 hosts 或预览域名验收，再安排停写窗口。

## 2. 新服务器预部署

生产主机目录必须固定，版本目录只保存代码，所有不可随版本切换的状态放在共享目录：

- `/opt/guoxue/shared/.env.production`：生产私有配置，权限只能是 `600` 或 `400`。
- `/opt/guoxue/shared/infrastructure-intake.json`：只能由当前命令新生成并填实的 `schemaVersion: 2` 新基础设施接入清单，权限只能是 `600` 或 `400`，不得提交到 Git。数据库与 Redis 主机名、对象存储 Bucket/地域和公开域名必须与正式环境文件一致；还必须登记最终权威 DNS 至少双 NS、计划切流 TTL、证书供应商/类型、验证方式、部署入口、续期与兜底责任人，以及 `externalEndpoints` 中已启用支付/物流回调、第三方控制台和客户端域名白名单的负责人、变更证据与现场验收状态。`predeploy` 会把回调 URL 指纹与正式环境逐项绑定，`launch` 还会验证双 NS 委派、真实 TTL 收敛、续期/替换演练、公网 TLS 握手、回调验签/重放幂等和客户端白名单；报告不记录原始地址或凭据。
- 该接入清单同时是迁移启动门禁：`launch` 阶段必须证明源库导出权限、目标库连接权限、DNS 变更权限均已实测，迁移演练已完成，停写负责人和 UTC 维护窗口已登记，旧环境至少保留 `72` 小时且不会被覆盖或释放。
- 初次创建时使用 `pnpm release:prepare-infra-intake -- --deploy-target tencent`；自建 PostgreSQL/Redis 时改为 `standard`。该命令默认写入 Git/Docker 均忽略的 `config/release/infrastructure-intake.json`、设置私有权限并拒绝覆盖；不得用复制旧环境清单替代新资源逐项填写。
- `/opt/guoxue/shared/nginx-ssl`：证书与续期结果。
- `/opt/guoxue/backups`：数据库备份与校验文件。
- `/opt/guoxue/releases/<release-id>`：逐版本、已验真的只读发布内容。
- `/opt/guoxue/current`：部署成功后原子指向当前版本的唯一权威符号链接。
- `/opt/guoxue/current-release-id`：兼容旧值班工具的稳定符号链接，始终指向 `current/.release-id`；不得手工写成独立版本号文件。
- `/opt/guoxue/incoming`：尚未验真的上传暂存区。
- Compose 项目名固定为 `guoxue`，确保 PostgreSQL、Redis 等命名卷不会随版本目录改变。
- systemd 只能通过权威 `current/scripts/release/current-compose.sh` 管理 Compose；该脚本每次操作都会从 `current/.release-id` 动态注入 `RELEASE_ID`，并显式固定 `PLATFORM_ROOT`、`RUNTIME_DIR`、`ENV_FILE`，保证自定义安装路径下的服务器重启、服务重载和人工停止仍保持同一运行版本与配置身份。

1. 将 DNS TTL 提前降低到 300 秒，并在接入清单登记最终权威双 NS；控制台显示已修改不能替代三路公网解析器对真实剩余 TTL 和 NS 委派的机器复核。
2. 从干净工作树生成并验收固定发布包；包内必须有 `.release-id` 和 `RELEASE-MANIFEST.json`，不允许服务器自行拉取不确定分支：

   ```bash
   RELEASE_ID=release-20260731-001
   SOURCE_COMMIT="$(git rev-parse HEAD)"
   SOURCE_BRANCH="$(git branch --show-current)" # 必须与本次获批的正式来源分支完全一致
   PRODUCTION_ENV_FILE='/安全受控路径/.env.production'
   INFRASTRUCTURE_INTAKE_FILE='/安全受控路径/infrastructure-intake.json'
   DEPLOY_TARGET='tencent' # 托管数据库/Redis；自建数据库/Redis 时改为 standard
   pnpm release:gate:full -- \
     --env-file "$PRODUCTION_ENV_FILE" \
     --deploy-target "$DEPLOY_TARGET" \
     --infrastructure-intake "$INFRASTRUCTURE_INTAKE_FILE" \
     --report-dir release-evidence \
     --expected-branch "$SOURCE_BRANCH" \
     --expected-commit "$SOURCE_COMMIT" \
     --release-id "$RELEASE_ID"
   # 注意：退出 0 只表示“构建机 launch 候选门禁”通过，可生成固定包；不是最终上线 GO。
   # 最终 GO 必须在服务器现场完成九/十份证据聚合，并通过不同技术、业务负责人的双签门禁。
   pnpm release:package "$RELEASE_ID" \
     --client-config-binding release-evidence/client-config-binding.json \
     --client-artifact-audit release-evidence/client-artifact-audit.json \
     --client-artifact-verification release-evidence/client-artifact-verification.json \
     --source-freeze-audit release-evidence/source-freeze-readiness.json
   pnpm release:verify:package \
     "artifacts/releases/gx-deploy-91-$RELEASE_ID.tar.gz" \
     "artifacts/releases/gx-deploy-91-$RELEASE_ID.tar.gz.sha256" \
     --expected-commit "$SOURCE_COMMIT" \
     --report "release-evidence/package-$RELEASE_ID.json"
   ```

   上传后先在新服务器执行 `sha256sum --check`，必须按包内 `.release-id` 解压到 `/opt/guoxue/releases/<release-id>`，并在该目录再次运行 `release:verify:package`，再进入主机初始化。`incoming/` 只允许作为传输暂存区，项目根或临时目录不得成为 `current`。生产包不得使用 `--allow-dirty`；验真失败不得部署。

3. 在任何系统变更前执行只读主机预检：

   ```bash
   cd /opt/guoxue/releases/release-20260731-001
   PROJECT_DIR=/opt/guoxue/releases/release-20260731-001 \
   ENV_FILE=/opt/guoxue/shared/.env.production \
   DOMAIN=api.example.com \
   bash scripts/release/preflight-host.sh
   ```

   首次执行尚未创建环境文件时允许出现该项警告，但 CPU、内存、磁盘、inode、Linux 架构与内核、DNS、80/443 端口和固定包身份不得失败。该脚本不修改主机状态。

4. 执行服务器准备脚本。自建数据库与 Redis 使用 `standard`；腾讯云托管数据库、Redis、CLB 和证书使用 `tencent`，两种模式不得混用：

   ```bash
   cd /opt/guoxue/releases/release-20260731-001

   # 标准自建模式：本机启动 PostgreSQL / Redis，由脚本申请证书
   sudo PLATFORM_ROOT=/opt/guoxue \
     ENV_FILE=/opt/guoxue/shared/.env.production \
     DOMAIN=api.example.com LETSENCRYPT_EMAIL=ops@example.com \
     DEPLOY_TARGET=standard NODE_ROLE=operations DATABASE_MODE=prepare bash docker/setup-server.sh

   # 腾讯云托管模式：不启动本机 PostgreSQL / Redis；公网 HTTPS 由 CLB 承担，托管数据服务独立校验证书链
   sudo PLATFORM_ROOT=/opt/guoxue \
     ENV_FILE=/opt/guoxue/shared/.env.production \
     DOMAIN=api.example.com \
     DEPLOY_TARGET=tencent NODE_ROLE=operations DATABASE_MODE=prepare bash docker/setup-server.sh
   ```

   两台应用服务器都必须显式指定角色：节点 A 使用 `NODE_ROLE=app`，节点 B 使用
   `NODE_ROLE=operations`。两台都运行应用，只有 B 启动监控、告警、镜像清理和数据库定时备份。

   脚本会把 `DEPLOY_TARGET` 写入 systemd 服务和备份定时任务；服务器重启后不得从托管模式退回自建模式。腾讯云托管模式的日常备份由宿主机锁定版本的 `psql`、`pg_dump`、`pg_restore` 直接连接正式托管库，不依赖也不信任残留的本地数据库容器。

   腾讯云模式还必须从云厂商可信下载源取得数据库 CA，保存到受控宿主机路径并只读授权；示例：`sudo install -o root -g root -m 0400 <下载后的CA文件> /opt/guoxue/shared/tencentdb-ca.pem`，然后在私有正式环境文件中设置 `TENCENTDB_CA_CERT_PATH=/opt/guoxue/shared/tencentdb-ca.pem`。不得从聊天、工单附件或不可信镜像下载证书，不得用 `rejectUnauthorized=false` 绕过验证。

5. 首次执行会生成私有生产配置并安全退出；填写真实值后复核权限：

   ```bash
   sudo chmod 600 /opt/guoxue/shared/.env.production
   ```

6. 完整校验环境和发布配置：

   ```bash
   pnpm migration:check-env /opt/guoxue/shared/.env.production --full \
     --deploy-target "$DEPLOY_TARGET" \
     --node-role operations \
     --report release-evidence/environment-readiness-$(date +%Y%m%d-%H%M%S).json
   docker compose \
     -f docker/docker-compose.yml \
     -f docker/docker-compose.prod.yml \
     --env-file /opt/guoxue/shared/.env.production config -q
   ```

   环境验收报告只记录检查时间、环境文件相对路径、通过状态、问题字段名和计数，不写入任何配置值；
   可作为变更单附件，但仍不得把共享生产配置、私钥或证书提交到 Git。

7. 通过 hosts 或预览域名验证证书、H5、管理端和 API；正式 DNS 尚未切换时不得修改旧生产。

`release:gate:full` 必须在 CI 或有完整锁定依赖的构建机上执行并通过；`launch` 阶段必须传入 `--release-id`，门禁会在同一进程中生成已绑定发布标识和源提交的客户端审计、独立验真与公开配置指纹三份固定包证据。它的退出码 `0` 只代表“构建机候选固定包门禁通过”，绝不等于最终生产上线 `GO`。最终结论必须由服务器现场九份（标准部署）或十份（腾讯部署）证据生成 `launch-decision.json=GO`，再由不同技术与业务负责人完成双签并生成 `final-launch-decision.json=GO`。固定发布包刻意不携带宿主机 `node_modules`，新服务器不重复安装项目依赖或运行全仓构建。服务器只复核固定包、共享生产配置指纹、Compose 展开、生产镜像构建、数据库证据和运行时验收，任何一步失败都不得继续部署。

客户端公网变量在构建时固化，切换域名后必须重新构建 Admin、H5、小程序、App 和 Harmony：

- `VITE_API_URL` 必须等于 `PUBLIC_API_URL`，不要包含 `/api/v1`，客户端请求层会自动追加。
- `VITE_PUBLIC_H5_URL` 必须等于 `PUBLIC_H5_URL`，用于分享链接、海报和跨端跳转。
- `VITE_PUBLIC_ASSET_ORIGIN` 必须等于 `PUBLIC_ASSET_ORIGIN`，历史兜底图片会在构建时统一改写到该对象存储/CDN。
- 构建完成后必须审计五端产物不再包含旧域名、开发地址、源码映射或缺失的新公网地址，并把每一端的字节数、确定性 SHA-256 内容指纹和源提交写入审计报告，再上传 H5，并重新提交小程序、App 与 Harmony 安装包。实际提交的成品必须与该报告指纹一致。
- GitHub `production` Environment 必须配置 Secrets：`PROD_HOST_A`、`PROD_SSH_FINGERPRINT_A`、`PROD_HOST_B`、`PROD_SSH_FINGERPRINT_B`、`PROD_USER`、`PROD_SSH_KEY`、`DEPLOY_PORT`（非 22 时必填）。A 为业务节点，B 为业务兼运维节点；两个 SSH 指纹都必须从云厂商可信控制台或服务器本地控制台独立核对，生产部署与切流后复核均会强制校验。
- GitHub `production` Environment 必须配置 Variables：`PUBLIC_H5_URL`、`VITE_API_URL`、`VITE_PUBLIC_H5_URL`、`VITE_PUBLIC_ASSET_ORIGIN`、`PRODUCTION_DEPLOY_TARGET`（`standard` 或 `tencent`）和 `PRODUCTION_DEPLOY_READY`。其中三项 `VITE_*` 必须分别与本节上方对应的 `PUBLIC_API_URL`、`PUBLIC_H5_URL`、`PUBLIC_ASSET_ORIGIN` 完全一致。
- GitHub `production` Environment 必须启用 Required reviewers，并把 Deployment branches 限制为仓库默认分支；部署和切流后只读复核两个工作流都会执行仓库内机器门禁，但它们不能替代 GitHub 平台侧分支策略。
- 所有读取生产 SSH 密钥的任务必须显式使用最小 GitHub Token 权限 `contents: read`，不得授予 `contents: write` 或 `packages: write`；制品上传下载使用工作流内置制品权限，不扩大仓库写权限。
- 准备期间保持 `PRODUCTION_DEPLOY_READY=false`；只有新服务器、数据库、域名、共享配置和回滚演练全部通过后才能改为 `true`。
- 生产发布仅允许从仓库默认分支手动触发；`production_confirmation` 必须与 `release_id` 完全相同，固定包清单中的提交 SHA 还必须与本次 GitHub 源提交完全一致。日常双节点滚动发布还必须填写两台节点共同的 `expected_current_release_id`；工作流会在 A/B 两端核对当前版本，并只读验真该版本的保留包、发布目录和成功历史，任何一端不具备可信恢复点都不得先更新 A。
- 数据库迁移开关默认关闭；如确需开启，必须同时填写 `migration_confirmation=migrate:<release_id>` 和 `schema_compatibility_confirmation=schema-compatible:<release_id>`。后者表示已经确认旧应用可在新数据库结构上短时运行，供跨节点失败时安全恢复旧应用；不能确认时应拆分为兼容迁移、应用发布、清理迁移三个窗口，禁止伪造确认值。普通 push、tag 和非默认分支不会触碰生产。
- 同一次生产任务会重新执行锁定依赖安装、全部代码审计、测试和全端构建，再用 GitHub `production` Environment 的正式公网变量重建 Admin、H5、微信小程序、App、Harmony；只有 `client-artifact-audit.json` 成功、源提交一致、五端内容指纹齐全且成品已归档后，才生成固定包并在 CI 与服务器两端逐文件验真。
- CI 会从上述三项 `VITE_*` 生成不含原始 URL 的 `client-config-binding.json` 指纹，并与 `client-artifact-audit.json` 一并写入固定包。服务器激活时必须在 Docker 构建前用 `/opt/guoxue/shared/.env.production` 重算指纹；不一致立即停止，不得以“服务器稍后再改环境变量”绕过。校验结果保存为 `client-config-binding-verification.json`。
- 五端成品下载、转交或提交应用商店前，还必须在完整解压目录运行 `pnpm release:verify-client-artifacts release-evidence/client-artifact-audit.json --expected-release-id "$RELEASE_ID" --expected-commit "$SOURCE_COMMIT" --output release-evidence/client-artifact-verification.json`。该命令独立重算每端文件数、字节数和 SHA-256 内容指纹，防止拿错版本、漏文件或转交后内容被改动；不能用构建时报告代替交付时复验。

### 2.1 首次固定版本引导（仅一次）

日常 GitHub 双节点滚动工作流要求 A/B 已经运行同一个可回滚固定版本，因此当前“临时预部署目录”不能冒充 `expected_current_release_id`。首次固定版本必须在受控维护窗内完成一次引导，不得通过放宽工作流校验来兼容临时目录：

1. 数据库恢复、增量迁移和最终对账已经按第 3 节完成；首次应用激活保持 `RUN_MIGRATION=false`。
2. 从 CLB 摘除 A，仅向 A 上传并激活已验真的首个固定包；首次引导不设置 `EXPECTED_CURRENT_RELEASE_ID`。
3. 直连 A 验证存活、就绪、运行版本、核心只读接口和日志后，将 A 加回 CLB，确认公网探针持续成功。
4. 从 CLB 摘除 B，以 `NODE_ROLE=operations` 激活完全相同的固定包；确认应用和单例监控栈正常后将 B 加回。
5. 核对 A/B 的 `/opt/guoxue/current/.release-id`、保留包、发布历史和 CLB 返回的 `releaseId` 全部同值，才把该版本登记为后续滚动发布的共同基线。

首次引导期间没有可信旧固定包可供脚本回滚：A 失败时保持 A 摘除并由 B 的临时实例承接；A 成功而 B 失败时保持 B 摘除并由 A 的固定实例承接。不得把临时目录写入发布历史、伪造保留包或手工改 `current`。两台节点未形成同一固定基线前，不得运行日常双节点发布工作流。

`DATABASE_MODE` 只允许：

- `prepare`：只准备主机，不初始化数据库，默认且最安全。
- `restored`：确认已经从旧库恢复并完成校验后使用。
- `empty`：仅明确创建全新空库时使用，并同时提供 `CONFIRM_EMPTY_DATABASE=YES`。

## 3. PostgreSQL 全量迁移

### 导出

```bash
export SOURCE_DATABASE_URL='postgresql://旧库连接'
export MIGRATION_BACKUP_DIR='/secure/backups/guoxue-migration'
bash scripts/migration/export-postgres.sh
```

未指定模式时默认执行 `rehearsal` 演练导出。导出物包含 custom-format dump、SHA-256、public 表行数、数据库版本、扩展和 Prisma 迁移清单。归档和逐表计数绑定同一个 PostgreSQL 一致性快照，避免导出期间仍有业务写入时产生不同时间点的证据；脚本不会修改源库。

最终停写后的正式归档必须显式使用 `final` 模式，并用真实源数据库名二次确认：

```bash
export SOURCE_DATABASE_URL='postgresql://旧库连接'
export MIGRATION_BACKUP_DIR='/secure/backups/guoxue-migration'
export MIGRATION_EXPORT_MODE='final'
export SOURCE_WRITES_FROZEN='true'
export MIGRATION_FREEZE_CONFIRM='真实源数据库名'
bash scripts/migration/export-postgres.sh
```

`SOURCE_WRITES_FROZEN=true` 是现场负责人的停写声明，不会替代网关维护模式、旧应用停机、队列与定时任务停止。最终迁移只接受清单中同时存在 `export_mode=final` 和 `consistent_snapshot=<快照标识>` 的归档。

### 恢复

只允许恢复到新建空库：

```bash
export TARGET_DATABASE_URL='postgresql://新库连接'
export BACKUP_FILE='/secure/backups/guoxue-migration/xxx.dump'
export RESTORE_CONFIRM='新数据库名'
export MIGRATION_RESTORE_MODE='final'
bash scripts/migration/restore-postgres.sh
```

目标 public schema 已存在业务表时脚本会拒绝执行，不得绕过保护。恢复使用 `pg_restore --single-transaction --exit-on-error`，任一对象或数据恢复失败都会回滚整个事务；为保证原子性不启用并行恢复。`MIGRATION_RESTORE_MODE` 必须显式声明；正式迁移使用 `final`，它只接受清单中 `export_mode=final` 且一致性快照标识有效的归档。隔离环境恢复演练可使用 `rehearsal`，但该结果不得作为正式上线数据验收。

### 核对

恢复完成后，必须先在新库执行当前代码版本的全部增量迁移，再做对象与数据核对：

```bash
export TARGET_DATABASE_URL='postgresql://新库连接'
export SOURCE_COUNTS_FILE='/secure/backups/guoxue-migration/xxx.table-counts.tsv'
export SOURCE_CHECKSUM_FILE='/secure/backups/guoxue-migration/xxx.dump.sha256'
export SOURCE_MANIFEST_FILE='/secure/backups/guoxue-migration/xxx.manifest.txt'
export TARGET_RELEASE_ID='release-20260731-001'
export EVIDENCE_DIR="/opt/guoxue/release-evidence/$TARGET_RELEASE_ID"
install -d -m 0750 "$EVIDENCE_DIR"
export MIGRATION_VERIFICATION_MODE='final'
export MIGRATION_VERIFICATION_REPORT="$EVIDENCE_DIR/database-migration-verification.json"
export MIGRATION_DEPLOY_CONFIRM="migrate:$TARGET_RELEASE_ID"
export PRISMA_COMPOSE_ENV_FILE=/opt/guoxue/shared/.env.production
bash scripts/migration/run-prisma-migrations.sh deploy
bash scripts/migration/verify-postgres.sh
```

固定发布包不会携带宿主机 `node_modules`。`run-prisma-migrations.sh` 会构建并复用实际生产 `server` 镜像执行 Prisma，避免临时在服务器安装项目依赖；`deploy` 必须以发布标识二次确认。`verify-postgres.sh` 会在逐表计数与核心业务完整性校验通过后，通过同一生产镜像执行 `prisma migrate status`；只有不存在待执行或失败迁移时才会写入数据库机器证据。

必须确认：

- 所有 public 表精确行数一致。
- 所有外键/检查约束均已验证，所有索引有效，serial/identity 序列不落后于表内最大值。
- 商品与 SKU 无负库存，库存流水满足 `afterStock - beforeStock = quantity`。
- 订单数量、金额、支付/退款时间和内容归因成对关系合法。
- 经营中商家资质完整且已审核；已审核文章全部具备首图。
- `vector`、`pg_trgm` 可用，`CircleKnowledge.embedding`、HNSW、全文检索、标签 GIN 与标题模糊检索索引存在。
- `pg_stat_statements` 建议启用；若数据库服务商要求控制台开通或配置 `shared_preload_libraries`，按服务商流程完成，不作为数据恢复本身的阻断项。
- Prisma 迁移状态正常。
- 用户、订单、支付、退款、课程、古籍、圈子、文章、视频、直播、库存、采购、物流和售后抽样一致。

## 4. 最终停写窗口

1. 公告 10–30 分钟维护窗口。
2. 旧站停止下单、支付、退款、发货、库存调整、内容发布、积分及佣金写入。

## 7. 切流前验收

DNS/证书和公开入口生效后，先执行跨平台运行时门禁。该命令自动验证 API 存活、数据库与 Redis
就绪、完整依赖、Prometheus 指标、H5/管理端入口、安全头、缓存策略、CORS、Socket.IO、鉴权边界、
降级端点和 HTTP→HTTPS 跳转，并生成不含密钥的验收报告：

```bash
DEPLOY_TARGET='tencent' # 托管数据库/Redis；自建数据库/Redis 时改为 standard
TARGET_RELEASE_ID='release-20260731-001'
EVIDENCE_DIR="/opt/guoxue/release-evidence/$TARGET_RELEASE_ID"
SOURCE_COMMIT="$(node -e 'const fs=require("fs");const m=JSON.parse(fs.readFileSync(process.argv[1],"utf8"));process.stdout.write(String(m.commit||""))' "/opt/guoxue/releases/$TARGET_RELEASE_ID/RELEASE-MANIFEST.json")"
node /opt/guoxue/current/scripts/release/verify-client-config-binding.mjs \
  "/opt/guoxue/releases/$TARGET_RELEASE_ID/release-evidence/client-config-binding.json" \
  /opt/guoxue/shared/.env.production \
  --expected-release-id "$TARGET_RELEASE_ID" \
  --expected-commit "$SOURCE_COMMIT" \
  --report "$EVIDENCE_DIR/client-config-binding-verification.json"
pnpm release:verify:runtime /opt/guoxue/shared/.env.production \
  --infrastructure-intake /opt/guoxue/shared/infrastructure-intake.json \
  --expected-release-id "$TARGET_RELEASE_ID" \
  --report "$EVIDENCE_DIR/runtime-verification.json"
```

正常生产切流不得使用 `--allow-degraded`。该参数只允许在隔离预览环境排查第三方服务尚未开通的场景，
不能作为上线通过证据。
运行时报告会绑定接入清单 SHA-256，并由系统解析器、DNSPod 与 AliDNS 分别核对权威区域、至少双 NS、A/AAAA 真实剩余 TTL 和本次 CLB/CDN 目标。任一路仍看到旧 NS、旧地址或超过清单 TTL 上限，都应等待传播完成或回滚，不能手工放行。
验收返回的 `releaseId` 必须与 `TARGET_RELEASE_ID` 完全一致；缺失、`unversioned` 或旧版本标识均阻断切流。
固定发布包激活必须显式提供完整的 40 位 `EXPECTED_COMMIT`；该值应来自本次已审核的 CI 源提交或固定包
`RELEASE-MANIFEST.json`，不得留空、使用短 SHA 或由服务器临时猜测。
激活脚本会先在 `.candidate-*` 候选目录逐文件验真，失败时自动清理候选目录；只有候选验真通过才会原子移动到
`releases/<release-id>`，并对正式目录再次验真和生成证据，避免坏包占用正式发布标识。
健康部署成功后，脚本先原子安装 `current-release-id -> current/.release-id` 兼容指针，再原子切换权威
`current`。因此任一步骤中断都不会产生“软链接是新版本、版本号文件仍是旧版本”的分裂状态；验收、回滚和
保留审计均以 `current/.release-id` 为准，并复核兼容指针一致性。
部署脚本必须在完整健康检查通过后才能声明完成。若新实例已启动但完整检查失败，脚本自动恢复旧镜像和部署前记录的旧 `RELEASE_ID`，并复核回滚实例的轻量存活与版本身份；该恢复失败时必须保持变更阻断并人工处置，不能继续切流。

DNS 已指向新环境后，优先手动运行 GitHub Actions 的 `Verify Production Cutover`，输入与发布完全一致的 `release_id` 和确认值。它会先确认同一证据目录已存在最终数据库迁移核验报告，并读取权限为 `600` 或 `400` 的 `/opt/guoxue/shared/infrastructure-intake.json`，再通过 SSH 只读重跑主机预检、新基础设施接入、客户端配置绑定、完整环境验收、公网运行时验收、版本保留审计；公网运行时报告会由运行主机系统解析器、DNSPod `119.29.29.29` 和 AliDNS `223.5.5.5` 三路独立解析 API、H5、后台和静态资源域名，分别保留 CNAME 链与公网地址快照，并执行唯一 HTTPS 入口的 TLS 握手，验证系统信任链、域名匹配、至少 14 天剩余有效期及 SHA-256 指纹，不能只靠接入清单中的人工勾选。三路解析必须覆盖完全相同的唯一域名且均不得命中私网、保留地址或旧入口；任一路仍看到旧地址、缺少域名或解析失败都必须判定 `BLOCK`。运行主机和 CI 因此必须允许到上述两组受控公共解析器的 DNS 出站访问，防火墙拦截时先修复网络策略，不得降级为单路解析。腾讯部署还会通过 CVM 实例角色审计目标监控、CLB、CDN 与证书，并把三路运行时 DNS 快照逐一与腾讯云返回的 CLB 公网 VIP/分配域名及 CDN CNAME 交叉校验；只要任一路域名仍落到旧入口，即使页面可访问也必须判定 `BLOCK`。标准部署聚合九份证据，腾讯部署聚合十份证据；它不启动容器、不执行数据库迁移、不修改 DNS。工作流成功且 `launch-decision.json` 为 `GO` 才能进入最终人工签字。人工签字必须使用 `finalize-launch-acceptance.mjs --init` 生成的结构化验收单，归档每项现场证据，并由不同技术与业务负责人签核；只有随后生成的 `final-launch-decision.json` 为 `GO` 才能宣布正式上线。GitHub 暂不可用时，才按本节与 8.1 节的等价命令人工执行。

保留兼容的基础 Bash 冒烟入口：

```bash
export PUBLIC_API_URL='https://新API域名'
export PUBLIC_H5_URL='https://新H5地址/'
export EXPECTED_ORIGIN='https://新H5域名'
bash scripts/migration/smoke-test.sh
```

人工验收至少覆盖：

- 登录、刷新登录态、搜索、客服、消息、举报和投诉。
- 首页、发现、圈子、工具、个人中心。
- 课程购买、商品下单、支付回调、退款、库存、采购、发货、物流和售后。
- 古籍阅读/听书、文章、视频、直播、智能体和语音通话。

- H5 手机/平板/PC、小程序和 App 真机。

## 8. DNS 切换与回滚

先切 API/H5，观察 15–30 分钟，再切管理端/CDN。持续观察 5xx、登录、CORS、数据库连接、慢查询、队列积压、支付/退款回调、IM、直播和 VOD。

以下任一情况应立即评估回滚：

- 支付、退款或订单出现错账、重复入账。
- 表计数或关键业务抽样不一致。
- 大面积登录失败、证书/CORS 错误。
- 核心回调持续失败且 15 分钟内无法修复。

回滚只恢复 DNS 和旧站写入，不得用旧库覆盖新库。切流期间的新数据要单独导出、对账和补偿。

### 8.1 新服务器应用版本回滚

应用版本只能回滚到服务器上“曾成功激活、保留原始固定包、目录仍能逐文件验真”的版本。不得从 Git
分支重新构建旧版本，也不得直接修改 `current` 软链接。执行入口必须来自当前可信版本：

```bash
TARGET_RELEASE_ID='release-20260731-001'
sudo ROOT_DIR=/opt/guoxue \
  ENV_FILE=/opt/guoxue/shared/.env.production \
  DEPLOY_TARGET="$DEPLOY_TARGET" \
  NODE_ROLE=operations \
  bash /opt/guoxue/current/scripts/release/rollback-fixed-release.sh \
  "$TARGET_RELEASE_ID" "$TARGET_RELEASE_ID"
```

脚本会依次验证保留包 SHA-256、固定包逐文件清单、已部署目录与保留包清单一致性、发布成功历史、
`current/.release-id`、兼容指针一致性和数据库迁移边界；随后以 `--skip-migrate` 启动目标版本。只有健康部署成功后
才原子切换权威 `current`，数据库、共享密钥、证书、备份和 Compose 数据卷不会回退。

若目标版本早于最近一次数据库迁移，默认阻断。只有完成数据库架构向后兼容评审并保留书面结论后，
才可临时增加 `ALLOW_SCHEMA_COMPATIBLE_ROLLBACK=reviewed`。该变量不是通用跳过开关，不能用于发布历史
缺失、保留包缺失、目录被篡改或目标版本从未成功上线的情况。

服务器至少保留当前版本、上一个已验证稳定版本、最近一次执行数据库迁移的版本及最近 5 个固定包；
切流和回滚窗口结束前禁止自动清理 `/opt/guoxue/releases`、`/opt/guoxue/release-packages` 和
`/opt/guoxue/release-evidence`。

首次正式激活、数据库最终对账和 DNS 切流完成后，优先手动运行 GitHub Actions 的
`Verify Production Cutover`。GitHub 暂不可用时，只允许调用固定发布包内的同一只读脚本；不要再人工拼接各个审计命令：

```bash
TARGET_RELEASE_ID='release-20260731-001'
DEPLOY_TARGET='tencent' # 自建 PostgreSQL/Redis 时为 standard
sudo PLATFORM_ROOT=/opt/guoxue \
  RELEASE_ID="$TARGET_RELEASE_ID" \
  MAX_AGE_HOURS=24 \
  DEPLOY_TARGET="$DEPLOY_TARGET" \
  bash /opt/guoxue/current/scripts/release/verify-production-cutover.sh
```

该脚本核对 `current`、兼容版本指针、共享文件权限、固定包源提交和最终数据库证据，随后统一刷新客户端配置绑定、
正式环境、新基础设施、主机、公网运行时及版本保留证据；腾讯部署还会生成目标云资源现场审计，最后按部署架构聚合九份或十份机器证据。它不启动/停止容器、不执行数据库迁移、
不修改 DNS。报告只列出受保护版本、可评审清理候选和磁盘余量，不执行删除。任何清理必须在回滚窗口结束后，依据
报告逐项人工复核，且不得删除当前版本、上一个稳定版本、最近一次数据库迁移版本及其固定包和证据。
最终聚合报告必须为 `GO`；主机预检、新基础设施接入、包、发布目录、客户端配置绑定、数据库迁移对账、完整环境、公网运行时、版本保留九份基础证据，以及腾讯部署必需的云资源现场审计，任一缺失、超过现场
有效期、允许降级或与 `TARGET_RELEASE_ID` 不一致都会输出 `BLOCK` 并以非零状态退出。

正式演练前可先执行只读复核。该模式仍检查全部可信链和数据库迁移边界，但不启动容器、不切换版本：

代码合并前，`pnpm release:test-rollback` 会在 Windows 验证两类前置阻断，并在 GitHub Actions 的 Ubuntu
`release-safety` 任务中补充验证数据库迁移边界与只读回滚不改变 `current`、发布历史。自动化测试仅用于提早发现
脚本回归，不能替代下列新服务器只读复核，也不能作为 `release-evidence/rollback-*` 的现场验收证据。

```bash
DEPLOY_TARGET='tencent' # 必须与首次初始化和当前线上架构一致
sudo ROOT_DIR=/opt/guoxue \
  ENV_FILE=/opt/guoxue/shared/.env.production \
  DEPLOY_TARGET="$DEPLOY_TARGET" \
  NODE_ROLE=operations \
  ROLLBACK_VERIFY_ONLY=true \
  bash /opt/guoxue/current/scripts/release/rollback-fixed-release.sh \
  "$TARGET_RELEASE_ID" "$TARGET_RELEASE_ID"
```

## 9. 旧资源下线条件

- 新 DNS 稳定超过 72 小时。
- 所有第三方回调验证成功。
- 新库完成自动备份和至少一次恢复演练。
- 订单、支付、退款、佣金、库存和物流连续三天对账正常。
- 旧数据库、对象存储和日志完成不可变归档。
- 负责人书面确认回滚窗口结束。
