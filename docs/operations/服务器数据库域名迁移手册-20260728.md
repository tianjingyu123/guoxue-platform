# 服务器、数据库与域名迁移手册

适用范围：后端 API、H5、管理端、小程序、App、PostgreSQL、Redis、对象存储、直播/点播、支付、物流与第三方回调。

目标是“先并行、再切流、可回滚”。旧服务器和旧域名至少保留 72 小时，不在 DNS 切换当天销毁任何资源。

## 一、迁移前需要确定的信息

将以下信息填入迁移工单，不要把密码、私钥提交到 Git：

- 新服务器：云厂商、地域、系统版本、CPU/内存/磁盘、内外网 IP、SSH 用户。
- 新数据库：厂商、PostgreSQL 版本、地址、端口、库名、TLS 要求、备份保留策略。
- 新 Redis：地址、端口、TLS、是否允许清空会话。
- 新域名：API、H5、管理端、静态资源/CDN、直播推流、直播播放、点播。
- DNS/CDN：服务商、当前 TTL、证书签发方式、是否接 WAF。
- 对象存储：COS Bucket、地域、CDN 域名、跨域规则、旧文件是否原址保留。
- 第三方账号：微信公众平台/小程序/商户平台、支付宝、银联、汇付、快递100、腾讯云 IM/直播/VOD/SMS。

建议域名结构：

| 用途 | 示例 |
| --- | --- |
| API 与 H5 | `https://api.example.com`、`https://api.example.com/h5/` |
| 管理端 | `https://admin.example.com` |
| 静态资源 | `https://cdn.example.com` |
| 直播播放 | `https://live.example.com` |
| 直播推流 | `push.example.com` |

## 二、现在已经具备的迁移保护

- 公开域名统一由 `PUBLIC_DOMAIN`、`PUBLIC_API_URL`、`PUBLIC_H5_URL`、`PUBLIC_ASSET_ORIGIN` 控制。
- 品牌配置即使 Redis 或数据库仍缓存旧域名，也会在返回前应用部署环境中的公网地址。
- 讲师名片、报告、赛事、协议页、共读等分享链接统一通过 `buildH5Url` 生成。
- 支付、物流、汇付回调均使用显式环境变量，不从浏览器请求猜域名。
- 数据库迁移脚本默认只读导出、校验后恢复到空库；不含自动删库。

## 三、T-24 小时：新环境预部署

1. 把 DNS TTL 调低到 300 秒。
2. 新服务器安装与当前生产一致的 Node.js、pnpm、PM2 或 Docker、Nginx、PostgreSQL 客户端。
3. 创建新数据库空库；启用扩展：

   ```sql
   CREATE EXTENSION IF NOT EXISTS vector;
   CREATE EXTENSION IF NOT EXISTS pg_trgm;
   CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
   ```

4. 从 `docs/operations/新生产环境变量模板.env.example` 复制到服务器私有配置目录，填入真实值。
5. 运行环境检查：

   ```bash
   node scripts/migration/check-env.mjs /secure/path/production.env
   ```

6. 用新域名签发证书，但暂不切 DNS。可先通过本机 hosts 或临时预览域名测试。
7. 同步对象存储/CDN 文件，并抽检图片、音视频、课程封面、古籍封面和用户上传文件。
8. 新服务器部署同一 Git 提交，记录提交 SHA、构建时间和环境文件校验摘要。

## 四、数据库全量迁移

### 4.1 导出

在能连接旧数据库的受控机器执行：

```bash
export SOURCE_DATABASE_URL='postgresql://...旧库...'
export MIGRATION_BACKUP_DIR='/secure/backups/guoxue-migration'
bash scripts/migration/export-postgres.sh
```

产物包括：

- PostgreSQL custom-format dump。
- SHA-256 校验文件。
- 每张 public 表的精确行数。
- 数据库版本、扩展、Prisma 迁移数等清单。

导出脚本不会清理旧备份，也不会修改源库。

### 4.2 恢复

只允许恢复到新建空库：

```bash
export TARGET_DATABASE_URL='postgresql://...新库...'
export BACKUP_FILE='/secure/backups/guoxue-migration/xxx.dump'
export RESTORE_CONFIRM='新数据库名'
bash scripts/migration/restore-postgres.sh
```

如果目标 public schema 已有表，脚本会拒绝执行。不要通过修改脚本绕过；应重新创建空库。

### 4.3 核对

```bash
export TARGET_DATABASE_URL='postgresql://...新库...'
export SOURCE_COUNTS_FILE='/secure/backups/guoxue-migration/xxx.table-counts.tsv'
bash scripts/migration/verify-postgres.sh
pnpm --filter @guoxue/server exec prisma migrate status
```

必须满足：

- 所有 public 表精确行数一致。
- `vector`、`pg_trgm` 已启用。
- Prisma 迁移状态为最新。
- 用户、订单、支付、退款、课程、古籍、圈子、文章、视频、直播、商家库存等关键业务抽样一致。

## 五、停写窗口与增量策略

当前脚本采用“短暂停写 + 最终全量快照”，不假设逻辑复制已配置。

1. 提前公告 10–30 分钟维护窗口。
2. 旧站进入只读/维护状态，暂停：下单、支付、退款、发货、库存调整、内容发布、评论、积分与佣金任务。
3. 停止旧服务器的 BullMQ/定时任务，避免迁移期间继续写库。
4. 做最终全量导出、恢复和计数校验。
5. 新服务器先启动单实例，执行迁移状态和冒烟检查。
6. 校验通过后再切 DNS。

若未来要求“零停机”，需另行配置 PostgreSQL 逻辑复制或云数据库 DMS/ DTS；未完成复制演练前不要临时启用。

## 六、Redis、队列和会话

- 缓存、验证码、短期会话不建议整体迁移；新 Redis 可从空实例启动。
- JWT 使用相同 `JWT_SECRET`，并保留 `JWT_PREVIOUS_SECRETS`，可减少用户被迫重新登录。
- BullMQ 切换时必须确保旧、新消费者不同时执行同一任务。
- 对支付补偿、退款、佣金、物流订阅等任务，切换前记录待处理数量，切换后核对一次。
- 幂等键和分布式锁若存 Redis，必须确认业务是否允许清空；不允许则安排 RDB/AOF 导入。

## 七、必须同步修改的第三方控制台

所有回调使用新 `PUBLIC_API_URL`：

| 系统 | 环境变量 | 路径 |
| --- | --- | --- |
| 微信支付 | `WECHAT_PAY_NOTIFY_URL` | `/api/v1/shop/pay/notify` |
| 微信退款 | `WECHAT_PAY_REFUND_NOTIFY_URL` | `/api/v1/shop/refund/notify` |
| 支付宝 | `ALIPAY_NOTIFY_URL` | `/api/v1/shop/alipay/notify` |
| 银联 | `UNIONPAY_NOTIFY_URL` | `/api/v1/shop/unionpay/notify` |
| 汇付 | `HUIFU_NOTIFY_URL` | `/api/v1/huifu/notify` |
| 快递100 | `KUAIDI100_CALLBACK_URL` | `/api/v1/shop/logistics/kuaidi100/callback` |
| 腾讯 VOD | 控制台回调 | `/api/v1/videos/vod/callback` |
| 腾讯直播 | 控制台回调 | `/api/v1/live/callback` |
| 腾讯直播审核 | 控制台回调 | `/api/v1/live/audit/callback` |
| 腾讯 IM | 控制台回调 | `/api/v1/im/callback` |

还需更新：

- 微信公众号：网页授权域名、JS 接口安全域名、业务域名。
- 微信商户平台：JSAPI 支付授权目录、H5 支付域名。
- 微信小程序：request/upload/download/socket 合法域名。
- App：Universal Link/App Link、隐私政策与服务协议域名。
- COS/CDN：CORS 来源、防盗链、回源 Host、证书。
- 短信、邮件、AI 服务：如存在 IP 白名单，同步加入新服务器出口 IP。

第三方平台更新完成后，旧回调地址暂时保留并返回 2xx，但旧系统不得重复入账。支付/退款回调必须继续依赖业务幂等。

## 八、Nginx、CORS、Cookie 和 WebSocket

- `CORS_ORIGIN` 使用逗号分隔，切换期同时包含新旧 H5、管理端来源；不得使用 `*`。
- `WS_CORS_ORIGIN` 同步包含实际 WebSocket 页面来源。
- `COOKIE_DOMAIN` 只有在确实使用跨子域 Cookie 时设置；不同主域无法共享 Cookie。
- 新旧主域并行时优先使用 Authorization/JWT，不依赖跨主域 Cookie。
- Nginx 必须正确转发 `Host`、`X-Forwarded-Proto`、真实 IP 和 WebSocket Upgrade。
- 上传大小、SSE 超时、直播/音频 Range 请求配置须与旧站一致。

## 九、切流前验收

通过 hosts 或预览域名执行：

```bash
export PUBLIC_API_URL='https://新API域名'
export PUBLIC_H5_URL='https://新H5地址/'
export EXPECTED_ORIGIN='https://新H5域名'
bash scripts/migration/smoke-test.sh
```

人工验收至少覆盖：

- 登录、验证码、刷新登录态。
- 首页/发现/圈子/工具/个人中心。
- 搜索、客服、消息、举报投诉。
- 课程购买、商品下单、支付回调、退款、库存、发货、物流轨迹。
- 古籍阅读/听书、文章、视频、直播、智能体、语音通话。
- 分享链接、海报二维码、微信内打开、小程序跳转、App 深链。
- 管理端、商家端、从业者工作台。
- H5 手机、平板、PC；小程序和 App 真机。

## 十、DNS 切换

1. 记录切换前 DNS 截图与旧解析值。
2. 先切 API/H5，观察 15–30 分钟；再切管理端/CDN 等。
3. 监控：5xx、登录失败、CORS、数据库连接、慢查询、队列积压、支付/退款回调、短信、IM、直播/VOD 回调。
4. 旧站保持可快速恢复，禁止立刻停机或删除旧库。
5. 72 小时内每天核对订单、支付、退款、佣金、库存与物流数据。

## 十一、回滚标准和步骤

出现以下任一情况立即评估回滚：

- 支付、退款或订单存在错账/重复入账。
- 数据库表计数或关键业务抽样不一致。
- 大面积登录失败、CORS/证书错误。
- 回调持续失败且不能在 15 分钟内修复。

回滚步骤：

1. 新站停止写入和队列消费者。
2. DNS 恢复旧解析。
3. 恢复旧站写入和队列消费者。
4. 导出新站切流期间产生的数据，形成补偿清单；严禁直接覆盖旧库。
5. 对支付、退款、库存、佣金逐单补偿并留审计记录。

## 十二、旧资源下线条件

同时满足后才允许下线：

- DNS 已稳定超过 72 小时，旧域名访问量接近零。
- 所有第三方回调均已验证新地址成功。
- 新库至少完成一次自动备份和一次恢复演练。
- 订单、支付、退款、库存、物流、佣金连续三天对账正常。
- 旧数据库、对象存储和日志已做不可变归档。
- 负责人书面确认回滚窗口结束。
