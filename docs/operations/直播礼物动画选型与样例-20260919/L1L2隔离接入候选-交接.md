## 二、真实链路核实（先调查后实现）

### 2.1 服务端何时确认礼物成功

`apps/server/src/modules/live/live.service.ts::sendGift`：

1. 校验房间可见性、`status === 'LIVING'`、主播 `allowGift`；
2. 幂等键命中已有记录 → 直接返回该记录，**不再广播**；
3. `prisma.$transaction` 内：`coin.assertLiveGiftSpendAllowed` → `coin.spend` → `giftRecord.create` → `revenue.record`（主播分成 0.5）；
4. **事务提交成功即确认**，随后才 `im.relayLiveGift`（`void ... .catch()`，广播失败只记日志，不影响交易）。

控制器 `live.controller.ts:815` 直接 `return this.svc.sendGift(...)`，`utils/request.ts` 解包 `body.data` —— **客户端拿到的就是完整 giftRecord**。

### 2.2 两条路径与字段清单

| 路径 | 触发 | 携带字段 |
| --- | --- | --- |
| **送礼响应** | 本人送礼，HTTP 201 | `id`(=recordId)、`userId`、`liveRoomId`、`toUserId`、`giftId`、`quantity`、`totalCoin`、`createdAt`、`user{id,nickname,avatar}`、`gift{id,name,icon,level}` |
| **房间广播** | `created === true` 时发一次 | `TIMCustomElem.Data = {type:'LIVE_GIFT', recordId, giftId, giftName, quantity}`；发送者取信封 `from`/`nick`，时间取信封 `time`（秒），房间由群 `to === groupId` 限定 |

自己送礼时两条路径带**同一 recordId** 先后到达 → 按 recordId 去重只展示一次。

**广播缺的字段与补法（不改协议）**：`roomId` 由订阅方注入；`icon`/`level` 用 `giftId` 回查 `/live/gifts`（该接口 `listGifts` 无 select，返回完整 Gift 含 `level`），查不到按 `BASIC` 降级，不猜测。

### 2.3 稳定标识结论

**`giftRecord.id` 就是稳定唯一标识，已经贯通到两条路径，不需要任何后端改动。**
缺口纯在客户端：`sendLiveGift` 原来只 `Number(value?.totalCoin)`，把整个记录丢了。本轮补回。

`normalizeFromSendResponse` / `normalizeFromTimMessage` 在缺 `recordId` 或数量非法时**返回 `null`，不展示**，不用昵称、礼物名或客户端时间拼假标识。

### 2.4 断线重连是否重放历史

- 直播群由 `live.service.ts:576` 建为 **`AVChatRoom`**（直播大群）。
- `composables/useTim.ts` 只订阅 `MESSAGE_RECEIVED`，两个观看页都**没有**为直播群调用 `getMessageList`/`getGroupHistory`。
- 因此**源码层面没有历史重放路径**。

SDK 侧重连是否补发本轮未实测，**去重按最坏情况设计**：假定可能重复，recordId 去重 + 事件过期阈值（15 秒）双保险，重连补发的老消息即使绕过去重缓存也会被过期闸挡住。

### 2.5 现有 H5 是否已经播放一次

是。`watch/index.vue` 原来在送礼成功后本地 `giftFlyers.push` + 4 秒 `setTimeout` 清除，**只有自己送礼时出现，别人的礼物完全看不到**（群消息过滤条件是 `m.payload?.text`，礼物事件在 `payload.data`，整条被漏掉）。

本轮**移除**这套本地飘屏，改为与广播同走一条编排链路，避免同一件事出现两套动效。测试用例 `H5 不再保留第二套本地飘屏` 对此做了源码断言。

## 三、去重、合并、过期策略与理由

全部集中在 `apps/mobile/src/pkg-live/gift-feed.ts`。

| 策略 | 取值 | 理由 |
| --- | --- | --- |
| 去重键 | `recordId` | 服务端唯一且稳定，两条路径同源 |
| 去重缓存 | 512 条 + **10 分钟有效期** | 有容量也有有效期，长场直播不无限增长；过期淘汰后由事件过期闸兜底 |
| 事件过期 | 早于当前 15 秒直接丢弃 | 迟到、乱序、重连补发的老消息再播已无意义；与去重构成双保险 |
| 合并键 | `roomId \| userId \| giftId` | 三者都相同才合并，**不跨房间、不跨用户、不跨礼物** |
| 合并窗口 | 3 秒 | 超窗口后**收掉旧条再开新条**（渲染键带轮次），不同键覆盖——覆盖会让上一轮累计数凭空消失 |
| 数量口径 | `giftRecord.quantity` 是**单次数量** | 已核实 `sendGift(roomId,userId,giftId,quantity)` → `giftRecord.quantity = quantity`，不同记录相加不翻倍 |
| 队列上限 | 24 | L1/L2 各 3 条车道、单条最长驻留 3.2 秒 ⇒ 约 12 秒积压；再长就不是"实时反馈"了 |
| 溢出处理 | 优先丢最旧 L1，累计成一条"另有 N 份心意已合并" | 只丢**视觉效果**；公屏与交易记录不受影响 |
| 车道 | L1 3 条 / L2 3 条 | 同屏节点不堆积 |
| 切房 | `enterRoom()` 清展示 + 清去重 + epoch 自增 | 旧房间迟到事件按 `roomId` 拒绝 |
| 后台 | 超过 8 秒回前台 → 丢弃全部积压 | 不集中补播 |
| 层级 | `BASIC`→L1；`MID`/`HIGH`/`TOP`→L2 | 后端 `Gift.level` 原样使用；**本轮不做 L3**，HIGH/TOP 暂以 L2 呈现（描边随层级加强），不静默丢掉高价值礼物的反馈 |

**边界**：`GiftFeed` 不判断送礼成败、不扣费、不改余额、不发 IM、不写公屏业务记录。展示数量不是财务统计。

## 四、各端接入情况与展示层实现

| 端 | L1 轻量 | L2 连击 | 减少动态效果 |
| --- | --- | --- | --- |
| App（nvue） | 左下气泡，2.2 秒 | 左侧横幅，数字脉冲 | **无系统偏好来源**（见下） |
| H5 | 右下气泡 | 左上横幅 | ✅ `@media (prefers-reduced-motion: reduce)` + `matchMedia` 驱动编排层 |
| 微信小程序 | 同 H5 模板 | 同 H5 模板 | ❌ 无该能力，保持默认（不假装支持） |

**nvue 动效做法**：全仓两个 `.nvue` 文件里**没有任何 `@keyframes` 或 `transition`**；`watch/index.nvue` 既有的 `likeParticles` 是 `setInterval(55ms)` 帧驱动 + `:style` 计算。本轮沿用同一套做法，并保证**每一帧的终态都是正确状态**——定时器被系统压制时元素停在可读的最终样式，不会卡在半透明。

**长昵称/小屏**：nvue 用 `:lines="1"` + 固定车道宽度截断；vue 用 `text-overflow: ellipsis` + `max-width`。
**大字体**：nvue 文本不随系统字体缩放（weex 渲染层行为），本轮用固定车道宽度 + 截断保证不撑破布局，**未验证系统大字体下的真机表现**。

**不遮挡关键操作**：礼物层位置避开顶部退出/举报、右侧社交栏（好物/心意/点赞/连麦/更多）、底部输入与分享条。nvue 侧礼物层模板里**没有任何 `@click`/`@tap`**；vue 侧三个容器都声明 `pointer-events: none`。两条都有测试断言。

因此 nvue 帧驱动动效的真机表现、与直播视频层的叠加顺序、低端机连续播放、系统大字体、真实后台挂起恢复，**全部未验证**。

**桌面浏览器不能代替 nvue 真机验证**，上面的 H5 构建成功也不构成 nvue 渲染结论。
