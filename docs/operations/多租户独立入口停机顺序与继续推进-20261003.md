# 独立入口停机顺序与继续推进

本批继续推进一期剩余运维门槛，仍限本地隔离候选，没有获得主线接收、远端推送、云写入、生产迁移、真实收费或渠道登记的新授权。此前微页面和品牌资源冻结保持原样，见 [上一批交接](多租户微页面消费与品牌小程序补齐-20261003.md)。

## 问题及结果

原lease-main在启用Nest退出钩子之外，另注册SIGINT/SIGTERM监听，收到事件即并行发起两库断开；数据库释放与HTTP关闭缺少顺序保证。第一阶段修复交给同一Nest生命周期，26套验证通过，受测源码为 `0f160a3cc2241331fa5f7062014a423db5dbbf50`。继续检查发现，HTTP关闭只等待连接结束；客户端主动断线时，后台控制器与数据库事务可能尚未完成。因此第一阶段结果只证明有连接请求的关闭顺序，不能代表断线业务已经排空。

本次进一步补全：beforeApplicationShutdown标记退出，HTTP入口拒绝新请求，全局拦截器不再启动新的控制器业务；每项已经进入业务的操作独立计数，正常完成、异步失败或同步抛错均只释放一次。HTTP关闭后onApplicationShutdown仍等待业务计数归零，之后才停用运行状态并释放该实例控制面和业务连接。客户端连接关闭不会释放业务计数。连接释放缓存同一Promise，重复调用不建立另一退出任务；两连接均尝试释放，错误统一脱敏。

通过HTTP停机入口的新请求返回503、private/no-store、Connection: close和Retry-After；客户端仍不自动重发写请求，应先核已有记录。在停机前已通过入口、但尚处于正文解析或认证阶段的请求，也不能在停机后新启动控制器业务。退出阶段不提前撤销已经进入控制器处理的业务上下文；这些请求仍逐次检查原授权、围栏和事务约束，授权变化或事务失败仍按原规则拒绝。没有增加HTTP停机、身份签发或维护路由，也没有关闭数据库服务、其他客户实例或改变部署绑定。

## 本地演练与边界

新增验证直接启动自己的编译lease-main。通过真实PG资源行锁使一笔合成商品订单进入事务等待；开始退出后核新订单及公开请求503、B客户查询正常；放行HTTP关闭后核端口不接受新连接、原事务仍等待且未释放数据库；再释放行锁，原订单、库存和来源完成同事务提交。确认HTTP关闭后才释放连接，重复退出事件只执行一次链路。重新启动相同部署，原请求键核对同一待支付单，库存不再扣减；另一客户令牌仍拒绝。

第二组演练在订单进入真实PG行锁等待后取消客户端请求，再启动退出。HTTP关闭时精确记录一项仍在途业务且两库未释放；同一实例此前400异常请求没有泄漏计数。释放锁后，断线订单仍提交一条待支付事实、一次库存扣减，业务归零才断开两库。第三次启动后用断线请求原键核对同一订单，库存保持不变。客户B在此期间保持可访问。专项16组通过，最新冻结26套及逐源归档正在执行。

合成商品必须提供正文和本应用图片才能上架；初始测试夹具缺这些条件而被400拒绝，修正夹具后才进入实际停机演练。没有修改经营准入来使测试通过，也不把初始运行记录伪称成功。

包装器仅存在pilots，主动触发Node事件并暂停生命周期以观察重叠窗口；正式入口没有IPC控制。Windows不支持Linux原生SIGTERM，因此本结果不能关闭Linux/systemd真实信号、cgroup/账户/网络隔离门槛。实现顺序依据 [Nest生命周期](https://docs.nestjs.com/fundamentals/lifecycle-events)，HTTP等待依据 [Node 24 server.close](https://nodejs.org/download/release/latest-v24.x/docs/api/http.html#serverclosecallback)，平台限制见 [Node进程信号](https://nodejs.org/download/release/latest-v24.x/docs/api/process.html#signal-events)。本机安装版本Nest/Express适配器源码也已核对该关闭顺序。

Linux模板的45秒退出窗口尚未经真实最长HTTP/事务/供应商请求验证。后续须同网关及业务超时、外部任务停派、请求记录核对联合演练；强制结束不能被表述为请求均已完成，未知外部结果仍不自动重放。停机排空也不能替代数据库写围栏及迁出冻结。
