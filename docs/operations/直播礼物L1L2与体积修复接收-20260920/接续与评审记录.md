### 2.3 本轮发现并修复的缺陷（`697f7bda`）

**派发阶段用同一个 `comboKey` 覆盖了已在屏的连击条。**

`drain()` 对 L2 事件直接调 `openCombo()`，而 `openCombo` 无条件 `this.combos.set(key, slot)`。
当队列里堆了两条以上**同房间 + 同用户 + 同礼物**的 L2 事件时，后一条会顶掉前一条的 slot，
前一条的 `renderKey` 从此再也收不到 `hideCombo`：

1. 同一个人送的同一份礼物被拆成并排的多条各 ×1，**而不是合并成 ×N** —— 直接违反「多笔真实记录正确合并」；
2. 旧连击条**永久留在礼物层上**，只有切房 / 终态 / 卸载的 `clearAll` 能清掉；
3. nvue 端更重：`giftCombos` 里的残留节点让帧循环的 `alive` 恒为 `true`，
   **55 ms 的 `setInterval` 停不下来**，真机上持续占用主线程并耗电。

**触发路径**（默认配置，无需构造）：切后台或锁屏期间同一观众连送同一礼物 ≥2 笔、8 秒内回前台；
或 3 条连击车道占满时同组合排队、车道释放后一起派发。

**复现证据**（修复前，`comboHoldMs` 缩短为 60 ms 以便观察）：

```
resume 后屏上:   [ g9#1 → 1, g9#2 → 1, g9#3 → 1 ]     ← 3 笔被拆成 3 条
到期后屏上残留: [ g9#1 → 1, g9#2 → 1 ]                ← 只有最后一条收到 hideCombo
snapshot: { comboActive: 0, timers: 0 }               ← 编排层以为已清空，展示层还挂着 2 个节点
```

修复后同一脚本：

```
resume 后屏上:   [ g9#1 → 3 ]                          ← 合并为一条 ×3
到期后屏上残留: []
```

**修复方式**：把合并逻辑收成 `mergeCombo()` / `admitCombo()` 两个私有方法，
`push()` 与 `drain()` 共用同一口径 —— 同组合在窗口内并入现有连击条，超窗口先收掉旧条再另起一轮，
都没有才新开车道；已在屏的组合不再受 `comboLanes` 限制（并入不占新车道）。
派发阶段的合并只发 `merged` 指标、**不计** `stats.merged`（那条记录在 `push` 时已计入 `accepted`，两处都加会重复计数）。

改动范围：`apps/mobile/src/pkg-live/gift-feed.ts`（+43 / −8），`tests/release/live-gift-feed.test.mjs`（+52）。
未触碰两端页面、未触碰交易与公屏。
