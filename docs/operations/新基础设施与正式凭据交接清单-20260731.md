更新时间：2026-08-01
适用范围：新服务器、新 PostgreSQL、新 Redis、新域名、对象存储、第三方平台、多端发布。
执行仓库：`D:\gx-deploy-91`

## 1. 交接原则

- 本清单只记录字段名、资源编号、负责人、状态和验证结果，不记录密码、Secret、私钥、证书正文或数据库完整连接串。
- 敏感值只能由负责人写入新服务器私有配置、云密钥管理服务或权限为 `600`/`400` 的 `/opt/guoxue/shared/.env.production`。
- 只能用最新的 `pnpm release:prepare-infra-intake` 生成 `schemaVersion: 2` 的现场私有清单，填实后保存到 `/opt/guoxue/shared/infrastructure-intake.json` 并设置 `600` 或 `400`；不得把旧版清单改一个版本号继续使用。该文件不含口令，但必须登记数据库与 Redis 主机名、对象存储 Bucket/地域、公开域名、至少两个权威 DNS NS、切流 TTL、证书生命周期方案和责任人，以及 `externalEndpoints` 中的回调 URL、第三方控制台、客户端合法域名逐项清单、责任人与证据，不得提交到 Git。`predeploy` 和 `launch` 门禁都会将这些非敏感资源标识与正式环境文件逐项绑定，防止两份配置各自合法却误连到不同环境。
- 接入清单的 `migration` 段必须登记源库/目标库/DNS 权限实测、迁移演练、停写负责人、UTC 维护窗口、旧环境保留确认与至少 `72` 小时回退期；采购阶段可保留未完成状态，`launch` 阶段任一项缺失都会阻断上线。
- 新资源确定部署架构后，先运行 `pnpm release:prepare-infra-intake -- --deploy-target tencent`（自建 PostgreSQL/Redis 改为 `standard`）安全生成本地私有清单；命令设置 `0600` 权限且拒绝覆盖已有文件。填写后运行 `pnpm release:audit-infra-intake -- --input config/release/infrastructure-intake.json --stage procurement`。
- 新生成的清单第一次运行采购阶段审计时，会按设计阻断“责任人和双人审批未登记”“权威 DNS 双 NS 委派未填实”“证书生命周期方案未填实”及“第三方换址责任未登记”，这不是脚本故障。除 `operations.backupOwner`、`cutoverOwner`、`rollbackOwner`、`technicalApprover`、`businessApprover` 外，还必须填写 `domains.authoritativeNameServers`、证书生命周期字段，以及 `externalEndpoints.owner`、`clientDomainAllowlistOwner`、`evidenceReference`；实际启用渠道的环境变量回调 URL 逐项放入 `callbackUrls`，腾讯 VOD、直播、直播审核和 IM 控制台回调按启用情况逐项放入 `controlPlaneCallbacks`。小程序和公众号合法域名逐项放入 `clientDomainAllowlistEntries`；门禁会按正式环境实际启用的 AppID 计算完整集合，未启用客户端保持不登记。技术与业务审批人不得为同一人。采购阶段不要求写入密码、Secret、私钥或完整连接串。
- 新资源购买完成、正式环境文件已经绑定，但尚未执行迁移演练时，必须在有锁定依赖的 CI 或构建机运行统一预接入门禁：`pnpm release:gate:predeploy -- --env-file <仓库外受控正式环境文件> --deploy-target tencent --infrastructure-intake <仓库外受控接入清单> --report-dir artifacts/release-audit/predeploy-<变更单号> --expected-branch <正式来源分支> --expected-commit <40位提交SHA>`。只有同目录脱敏报告 `predeploy-decision.json` 为 `GO` 才能进入耗时构建和迁移演练。该门禁会同时绑定源码身份、接入清单和正式环境，阻断占位资源、错误 SSH 指纹、证书未签发或未部署到目标入口、对象存储未实测以及数据库、Redis、域名、CLB、Bucket 错绑；最终 `launch` 还会阻断未演练证书续期/替换、未完成公网证书链握手、监控告警、恢复演练、迁移权限和旧环境保留。`release:audit-infra-intake --stage predeploy` 只用于排查单项失败，不能代替统一门禁。
- 禁止把敏感值发送到聊天、工单正文、截图、Git、构建日志或验收报告。
- 新旧环境必须并行。新环境通过全部门禁、数据对账和预览验收前，不切 DNS、不关闭旧站、不删除旧库。
- 每个资源都必须有“获取来源、负责人、到期时间、轮换方式、验证证据”五项信息。

状态统一使用：`待购买`、`待配置`、`待验证`、`已通过`、`不启用`、`受阻`。

### GitHub production Environment

- Secrets：`PROD_HOST_A`、`PROD_SSH_FINGERPRINT_A`、`PROD_HOST_B`、`PROD_SSH_FINGERPRINT_B`、`PROD_USER`、`PROD_SSH_KEY`、`DEPLOY_PORT`（非 22 时填写）。A 为纯业务节点（`NODE_ROLE=app`），B 为业务兼运维节点（`NODE_ROLE=operations`）；两个 SSH 指纹都必须从云厂商可信控制台或服务器本地控制台独立核对，禁止直接信任首次网络连接返回的指纹。
- Variables：`PUBLIC_H5_URL`、`VITE_API_URL`、`VITE_PUBLIC_H5_URL`、`VITE_PUBLIC_ASSET_ORIGIN`、`PRODUCTION_DEPLOY_TARGET=standard|tencent`、`PRODUCTION_DEPLOY_READY=false`。三项 `VITE_*` 必须分别等于正式配置中的 `PUBLIC_API_URL`、`PUBLIC_H5_URL`、`PUBLIC_ASSET_ORIGIN`。
- Protection rules：启用 Required reviewers；Deployment branches 只允许仓库默认分支。生产部署和切流后只读复核都持有生产 SSH 凭据，因此平台侧限制和仓库内机器门禁必须同时存在。
- 权限基线：凡读取 `PROD_SSH_KEY` 的生产任务只允许 `contents: read`，不得附带仓库写入或软件包写入权限。
- 新基础设施全部验收前不得把 `PRODUCTION_DEPLOY_READY` 改为 `true`。
- 生产发布只能从仓库默认分支发起，`production_confirmation` 必须与 `release_id` 完全一致，固定包提交 SHA 必须与本次 GitHub 源提交一致。`run_migration` 默认保持关闭；如确需开启，还必须填写 `migration_confirmation=migrate:<release_id>`。普通 push/tag 和非默认分支不触发生产部署。
- 手动生产任务会重跑锁定依赖安装、代码审计、测试和五端构建，再生成固定包、双端逐文件验真并原子切换 `current`。

## 3. P0：数据迁移与回滚资料

### PostgreSQL 整库迁移

- 源库只读账号或受控导出窗口。
- 演练导出使用默认 `MIGRATION_EXPORT_MODE=rehearsal`；最终归档必须设置 `MIGRATION_EXPORT_MODE=final`、`SOURCE_WRITES_FROZEN=true`，并以 `MIGRATION_FREEZE_CONFIRM=<真实源数据库名>` 二次确认。
- 导出时区、PostgreSQL 版本、扩展清单、表行数、归档清单和 SHA-256；归档清单必须记录 `export_mode=final` 与 `consistent_snapshot`，证明 dump 和逐表计数来自同一数据库快照。
- 最终停写或增量追平方案，以及明确的 T0 时间。
- 目标库恢复前快照、恢复后业务完整性校验和序列校验。
- 旧库至少保留 72 小时；回滚只恢复流量，不用旧库覆盖切流后产生的新数据。

## 6. 多端发布资料

### 微信小程序

- 管理员/开发者权限、合法 request/upload/download/socket 域名、业务域名、隐私保护指引、类目与备案。
- `externalEndpoints.clientDomainAllowlistEntries` 必须登记以下固定表面并使用纯 origin（不得带路径、查询参数或凭据）：`wechat-mini-request-api`、`wechat-mini-upload-api`、`wechat-mini-download-api`、`wechat-mini-download-assets`、`wechat-mini-socket-api`、`wechat-mini-business-h5`。前四类 API 入口绑定 `PUBLIC_API_URL`，静态下载绑定 `PUBLIC_ASSET_ORIGIN`，socket 绑定由 API 主机派生的 `wss://` origin，业务域名绑定 `PUBLIC_H5_URL` 的 origin。
- 体验版测试成员、审核账号、功能说明、支付商户号与 AppID 绑定。
- 首次发布前真机验证登录、支付、分享、web-view、客服、消息、举报投诉和隐私授权。

### 微信公众号

- 启用 `WECHAT_OFFICIAL_APPID` 时，`externalEndpoints.clientDomainAllowlistEntries` 还必须登记 `wechat-official-oauth-h5` 与 `wechat-official-js-sdk-h5`，两者均绑定 `PUBLIC_H5_URL` 的 HTTPS origin。
- 网页授权域名和 JS 接口安全域名必须在公众号控制台现场配置并截图归档；只填写接入清单、不做控制台实测，不能把 `clientDomainAllowlistVerified` 设为 `true`。

### 对象存储与 CDN 跨域

- `storage.corsAllowedOrigins` 必须逐项填写纯 HTTPS origin，不得使用 `*`、HTTP、路径、查询参数、片段、内嵌凭据或重复来源。当前浏览器上传统一经自家 API，不需要也不得为了迁移方便给 COS/CDN 开放浏览器写入口。
- `predeploy` 会把该清单与正式 `PUBLIC_H5_URL`、后台入口（由 `PUBLIC_API_URL/admin/` 派生）的唯一 origin 集合做精确指纹绑定；漏登、多登、仍保留旧域名或把 CDN 自身域名误当调用来源都会阻断。只有新 Bucket/CDN 已完成 H5 与后台跨域读取、私有读和签名过期实测后，才能把 `storage.corsConfigured`、`storage.signedUrlVerified` 设为 `true`。

### 对象存储旧文件迁移完整性

- `storage.objectMigration` 固定使用 `mode=copy` 与 `manifestAlgorithm=sha256-content-v1`。清单算法按对象键排序，以“对象键、字节数、文件内容 SHA-256”组成逐对象记录后再计算总清单 SHA-256；禁止用 COS/S3 分片上传的 ETag 代替文件内容摘要。
- 将旧桶和新桶分别同步到两个仓库外、权限受控且互不覆盖的临时目录；不得把临时目录、对象键清单、下载地址或访问凭据提交到 Git。运行 `pnpm release:inventory-storage -- --root <旧桶同步目录> --report <旧桶摘要.json>`，再对新桶运行同一命令。
- 运行 `pnpm release:compare-storage-inventory -- --source <旧桶摘要.json> --target <新桶摘要.json> --report <对象存储比对证据.json>`。只有输出 `GO`，且对象数、总字节数和内容清单 SHA-256 三项完全一致，才能把摘要字段写入私有接入清单并设置 `comparisonVerified=true`。
- 初次全量复制的结果只能用于演练；正式切流必须在停写后的最终增量复制完成后重新生成两份摘要。`launch` 会阻断空清单、摘要不一致、使用 ETag、缺少责任人/证据编号或提前释放旧桶。旧桶至少保留 `72` 小时且只读可恢复，确认后才能设置 `oldBucketRetentionConfirmed=true`。

### Android

- 正式 keystore、alias、密码托管位置、证书指纹、应用商店账号、隐私政策 URL、软著/备案材料。
- 禁止在聊天或仓库交付 keystore 密码；签名包必须记录 SHA-256、versionName、versionCode。

### iOS

- Apple Developer 团队权限、Distribution 证书、Provisioning Profile、Bundle ID、Associated Domains、隐私清单与 App Store Connect 资料。

### Harmony

- AppGallery Connect 权限、发布证书、签名 Profile、包名、隐私与备案资料；使用 DevEco/HBuilderX 生成受控签名 `.app` 并真机覆盖安装验证。

五端交付验真必须得到 `success: true`，且发布标识、源码提交、五类目录、文件数、字节数和 SHA-256 内容指纹全部一致。不能只看构建时生成的审计报告；拿错版本、漏文件或转交后内容被改动都会被阻断。

服务器准备阶段尚未完成首次正式激活时跳过第 7、8、11 项，第 9、10 项仍用于验收基础设施本身；不得伪造发布历史或用临时目录代替正式版本。首次激活后如尚无可回滚的前一成功版本，仅跳过第 7 项。
保留审计只生成候选清单，不删除任何文件；清理必须在回滚窗口结束后另行人工审批。
`launch-decision.json` 会绑定标准部署九份来源报告的 SHA-256；当 `deployTarget=tencent` 时，还会条件性强制绑定 `tencent-cloud-readiness.json`，共十份。任一报告缺失、过期、版本不一致或允许降级，结论均为 `BLOCK`。其中 `database-migration-verification.json` 必须来自第 5 项的 `final` 恢复核验，公网复核工作流只校验它，不会重新执行数据库迁移。`runtime-verification.json` 必须绑定本次 `infrastructure-intake.json` 的 SHA-256，并包含系统解析器、DNSPod `119.29.29.29`、AliDNS `223.5.5.5` 三路独立快照；三路必须覆盖相同入口、看到接入清单声明的同一组至少双 NS 权威委派、确认 A/AAAA 真实剩余 TTL 不超过清单计划值，并全部指向本次目标资源。任一路仍命中旧入口、NS 不一致、TTL 未收敛、返回不安全地址、缺少域名或不可访问都阻断上线。执行主机与 CI 必须预先放通到两组公共解析器的 DNS 出站访问，不得因网络策略失败而删除或跳过该门禁。

DNS 已指向新环境后，标准路径是手动运行 GitHub Actions 的 `Verify Production Cutover`，填写与本次发布完全一致的 `release_id`、确认值和证据有效期。它只读执行第 2、6、8、9、10、11 项，不启动或替换容器、不执行 Prisma 迁移、不修改 DNS；工作流必须显示成功且服务器 `launch-decision.json` 为 `GO`。如 GitHub 暂不可用，才按上面的等价命令人工执行并双人复核。

生产部署工作流还会使用 GitHub `production` Environment 的 `VITE_API_URL`、`VITE_PUBLIC_H5_URL`、`VITE_PUBLIC_ASSET_ORIGIN` 重建 Admin、H5、微信小程序、App、Harmony，并归档五端成品、`client-artifact-audit.json`、`client-artifact-verification.json` 与 `store-readiness.json`。审计报告会绑定源提交，并记录每一端的字节数和确定性 SHA-256 内容指纹；独立验真报告会重新计算同一批成品的文件数、字节数和内容指纹；商店报告会保留 23 项覆盖升级与提审检查的通过/阻断分类。小程序、App、Harmony 等提交物必须与两份成品报告指纹一致，商店报告必须在正式提审前达到 `23/23`。临时客户端环境文件不会归档，报告均不得包含任何配置值或签名口令。

同一任务还会生成仅含 SHA-256 指纹、发布标识和源提交的 `client-config-binding.json`，并把它、客户端审计报告和独立验真报告写入固定包。固定包验真必须逐端确认两份客户端报告的目录、文件数、字节数和内容指纹完全一致。服务器必须在构建前用共享生产环境重算并通过 `client-config-binding-verification.json`；这一步证明 CI 审计输入就是实际运行镜像的构建输入，任何差异都会阻断激活。

固定包验真会逐文件复核 `RELEASE-MANIFEST.json` 的大小和 SHA-256，并核对清单提交 SHA 与本次 GitHub 源提交一致；同时拒绝路径穿越、符号链接、清单外文件、疑似密钥、缺少运行文件及默认拒绝 `dirty` 包。包级验真报告不含业务凭据，可随变更单保存；生产包禁止使用 `--allow-dirty`。

正式激活入口还会在任何解压、写证据或启动容器之前强制校验完整的 40 位 `EXPECTED_COMMIT`。该值必须与本次 GitHub 源提交及固定包清单一致，禁止留空、使用短 SHA 或由现场人员临时猜测。

目录验真采用两阶段顺序：先在 `.candidate-*` 候选目录复核逐文件哈希、额外文件和共享证书链接，失败自动清理；通过后才原子落入 `releases/<release-id>`，随后对正式目录复核并生成归档证据。候选验真失败不得留下同名正式目录。

正式目录落盘后的部署失败不得靠人工删除目录恢复。再次激活完全相同的固定包时，脚本会比对候选包与既有正式目录的 `RELEASE-MANIFEST.json`，使用候选包内已验真的校验器再次逐文件复核正式目录，再从部署步骤可重入恢复；相同发布标识但清单不同、目录标识异常或目录被修改时必须阻断。失败任务会清理 `current.next`，不会提前切换当前版本。

容器存活不是发布成功的充分条件。`/api/v1/health/live` 必须返回运行实例的 `releaseId`，部署脚本只有在状态为 `alive` 且该值与本次 `RELEASE_ID` 完全一致时才继续；旧实例仍可响应、环境变量未注入或新容器未真正接管都会超时并进入自动镜像回滚。

完整健康检查失败同样视为部署失败，即使新容器已经通过轻量存活。脚本必须恢复部署前记录的旧镜像和旧 `RELEASE_ID`，并在回滚实例同时满足 `alive` 与旧版本身份后才结束；禁止先输出“部署完成”再执行后置验证。

激活和回滚均以 `current/.release-id` 作为当前版本的权威身份。兼容指针 `current-release-id -> current/.release-id` 会在切换前原子安装，随后才原子切换 `current`；生产复核必须同时验证真实目录、目录内发布标识和兼容指针三者一致，禁止手工改软链接或版本号文件。

`guoxue.service` 的启动、停止和重载必须经 `/opt/guoxue/current/scripts/release/current-compose.sh` 执行。该入口每次都会解析权威 `current`、验证其位于 `releases/<release-id>`、读取并校验 `.release-id` 后再注入 Compose，因此服务器重启后不得出现 `unversioned`，也不得把 setup 时的临时环境当作长期状态。

`preflight-host.sh` 是只读脚本，不会安装软件、修改防火墙、内核、磁盘或服务；任一 `FAIL` 都必须先处理。已有 Nginx/容器占用 80/443 的重复部署场景，只有在明确核实占用者后才能设置 `ALLOW_OCCUPIED_PORTS=true`。

新服务器还必须执行：`nginx -t`（如使用宿主机 Nginx）、`docker compose ps`、服务日志检查、备份首跑、告警试发、单节点摘除/恢复和隔离环境恢复演练。

回滚演练必须保留 `release-evidence/rollback-*` 证据，并确认：保留固定包与校验文件存在、目标版本在
`release-history.tsv` 中有成功记录、目标目录未被修改、`current/.release-id` 与兼容指针一致、健康检查成功后才切换 `current`。数据库迁移后的
旧应用版本只有通过向后兼容评审才能回滚；不得自动执行逆向 Prisma 迁移。

合并前统一执行 `pnpm release:test-rollback`：Windows 开发机验证非法版本号与二次确认不一致的前置阻断；
GitHub Actions 的 Ubuntu `release-safety` 任务还会验证数据库迁移边界和只读复核不改变 `current`、发布历史。
这些是脚本行为回归，不是生产现场证据；新服务器交接后仍必须执行下述只读复核并归档真实
`release-evidence/rollback-*` 报告。

`launch-decision.json`、按部署架构生成的九份或十份来源报告、五端成品、`client-artifact-audit.json`、`client-artifact-verification.json`、`store-readiness.json` 和固定包内的 `client-config-binding.json` 必须与本次变更单一并归档；来源报告 SHA-256（其中包含主机预检、数据库最终迁移核验、服务器重新生成的客户端配置绑定核验，以及腾讯部署的现场云资源审计）还必须与现场文件复核一致。任一 P0 项缺失、机器判定不是 `GO` 或证据归档不完整，结论只能是“预部署或隔离预览可用”，不得标记为“正式上线”。

纸面表格只便于现场查看，不能作为可执行门禁。机器证据为 `GO` 后，必须在同一证据目录初始化结构化人工验收单：

```bash
node /opt/guoxue/current/scripts/release/finalize-launch-acceptance.mjs \
  --release-id "$TARGET_RELEASE_ID" --evidence-dir "$EVIDENCE_DIR" --init
```

把每项现场截图、对账单、演练记录等证据文件放入 `$EVIDENCE_DIR`，填写生成的 `production-cutover-acceptance.json`：确认值必须为 `approve:$TARGET_RELEASE_ID`，九项检查全部为 `PASS`，技术与业务负责人必须为不同人员，签核时间和检查时间不得超过证据有效期。填写完毕后执行：

```bash
node /opt/guoxue/current/scripts/release/finalize-launch-acceptance.mjs \
  --release-id "$TARGET_RELEASE_ID" --evidence-dir "$EVIDENCE_DIR" \
  --max-age-hours 24
```

只有新生成的 `final-launch-decision.json` 为 `GO` 才代表正式上线门禁通过。该文件会绑定机器判定、人工验收单以及每份人工证据的 SHA-256；`launch-decision.json` 单独为 `GO` 只表示机器门禁通过，不能宣布正式上线。
