# 咨询停流单次派发与未知结果

## 本地实现范围

承接《咨询终态停流待办事务》，新增内部适配器、事务派发器及后台调度，已在 ConsultCallModule 注册；没有新增公共 HTTP 接口。

- 供应商动作：`RemoveUserByStrRoomId`，版本 `2019-07-22`。只发送原边界的 SDKAppId、字符串房间、两位参与者的房间隔离映射身份。
- 依据：[腾讯云移出用户接口](https://cloud.tencent.com/document/api/647/50426)。该响应只有 RequestId，不代表禁止重新进房，因此不构成资源释放证明。
- 请求前先提交 DISPATCHING 和 60 秒租约。两个节点竞争只有一个事务能认领。供应商网络等待不占用数据库事务。
- 请求成功只记 ACKNOWLEDGED；网络、HTTP、解析异常及不可信响应只记 UNKNOWN。没有重试循环，UNKNOWN 永不重新派发。
- 认领后进程中断或结果写库失败，保留 DISPATCHING；租约到期转 UNKNOWN，不重发。迟到回执不能把已转 UNKNOWN 的记录改成成功。
- SDKAppId、房间、凭据版本、保护时间、订单终态及发起者都与原记录核对。漂移拒绝，不用当前环境覆盖原范围。
- 错误仅输出固定码和汇总计数，不输出供应商原包、秘密、签名 headers 或请求正文。
- ACTIVE 额度不变化；没有增加完成或强制释放方法。

## 调度配置边界

`CONSULT_TRTC_STOP_REGION` 必须由部署侧明确设为 `ap-beijing` 或 `ap-guangzhou`，否则状态为 WAITING_CONFIGURATION，不扫描数据库也不发请求。配置没有在本轮写入任何服务器。

开启后每两分钟扫描最多 10 个 READY/DISPATCHING 待办，单轮有时间上限、游标和实例内防重入。跨节点唯一性靠数据库事务，而不是本机内存锁。部署前必须确认目标应用、实例角色权限和配置，不得通过测试替身伪造腾讯云验收证据。
